改了一条提示，Agent 的任务成功率提高了，这个改动能不能上线？要回答这个问题，需要知道分数来自哪些任务、评分器检查了什么证据、重复运行时结果是否稳定。这条路径的 7 篇文章先看评估方法，再看公开基准和产品自建评测各自能测出什么，最后看评估怎样进入开发流程：复查线上失败、守住关键行为、改进 Skill。

## 先分清几篇相近的文章

路径里有四篇文章都在讲怎样做评估，评估的对象各不相同：

## 路径怎样展开

**先看分数怎样支持判断。** Anthropic 一篇区分任务、单次运行（trial）、执行记录和最终状态，说明程序、模型、人工三类评分器各适合检查什么，并用 pass@k 与 pass^k 区分“至少成功一次”和“每次都成功”。产品评估一篇在原文三步流程之外，用一个假设的知识库问答场景说明：评估器校准以后仍会漏报和误报，缺陷诊断集、代表性抽样集和固定回归集各自能回答什么问题。

**再看公开基准与产品评测。** SWE-bench 一篇解读 OpenAI 对 SWE-bench Verified 的审查：在 o3 反复失败的 138 道题里，59.4% 有测试或题面上的缺陷，另有证据显示部分模型接触过题目相关材料；这个比例只针对难题子集，不代表全部 500 题。CursorBench 一篇介绍 Cursor 的自建评测：任务取自真实开发会话，用 agentic grader 接受合理的替代方案，再用线上实验检查离线分数是否对应使用体验。两篇连着读，可以看到两种评测各自的代价：公开基准便于社区复现和比较，但固定题集在前沿高分段的区分度会下降，题目相关材料也可能进入训练数据；内部评测取材于团队自己的会话，暴露风险较低，代价是构建和维护成本更高，对其他团队是否有代表性要另行验证，外部也难以完整复现。

**最后看评估怎样进入开发流程。** Agent Engineering 一篇把生产 trace 和评估放进同一个循环：从线上失败中找出重复模式，修改以后把这些案例补进回归集。行为评估一篇讨论中间动作的断言能证明多少：解读用“完成前验证”的例子说明，调用过验证工具、验证已经结束、结果对应最后一次修改，是逐级加强的证据；行为评估和端到端评测要配合使用。skill-creator 一篇把同一套思路用在 Skill 上：触发评估和产物评估分开做，产物评估把用了 Skill 的运行和基线比较；解读也指出，描述优化循环里叫作 test 的 40% 留出样例参与了候选选择，承担的其实是验证集的作用。

读完这条路径，应该能回答三个问题：一个分数来自什么任务和评分器，能支持多强的结论；评估器自己出错时怎样发现；一次线上失败怎样变成下次修改之前要跑的检查。
