Agent 每一步做得对不对，很大程度上取决于这一步的输入里有什么：任务目标、相关文件、工具说明、之前的执行结果。上下文工程处理的就是这件事：决定哪些信息进入模型的窗口、以什么形式进入、什么时候移出。这条路径的 16 篇文章先给出概念框架，再看具体机制，最后落到长任务的成本。

## 路径怎样展开

**先理解核心问题。** LangChain 那篇说明上下文工程是什么，以及 Agent 出错时怎样沿输入排查；两篇框架文章再提供一套词汇。第四篇 Computer History 是一个具体场景：Agent 要接着做一段被打断的工作，必须分清三类信息：可以参考的历史线索、需要重新核对的当前来源，以及只能来自用户的授权。

**再看具体机制。** Manus 一篇先给出一个产品团队的整套做法，其中“把文件系统当作上下文”的思路由后面两篇展开。Cursor 的动态上下文发现和 LangChain 的文件系统文章讲的是同一个做法：完整资料存进文件，窗口里只放摘要和读取入口。前者是产品实现，给出了 MCP 工具按需加载后总 token 减少 46.9% 的数据；后者解释这样做为什么有效，以及保存下来的信息仍然要靠检索才能用上。接下来的原创文章讲压缩：Codex 原有的做法在压缩时就要决定以后用到哪些信息，新实验先记下进度、换一个窗口，再按需查询历史。Subagents 一篇讲隔离：探索交给独立的上下文，主会话只接收结果，代价是交接时可能丢信息。

**最后看长任务与成本。** Lance Martin 的模式汇总先把长程 Agent 的几种常用设计放在一起比较；Harrison Chase 的访谈再把上下文、trace 和人工审查放在一起，说明长程 Agent 怎样维持任务连续性。后面五篇都和成本有关：Auto-Caching 一篇先在 API 层说明缓存断点标记的是一个前缀，Claude Code 一篇再看产品怎样围绕稳定前缀设计；Cursor 和 Claude Platform 两篇给出可以照着检查的调整清单，以及各自报告的降幅；Uber 一篇把成本拆到模型选择、工具调用和上下文路径，再用任务质量检验每项优化。

读完这条路径，应该能回答三个问题：一条信息该常驻窗口、按需读取，还是交给子任务处理；压缩历史时，丢掉哪些内容会让下一步出错；为了缓存命中调整上下文布局时，怎样同时检查任务质量。
