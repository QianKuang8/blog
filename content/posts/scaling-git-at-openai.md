当一批 Agent 同时提交代码，Git 服务要处理两种不同的压力：写入之间如何协调，以及相似历史如何分发。分析这两条路径，有助于判断增加服务器之后，哪些工作能并行，哪些仍会排队。

OpenAI 的 [Pando 工程文章](https://openai.com/zh-Hans-CN/index/scaling-git-at-openai/)介绍了两项取舍：按分支协调更新，以因果一致性支持写入扩展；复用包文件服务读取。跨分支读取因此可能来自不同时点，客户端也可能重复传输对象。作者报告，生产环境中的推送延迟中位数下降近 80%。

下面结合 Git 官方文档，用假设例子讨论这些取舍。例子用于分析设计，不是 Pando 的实现规格或压测结果。

## 先问哪些写入必须相互等待

假设两个任务分别更新分支 A 和 B。在引用竞争这一层，A 的更新需确认 A 仍指向预期的旧提交；B 也有自己的更新条件。如果服务额外要求它们先竞争同一个仓库级发布序号，就增加了一处共享等待。

Git 的 [`update-ref` 文档](https://git-scm.com/docs/git-update-ref)提供了理解这种检查的入口：指定旧对象 ID 时，只有引用当前值与之匹配，更新才会成功。这是本地命令的语义，不代表分布式服务直接调用它完成协调。

可以用下面这个假设时序检查设计：

| 请求 | 预期旧值 | 目标值 | 应检查的条件 |
|---|---|---|---|
| 任务一更新 A | A0 | A1 | A 是否仍为 A0 |
| 任务二更新 B | B0 | B1 | B 是否仍为 B0 |
| 任务三也更新 A | A0 | A2 | 若 A1 已生效，应发现旧值不匹配 |

这个例子区分了两类并发：独立分支有机会并行，同一分支上的竞争仍需处理。如果所有任务最后都往主干提交，主干仍有自己的排队与冲突处理成本。因此，测试时可以把“不同分支的完成速率”和“同一分支的重试率”分开测量，避免用一个总吞吐量掩盖热点。

还要检查读取方的需求。如果发布工具把 A、B 两个分支头组合成一个交付版本，就应明确记录这对提交 ID 的关系。分别读取两次“最新分支头”，无法替代应用自己定义的发布清单。哪些业务需要这种配对，应该在放宽协调范围之前确认。

## 一个包能否复用，取决于接收方已经有什么

Git 协议 v2 的 [`fetch` 文档](https://git-scm.com/docs/gitprotocol-v2)用 `want` 表达目标提交，用 `have` 帮助确定客户端已有的历史。文档还定义了 `packfile-uris` 能力，让支持它的双方协商通过额外 URI 下载包。

沿着这个接口，可以构造一个简化的成本模型。设 B 是共同基线，P 包含基线之外的两组对象 p1、p2；这些符号只表示对象集合，不代表完整的 Git 对象图。读取方甲已有 B 和 p1，读取方乙只有 B。

![假设两个客户端共享基线 B：甲已有 p1，乙没有；二者下载同一个包含 p1 和 p2 的包 P，甲会重复接收 p1。](/images/scaling-git-at-openai/shared-pack-example.svg)

*图 1：本文绘制，依据 [Git 协议文档](https://git-scm.com/docs/gitprotocol-v2)构造的假设示例。对象集合用于比较传输方案，不表示 Pando 的实际包内容或性能数据。*

如果为甲、乙分别准备响应，甲可以只接收 p2，乙接收 p1、p2。如果让二者下载同一个 P，服务器能够复用同一份字节，甲则多接收一次 p1。两种方案的工作量分布不同：前者更贴近每个客户端的缺口，后者更容易共享生成结果与缓存。

这里有一个必要前提：下载方必须具备包所依赖的基线。若乙连 B 都没有，单独给它 P 无法补齐历史。因而，可复用包的设计需要同时回答“包包含什么”和“使用它还需要什么”。只统计缓存命中率，会漏掉补齐依赖的工作。

## 比较总成本，也观察等待发生在哪里

可以先用下面的粗略模型组织压测，而不预设哪种方案更快：

- 按客户端生成：累计每次协商、对象选择与打包的工作，再加实际传输量。
- 共享已有包：累计包准备、包选择与分发的工作，再加重复字节、依赖补齐和客户端处理量。

这不是性能公式。它的用途是提醒测试者在服务端 CPU 之外，也记录网络与客户端成本。缓存已热和缓存为空应分别测量；刚落后几个提交的客户端与很久没有同步的客户端，也应分别观察。

另一个需要拆开的指标是“写入完成”与“别人能用”。假设一次推送很快返回，后续 CI 却一直等不到所需对象，那么用户的任务仍然没有推进。适合 Agent 工作流的测量，可以从提交开始计时，直到一个独立工作区获取目标提交并完成检出，同时单独保留推送确认、下载、索引等阶段的耗时。

这个验证方式还有一个好处：它迫使测试覆盖新读取方。重复使用同一个已经缓存全部对象的工作区，很容易漏掉数据尚未可用、依赖未传齐等问题。

## 迁移时，把承诺写成可检查的行为

对准备调整 Git 服务的团队，可以先写一份小型验收矩阵：独立分支同时更新、同一分支竞争、缺少基线的读取、冷缓存获取，以及下载中断后的重试。每项都写明应得到哪个提交、哪些错误允许重试、怎样发现数据不完整。

这份矩阵可以帮助判断优化是否保持了业务需要的行为。不同分支可以并行，并不会自动解决主干整合；包可以复用，也仍需验证每类客户端是否能完成下载与检出。将这些条件与真实工作负载一起测量，才能决定扩容应该投入协调服务、数据分发，还是客户端处理。
