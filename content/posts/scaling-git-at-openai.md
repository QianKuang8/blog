Codex 让一名工程师可以同时推进多项修改，OpenAI 单体仓库的负载也随之改变：分支、推送和合并更多了，开发环境、研究任务和 CI 发起的获取与克隆也更多了，而且彼此叠加，一次推送可能触发多个任务去获取同一个提交。原文的季度图表显示，2026 年第三季度合入 master 的提交量比 2024 年第一季度增长约 1378%。大约从 2025 年底开始，原有系统跟不上需求：获取和推送变慢，合并失败，可靠性一度跌到 90% 以下。

OpenAI 的 [OpenAI 如何扩展 Git](https://openai.com/zh-Hans-CN/index/scaling-git-at-openai/) 介绍了他们的应对：在不改变工程师 Git 用法的前提下，从零构建了一个兼容 Git 协议的仓库后端 Pando。它有两个目标：写入能力可以水平扩展，并针对大量分支的并发推送优化；读取吞吐量足以用满客户端的网络带宽。切换后，推送延迟的中位数下降近 80%，合并可靠性提高到 99.99%（原文图表标注），Pando 每天分发约 1 PB 的 Git 数据。

这篇文章值得细读，是因为它明确说出了 Pando 放弃了什么：仓库级的一致快照，以及为每个客户端单独生成的包文件。下面先看常见方案卡在哪里，再看这两项取舍怎样落到推送、获取和后台压缩上，最后看这个系统怎样用 Agent 构建和迁移。

## 常见方案卡在哪里

Git 仓库要同步两样东西：对象（blob、树、提交、标签，按内容哈希标识、不可变）和引用（指向提交的分支和标签）。获取时客户端用 `want` 和 `have` 告诉服务器需要哪些提交、已经有哪些，服务器算出差集，压缩成包文件发出去。推送方向相反，客户端根据服务器通告的引用排除服务器已有的对象，所以推上来的包可能依赖服务器已有的对象，单独拿到这个包无法重建历史。

把仓库复制到多台服务器时，副本必须先能提供某个引用新值可达的全部对象，才能对外通告这个新值；服务还要协调相互竞争的引用更新。如果所有写入共用一个全局顺序，向互不相关分支的推送也要相互等待。原文建模了两种传统方案：

| 方案 | 写入怎样协调 | 负载上来后的瓶颈 |
| --- | --- | --- |
| 三阶段提交（3PC） | 推送的包并行复制到所有副本，多数副本锁定引用、确认旧值并接受预提交后才生效 | 引用只能逐个更新，每次推送多轮往返；副本磁盘与通信延迟进入推送路径 |
| blob 存储中的共享 WAL | 包并行上传，所有引用更新追加到同一份清单，用比较并交换发布 | 无关分支也争用同一份清单；副本要先读取包、建好索引才能服务读取，写入快时副本落后 |
| Pando | 每个分支独立更新，只有引用指针用类似比较并交换的操作保护 | 客户端、网络或 blob 存储的容量 |

原文附带一个交互式教学模拟：1000 个客户端各推一个分支（模拟中放宽了 3PC 的全局一致性要求）。负载下，3PC 因磁盘饱和写入延迟明显升高，WAL 因服务器读不完日志而读取延迟明显升高。页面标明这是教学模拟，生产数据见后文。

## 放弃仓库级一致快照：按分支保证顺序

Pando 把每次推送的包作为不可变 blob 写入 blob 存储；每次分支指向变化，在元数据存储里记一条**引用版本**：新的分支头、提供它的包，以及这个包依赖的所有先前引用版本。两种存储都可以水平扩展。获取某个引用时，Pando 把相关的引用版本（也就是一组包）重放给客户端，重建写入方当时的状态。

原文称之为**因果一致性**：读取方看到的是产生这个引用的写入方所经历的历史。单个引用的更新可串行化，只有同时推送同一个引用的客户端才会冲突。代价是读取多个分支时，结果可能来自不同时间点。原文的例子是：一次完整克隆协商期间，`foo` 和 `bar` 都更新了，一个客户端可能看到 `foo` 的版本 1 和 `bar` 的版本 2，另一个客户端看到的恰好相反。作者的判断是，用户和 Agent 实际依赖的是单个引用的更新顺序，并不依赖全局顺序。

![左侧是主干：三个连续的包分别包含提交 A、B、C，D、E，以及 F。右侧是主干与主题分支在 C 处分叉：主干推进到 G，主题分支依次推进到 D、E、F；最新的主题分支包包含 D、E 和 F，虚线框标明 D、E 也在此前的主题分支包里，箭头标明新包依赖主干的 G 版本。](/images/scaling-git-at-openai/pando-branch-packs.svg)

*图 1：原图，来源：[OpenAI 如何扩展 Git](https://openai.com/zh-Hans-CN/index/scaling-git-at-openai/)。主干每次推送只新增一个增量包；主题分支每次推送都重新带上分支此前的提交，并以某个主干版本为基础。*

图 1 说明了包怎样组织：向主干推送，新增一个只含新提交的增量包；向主题分支推送，包里会再次带上这个分支此前的提交。这样，已有这个包所依赖的主干版本的客户端，只需下载一个包就能拿到整个主题分支。

我的理解是，放松一致性的成本落在“同时读多个分支”的工具上。比如发布工具要把两个分支头组合成一个版本，就应当自己记录这对提交 ID，不能指望两次读取“最新分支头”得到同一时刻的状态。迁移到类似系统之前，值得先清点有哪些工具做了这种假设。

## 推送：只通告主干，让包可以复用

传统 Git 服务器在推送时会通告自己拥有的每一个分支，客户端据此排除服务器已有的对象，生成尽量小的包。通告得越多，包越小，但也越难复用：其他客户端可能恰好缺少写入方省略掉的对象。反过来，完全不通告引用，客户端就会推上整个历史，任何人都能用这个包，代价是每次获取都相当于一次完整克隆。

![曲线：横轴是通告的引用数量，从无到全部；纵轴是包大小。不通告引用时包含完整历史；通告主干后包大小迅速降到低位；通告全部引用时只含新对象，与只通告主干相差不多。](/images/scaling-git-at-openai/advertised-refs-pack-size.svg)

*图 2：原图，来源同上。只通告主干一个引用，就可能拿到大部分体积缩减。*

Pando 只通告选定的一组引用：客户端推送新功能分支时，默认只通告指定的主干。原文给了两个理由。其一，分支达到数百万时，仅引用通告就可能超过 100 MiB，要提供一致的全量视图，每台服务器要么维护最新映射、承担大量协调开销，要么执行随引用数增长的数据库查询。其二，客户端生成的包只依赖服务器明确允许它排除的对象，Pando 就能跟踪每个包的依赖，把推送时收到的包直接作为后续获取的响应。

这项取舍的代价也写得很具体：反复推送同一分支，或者在一个功能分支上再叠一个功能分支时，客户端要重新发送主干之外的全部内容，包里可能有冗余对象，消耗更多客户端带宽。在 OpenAI 的单体仓库里，这样生成的包大小中位数低于 20 KiB，第 99 百分位低于 3 MiB。作者认为这是合理的代价，因为有主干历史的读取方只需这一个包。

服务器这一侧，Pando 一边把传入的包流式写入 blob 存储，一边单遍解码验证，不把包解开到本地仓库。元数据更新分成两部分：同步部分写入新的引用版本、更新引用指针、记录协商时使用的依赖和包的链接，保证客户端能立刻读到自己刚推的提交；合并压缩等异步工作的调度记录在同一个事务里。规模很大的推送只同步写入部分提交，所以无论推送多大，一次写入的元数据读写次数都是常数。唯一存在争用的键是引用指针，因此增加 Pando 服务器、元数据存储单元或 blob 存储，就能提升写入吞吐量。

为配合这种方式，OpenAI 在自己维护的 [Git 版本](https://github.com/openai/git) 里引入了“显式 have”：服务器可以分别通告功能分支当前的头提交，以及推送方可以从包中省略的历史。客户端因此能用 `--force-with-lease` 确认功能分支没被别人改过，同时只以主干为基础构建包。

## 获取：选包、发链接、走区域缓存

获取时，Pando 不再为每个客户端计算对象差集。它用推送时记录的提交映射，把客户端的 `have` 和 `want` 解析成一组引用版本，每个引用版本对应一个此前收到的包，再选出覆盖所需对象的包。需要某个侧分支，也就需要主干上直到该分支所依赖版本的历史。这一步需要 *O(log Δ)* 次元数据读取，Δ 是客户端已有版本与所需版本之间以引用版本计的最短距离。

Git 协议只允许在克隆或获取的 HTTP 响应里放一个包文件。协议 v2 的 [`packfile-uris`](https://git-scm.com/docs/gitprotocol-v2) 能力允许服务器返回链接，让客户端另外下载其他包。Pando 完全依赖这项能力：响应正文里只有一个空包，所有数据都通过 URI 下载，OpenAI 也为此向上游贡献了多项改进。

下载由包分发服务 Express 承担，它在每个区域为 blob 存储做缓存，另有一个服务缓存元数据存储。Express 用一致性哈希路由包请求，缓存命中率超过 99%；在云厂商的标准虚拟机上，克隆和获取可以用满 10 Gbps 链路。代价是客户端可能下载一些自己已有的对象，换来服务器只做协商和选包这类很少的计算，所以 Pando 能在普通硬件上运行。

还有一个问题：如果每次推送都对应一个独立的包，客户端每天要下载数万个包才能让本地主干跟上。Pando 借用 LSM 树的合并压缩思路：每次推送产生一个 L0 包，后台把它们归集成覆盖一段引用版本、规模按几何级数增长的“覆盖集合”，单体仓库目前用到 L4。覆盖集合有两个用处：攒够内容后重新打包，提高压缩率；同时充当引用版本上的跳表，让选包能在对数时间内完成。各层的包都保留，按客户端的 `have` 和 `want` 分别使用；通过 API 读取单个对象时，从 L0 读通常比从 L4 读的数据更少。

## 怎样构建和迁移

原文第二部分讲的是工程过程，同样有不少具体做法：

- **构建**：从项目启动到投入生产用了 10 周，核心由一名工程师设计，多个 Agent 团队用 Codex 实现，少数几位工程师部署，2026 年 4 月开始承接生产流量。
- **验证**：用 Rust 从零实现，不引入遗留依赖；一套一致性测试让 Agent 可以对照标准 Git 行为检查自己的修改；确定性模拟测试框架检查系统不变量，发现了协商与选包中的竞态和回归。借助 GPT-6 Astra，Agent 写出了 Lean 和 TLA+ 形式化描述，用来发现缺陷、证明系统属性，多个会话持续运行了数百小时；另有 Agent 全天候对 Git 和 Pando 做红队测试。
- **迁移**：Pando 先作为原有系统前面的读穿透、写直达代理运行，两边保持同步，流量逐步切换、不停机；代理转发前还会对请求去重和合并；随着更多工作负载迁过来，旧后端的可靠性也随之提高。OpenAI 向开发者机器和 ChatGPT 桌面应用分发自己的 Git 发行版，通过内部 Git 命令行封装分阶段切换客户端，并迁移了数百个依赖旧 API、webhook 和仓库下载的集成。开发者可以直接让 Codex 用准备好的 Skill 迁移自己的开发环境和服务。

切换后的数字：推送延迟中位数下降近 80%；原文绘制了 37 个工作日里合并基础设施的每日成功率，标注切换后的合并可靠性为 99.99%；Pando 只用少量 CPU 核心，每天分发约 1 PB 数据，曾在一小时内分发超过 57 TB，其中超过 99% 来自本地磁盘缓存。

运行中暴露的 Git 客户端问题，OpenAI 也做了修复和改进：并发下载、传输中断后的清理、恢复已完成的下载等路径的修复，接受已有包时增加的验证，以及为 `packfile-uri` 下载和包生成增加的耗时与字节统计，用来区分一次慢获取是慢在生成包还是传输包。其中一些改进已经进入上游 Git，另有许多发布在 OpenAI 的公开代码仓库中。

我的理解是，“10 周用 Agent 写出一个 Git 后端”能成立，靠的是验证手段先行：一致性测试给出标准 Git 这个现成的参照，确定性模拟和形式化描述覆盖并发场景，读穿透、写直达的代理让新旧系统保持同步，流量可以逐步切换。这些做法对其他用 Agent 重写基础设施的团队更有参考价值。

## 适用条件

这一节是我的归纳。Pando 的两项取舍适合这样的仓库：一个主干，大量互相独立的分支，读取方大多已经有较新的主干。在这个前提下，按分支协调让独立分支的推送互不等待，只通告主干让包可以直接复用。成本落在三类场景上：同时读取多个分支并假设它们来自同一时刻的工具；反复推送同一分支或叠加分支的客户端，要重传主干之外的内容；已有部分对象的客户端会重复下载一些对象。

评估类似改造时，可以借用原文模拟里的指标“从推送到获取的时间”：从第一次推送尝试算起，到另一个独立的读取方验证拿到这个提交为止。只看推送确认很快，可能掩盖读取方迟迟拿不到所需对象的问题。
