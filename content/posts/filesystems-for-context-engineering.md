一次搜索返回一万 token，并不意味着下一步推理需要一万 token。若每次工具结果都完整留在消息历史里，Agent 会不断为已经不相关的内容付出成本。LangChain 的 [How agents can use filesystems for context engineering](https://blog.langchain.com/how-agents-can-use-filesystems-for-context-engineering/) 讨论了另一种组织方式：先保存材料，再让模型按任务需要寻找和读取。

文件系统在这里提供统一的存取接口。它可以保存工具结果、计划、技能说明和阶段性产物，但“已经存下来”只解决了信息可用性的一部分。模型还需要找到正确位置，并把合适的内容带回当前上下文。

## 先区分三种信息集合

原文用三种颜色表示可用信息、完成当前任务所需的信息，以及 Agent 实际检索到的信息。上下文工程的目标，是让检索结果覆盖必要内容，同时尽量少带入无关材料。

这个视角能区分三种失败。第一，必要文档根本没有接入，检索再好也找不到；第二，文档已经存在，却没有被召回；第三，只需要一页内容，却读入了上百页。它们分别对应数据接入、查找能力和检索范围，不能都归结为“模型没理解”。

还有一种情况是必要材料本身就超过窗口容量。这时无法靠一次更精准的搜索解决，需要分阶段阅读、保存中间结果，再围绕子问题继续获取信息。文件系统为这个过程提供了外部工作区。

## 长工具结果从历史消息转为可查材料

文章以搜索结果为例：工具返回大量内容后，先将其写入文件。Agent 可以随后搜索关键词、定位行号，再只读取相关片段。输入窗口因此承载当前推理所需的部分，原材料则仍可在后续步骤中重新访问。

这一改变的收益来自“选择性读取”，而非写文件动作本身。如果模型保存以后马上把全文重新读回，上下文占用不会减少；如果只保留摘要却没有可靠的原文路径，也可能失去复查依据。由机制可以推导，文件名、目录结构和返回给模型的定位线索，都属于上下文接口设计的一部分。

同一方式也可用于计划。将目标和进度写入文件，之后按需读取，可以在长任务中重新提醒模型当前要做什么。这里的文件充当工作记忆，不能仅凭磁盘存在就认定模型下一轮一定会使用它。

## 精确搜索与语义搜索可以分工

对于代码符号、接口名称等内容，语义相似性未必能表达用户寻找的对象。原文指出，目录层级常已经反映项目结构，而 `ls`、`glob`、`grep` 和按行读取可以逐步收窄范围。

一个典型过程是先列目录定位模块，再按文件名筛选候选，接着搜索符号，最后读取命中处的上下文。这保留了精确名称与结构关系，也让模型能够根据前一步结果调整下一步搜索。

但这不是文件搜索对向量检索的全面替代。用户可能只知道概念，不知道符号如何命名；这样的输入仍可能需要语义检索来提供入口。文章明确认可两者结合。可迁移的原则是按信息形态选择检索手段，并检查是否覆盖完成任务所需的证据。

## 文件也能承接协作与按需指令

多 Agent 任务中，子 Agent 可以把完整发现写入共享文件，再把路径和重点交给主 Agent。这样减少了消息转述的信息损失，也让负责人能够回查详细材料。不过，负责人是否真的读取，以及文件内容是否足以支持结论，仍是另外的验收环节。

技能指令采用类似方式：模型先通过简短描述识别相关能力，再读取具体操作说明，避免把全部流程预先塞进系统提示。这把文件系统同时用于任务数据和操作知识，但两者的角色需要清楚——外部材料提供待分析的信息，技能文件提供预先约定的工作方法。

## 保存用户反馈，不等于完成学习

原文最后讨论一个尚在探索的方向：用户指出缺失的规则或偏好后，Agent 把它写入文件，使后续任务能够使用。这个过程改变的是可检索上下文，并没有修改模型权重。

难点也从“能否写入”转移到了“应当记住什么”：反馈是否只适用于当前任务，是否与旧规则冲突，以及后续何时再次加载。作者明确表示，这种自动更新指令的模式尚未完全解决，因而不能把它理解成可靠的自我改进已经成立。

文件系统提供了一种朴素的分层：详细内容可以留在窗口外，当前步骤再按需要取用。其效果应沿保存、定位、读取和使用的完整过程检查。只要其中一环失效，外部存储再大，也不能弥补当下决策缺少关键信息的问题。
