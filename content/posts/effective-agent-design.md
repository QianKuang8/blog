长任务会不断产生文件、工具结果、失败尝试和中间决策。把它们全部放进一条不断增长的消息历史，模型既要维持目标，又要从越来越多材料里寻找下一步所需信息。

Lance Martin 的 [Effective Agent Design](https://x.com/RLanceMartin/status/2009683038272401719) 从多篇产品博客与研究中总结了一组做法。它是一篇设计模式综述，并非统一条件下的性能比较。阅读重点可以放在几个具体问题上：状态存在哪里，能力怎样被发现，重复输入怎样计费，以及拆分任务以后如何交接。

## 计算环境把窗口与持久状态分开

作者从“给 Agent 一台电脑”开始。文件系统提供持久化空间，shell 让模型调用系统工具、CLI、预置脚本或自己编写的程序。中间数据不必全部作为文本消息长期保留。

这进一步形成多层 action space。模型接口上可以只有少量原子工具，例如 shell；shell 内再调用丰富的程序能力。模型也可以编写代码串起多个操作，在程序里筛选中间结果，只把最后需要的部分返回上下文。

这个模式并没有减少底层能力的复杂度，而是改变了复杂度出现的位置。模型需要能够选择程序、理解参数、检查执行结果；运行环境也仍需管理权限与错误。少量顶层工具只有在这些条件成立时才足够有用。

## 渐进披露负责告诉模型“去哪里找”

能力放到环境中以后，还需要发现入口。原文举了几种方式：提供可用 CLI 名称，再让模型按需读取帮助；给工具说明建立索引，在任务需要时检索；Skills 先加载名称和描述，再读取正文与附属资料。

这些方式共同区分了两类输入：用于判断相关性的简短描述，以及实际执行时才需要的细节。前者常驻可以减少发现成本，后者延迟加载可以避免无关定义占用当前窗口。

Cursor 将 MCP 描述同步为文件，就是这条思路的具体例子。它与“少给信息”不同：完整资料仍存在，而且有明确的访问路径。若入口遗漏某项能力，Agent 可能根本不会去寻找；若描述过于宽泛，也可能频繁加载无关内容。发现质量与读取成本需要一起观察。

## 外置、压缩与缓存解决不同问题

Offload 把长工具结果或完整轨迹移到外部文件，窗口保留引用和当前需要的部分。相比只留下摘要，它保留了回查细节的机会。计划也可以写到文件，并在后续步骤重新读取，帮助恢复目标与进度。

压缩则在更小的表示中保留信息，通常伴随选择与损失。原文描述的做法可以结合使用：先外置大块结果，必要时再总结；如果摘要遗漏了某个条件，仍可回到文件核对。

Cache 的目标又不同。提示缓存复用稳定前缀的计算，降低重复调用的费用和延迟，却不直接缩短逻辑上下文。修改早期消息或工具定义，可能改变前缀，让后续请求失去部分复用机会。

因此，不能只问“这段上下文还要不要”。还要分别问：它是否需要留在窗口，是否需要保留可恢复的原始信息，以及移动或改写它会怎样影响缓存。原文引用了 Manus 对缓存命中率的重视，但没有给出所有系统都应遵循的唯一成本目标。

## 隔离上下文以后，交接成为新约束

独立子 Agent 可以并行检查不同问题，也可以承接主会话不需要保留全部过程的探索。长任务还可以分成多个会话，通过计划文件、进度记录和 Git 历史继续。

这些方式减少单个窗口承载的材料，却把压力转移到交接。执行者必须拿到目标与相关约束，负责人必须收到足以判断结果的证据。如果只返回一句“完成”，主会话虽然干净，却可能失去验证依据。

原文在未来方向中也讨论了多 Agent 的冲突：各自的动作会包含隐含决策，如果彼此不可见，就可能出现不兼容实现。独立上下文适合可分离的调查和检查；共享接口、产品取舍和跨模块修改，则更需要明确的协调状态。

因此，更多窗口并不直接等于更好的长任务表现。应当同时观察节省了多少主会话负担，以及新增了多少重复调查、沟通与集成工作。

## 经验更新发生在上下文层

最后的 Evolve Context 指向一种较具体的学习：从既有轨迹中提炼经验，更新提示、记忆或 Skill，而不是修改模型权重。

原文以 GEPA 的模式说明任务提示优化：收集轨迹、评分、反思失败、提出候选提示，再测试。作者也介绍了从会话日记更新 `CLAUDE.md`，以及把重复流程沉淀为 Skill 的尝试。

这条路径需要把“保存经验”和“证明改进”分开。一次失败后的解释可能不准确，某条规则也可能只适用于局部场景。写入之后还应在后续任务中比较结果，保留适用条件，并移除已经过时的约束。这是由原文流程引出的维护要求。

把这些模式连起来，会得到一套可检查的分工：环境保存完整状态，发现机制选择当前材料，缓存降低重复成本，独立会话控制局部上下文，评估决定哪些经验值得留下。选择其中哪几项，应从当前失败和成本结构出发，而无需一次搭齐全部组件。
