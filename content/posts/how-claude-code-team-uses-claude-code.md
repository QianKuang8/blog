这场 [Claude Code 团队访谈](https://www.youtube.com/watch?v=S-sYlFiGFv8) 讨论了一种协作变化：工程师开始把目标交给代理，减少对每次工具调用的监督。上下文、执行环境、工作流、验证和真实反馈，则让这些更大的委派目标有了可检查的结果。

视频原题是 *How the Claude Code team uses Claude Code*，由 Claude 频道发布，参与对谈的是 Thariq Shihipar、Sid Bidasaria 和 Robert Boyce，发布于 2026 年 9 月 2 日，时长 22 分 23 秒。本文依据人工英文字幕、时间戳和 14 页中文学习讲义整理。视频中的 Claude Tag 是团队在 Slack 中使用的代理；访谈没有说明它、dynamic workflows 或 routines 对所有用户的开放范围，因此本文只把它们作为当时的团队实践来讨论。

## 四个核心结论

1. 目标委派需要代码之外的产品背景和团队决策；提示词变长不能替代上下文。
2. Harness 应跟着模型失效模式和任务规模调整：旧补偿可以退场，新任务也会暴露新的工具需求。
3. 多代理并行的价值不在输出更多，而在“广泛查找—逐项复核—压缩汇总”的完整结构。
4. 减少逐次监督后，验证、代码审查和真实反馈仍要接得上，人才能把注意力移到系统边界与产品判断。

## 从任务委派走向目标委派

团队回顾，一年前的使用方式还围绕提示、反馈和逐次确认权限展开；现在，他们交给代理的问题已经远比“实现这个类”或“写这个函数”复杂。一位成员估计，自己约 70%–80% 的工作发生在 Claude Tag 中，剩余约 20% 才会打开终端界面或桌面应用继续调整。他更少检查单次调用和局部决定，更关注“我有一个目标，希望它被完成”。这是个人口述的工作比例，不是团队统计，也不代表所有开发者都适合这种用法。[00:00:35–00:02:17](https://www.youtube.com/watch?v=S-sYlFiGFv8&t=35s)

目标变大后，代理需要的信息也会变。Claude Tag 生活在 Slack 中，可以接近产品讨论和团队已经作出的决定。写一个局部函数时，相邻代码也许足以说明要求；推进一个产品目标时，代理还要知道为什么要做、哪些历史选择构成约束。访谈把这类背景与更好的决策联系起来，但没有展开权限、检索或索引的具体实现。

从这个例子可以看出，目标委派需要代理获得作出选择所需的背景。缺少产品意图、历史决策和验收标准时，目标越宽，错误方向上的执行空间也越大。

## Harness 跟着模型能力和任务规模调整

这里的 harness 指围绕模型搭建的工具、执行与交互支撑。团队用待办列表解释这些支撑为什么会随模型变化。早期模型接到五件事，可能完成三件就停下；显式待办能帮助它继续推进。模型变强、出现更复杂的记忆状态后，这项补偿的必要性下降，团队便可以重新评估甚至移除它。[00:03:19–00:04:48](https://www.youtube.com/watch?v=S-sYlFiGFv8&t=199s)

这段话容易被简化成“模型越强，harness 越薄”，但受访者紧接着谈到另一面：能力提高后，人会交给代理更大、更难的任务，新的连贯性问题又会出现。工具设计面对的其实是“当前模型能力 × 当前任务规模”。旧失效模式消失时，应删除已经失去价值的支撑；任务边界扩张时，也要补上新的环境、权限、交互和验证能力。

AskUserQuestion 的变化提供了另一个例子。它最初是规划之后的提问步骤，后来成为模型可按需调用的工具；一位成员最近又会让 Claude 创建带图示和 mockup 的 HTML artifact，通过可视化方案向他提问。[00:05:39–00:06:41](https://www.youtube.com/watch?v=S-sYlFiGFv8&t=339s) 这是个人工作方式的演变，不能写成 AskUserQuestion 已被 artifact 全面替代。更值得注意的是，提问、权限和可视化都被当作可重新组合的基础能力，而不是固定不变的产品流程。

## 持续执行先解决运行条件，再讨论自动化

Loops 的起点很朴素：任务过去运行在个人笔记本上，下班关机后代理也停止。团队成员先转向远端开发机，又经历 SSH 回连的摩擦，随后把 Claude Code on the web 的托管容器放进这条演进路径。远端环境让任务可以在后台继续，但要真正开发软件，容器仍需接入可构建、可运行、可检查的开发环境。[00:06:48–00:08:14](https://www.youtube.com/watch?v=S-sYlFiGFv8&t=408s)

持续运行又让 routine 成为可能。视频给出的例子是：每天收集反馈，按重要性归类，再处理代理有较高把握修复的问题。[00:08:14–00:08:52](https://www.youtube.com/watch?v=S-sYlFiGFv8&t=494s) 这里保留“高把握”很重要。讲者没有主张所有反馈都自动修改，更没有描述自动合并或部署。远端执行解决任务能否持续运行，routine 描述工作如何反复发生；调度、状态保存和发布边界仍取决于具体实现。

## 并行查找之后，必须逐项验证再收敛

代码生成加快后，审查很容易成为新的瓶颈。团队认为，代理可以先处理那些用来证明“我认真读过代码”的细小问题；人的注意力更适合放在 API 为什么这样设计、服务边界为什么画在这里，以及改动是否尊重历史取舍。这不是取消人工审查，而是把稀缺的背景判断留给人。[00:09:16–00:10:42](https://www.youtube.com/watch?v=S-sYlFiGFv8&t=556s)

为了提高发现问题的覆盖面，他们会让多个代理并行搜索潜在 bug。广泛搜索会产生更多候选，也会混入不成立的问题，因此下一步不是把列表直接交给审查者，而是对每个候选从三个不同视角进行对抗式复核，再过滤、排序和汇总，只呈现最需要人关注的部分。[00:10:42–00:11:48](https://www.youtube.com/watch?v=S-sYlFiGFv8&t=642s)

这里的“三个视角”用于复核每个候选 bug，不是三个固定的搜索代理或三种预设角色。视频也没有提供准确率、漏报率和成本数据。多代理增加的是推理阶段投入和搜索范围；候选生成之后的质疑与收敛，则帮助审查者判断结果是否可信。

*图：根据原视频 [00:09:16–00:14:04](https://www.youtube.com/watch?v=S-sYlFiGFv8&t=556s) 整理重绘。分支数量只作示意；复核针对候选问题，不代表固定的代理角色配置。*

团队随后把这一结构从专用代码审查扩展到动态 workflow：Claude 可以按问题决定子代理如何分支、怎样连接、上一层输出怎样进入下一层，再用程序组织遍历和汇总。受访者特别喜欢让代理写出清晰的 `for` 循环，保证一组项目被逐项处理；循环内部仍由模型完成语义判断。[00:11:48–00:14:04](https://www.youtube.com/watch?v=S-sYlFiGFv8&t=708s) 确定性代码让执行骨架更容易检查，却不能保证循环里的分析必然正确。

## 完成代码只是反馈闭环的中段

团队用 Claude Tag 开发 Claude Tag 时，首先投入的是让代理能进入开发环境，构建软件并验证端到端结果。代码生成只是其中一步；如果代理不能运行和观察产品，就无法自行完成“修改—检查—继续修改”的循环。[00:14:04–00:14:51](https://www.youtube.com/watch?v=S-sYlFiGFv8&t=844s)

Slack 中的消息界面也没有展示全部执行细节。按受访者描述，代理通过消息工具选择何时沟通、发送什么内容；用户可以关注进展和结果，需要细查时再通过链接打开完整 transcript。[00:14:51–00:16:13](https://www.youtube.com/watch?v=S-sYlFiGFv8&t=891s) 沟通经过筛选，并不等于执行记录被删除，更不表示人可以读取模型的原始内部思维。它改变的是默认注意力：日常看目标和结果，必要时再深入过程。

一个内部工具案例把这套方法串了起来。开发者先让 Tag 寻找可能支持想法的同事，制作 mockup 并实现功能；随后加入事件监测并在内部部署，观察用户是否完成整个流程，同时接收 Slack 中的反馈。从事件中判断用户似乎没有走完整个流程时，他原本准备让 Claude 实现自己想到的改法，后来改为让 Claude 围绕“如何改善漏斗”提出方案，自己的点子只作为示例。[00:16:13–00:17:26](https://www.youtube.com/watch?v=S-sYlFiGFv8&t=973s)

这段案例的重点不在某个功能，而在问题没有停在代码合并处。验证回答实现是否按预期运行，代码审查回答设计和代码有什么问题，真实反馈回答人们怎样使用、哪里仍不满足需求。测试、截图、操作录像和亲自试用帮助建立对实现的信心，事件、指标、Slack 与 GitHub issues 则把产品使用带回下一轮决策。访谈明确提到成员当时仍会克隆项目并亲自试用；未来也许减少这一步，只是他的展望。[00:17:26–00:18:37](https://www.youtube.com/watch?v=S-sYlFiGFv8&t=1046s)

## 扩大委派前，先确认哪些证据能回来

从这些案例可以归纳出，自治程度不能只由模型能写多少代码决定。目标是否带着必要背景、环境是否允许实际验证、工作流是否包含质疑与收敛、投入使用后的反馈能否回流，共同决定了代理可以走多远。

工程师减少对每次工具调用的监督，并不等于判断退出流程。判断被重新分配了：程序表达可检查的执行骨架，代理承担大范围搜索与语义分析，测试和真实反馈提供证据，人负责系统边界、产品意图和最终取舍。团队案例很有启发，但计算成本、通知频率、收敛条件和人工验收范围都没有通用阈值，需要在自己的任务中验证。

访谈最后谈到工程师怀念的手艺：有人怀念亲手做性能优化，有人怀念花一天用 CSS 打磨 Aqua 按钮，但他们也享受从想法到生产更快、能处理过去不熟悉的问题。[00:18:37–00:22:17](https://www.youtube.com/watch?v=S-sYlFiGFv8&t=1117s) 工具改变了手工过程，也扩大了可以尝试的范围；提出什么问题、为什么做、怎样判断完成，仍然是工程工作的主体。
