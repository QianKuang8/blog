把一个模块的接口改掉，通常还要找到调用方、调整错误处理、更新测试，再检查行为是否一致。聊天助手可以逐步给建议，但如果文件由人来搬、错误由人来回传，这些步骤仍由开发者手动连接。

Anthropic 的 [《Introduction to agentic coding》](https://claude.com/blog/introduction-to-agentic-coding) 将 agentic coding 定义为接收高层目标、拆分并执行步骤，再依据环境反馈调整方案的工作方式。它讨论的是执行范围与自主程度：一次交付可以覆盖相关文件和验证过程，而不只是一段待复制的代码。

## 目标怎样变成一组可执行的修改

原文用“给 API 加认证”说明上下文收集。Agent 先查看路由定义、现有中间件、会话管理和项目配置，再决定哪些端点需要保护、哪些能力可以复用。输入是一句目标，第一阶段的产出应该是对当前实现与约束的理解，以及据此形成的计划。

接下来才是协调修改。认证可能同时影响服务端路由、数据库结构、客户端、文档和测试。如果只生成一个中间件函数，其余调用关系并不会自动成立。Agent 需要把这些关联变化放进同一任务，再用构建或测试暴露不一致。

计划因此可以随新发现修订。已有机制能够满足目标，就不必重复建设；执行时发现兼容限制，就要重新检查方案。这里的自主性体现为选择下一步调查与修改，并不意味着用户的一句话已经包含完整的验收标准。

## 终端提供环境反馈，界面形态不决定能力上限

文章以 Claude Code 为例，介绍它在项目目录里读写文件、调用命令、运行测试以及使用 Git 的方式。把 Agent 接到实际工具链后，测试输出可以直接成为下一轮输入，减少人工复制结果的步骤。

终端是实现这种接入的一条路径。原文以浏览器聊天和局部补全作比较，但不能据此推导 IDE 或浏览器产品天然无法执行完整任务。能够访问哪些文件和工具、得到什么反馈、如何约束操作，才决定执行范围。

原文还介绍了当时的权限交互：用户可以查看并批准文件变化。权限解决“是否允许执行”，验证解决“执行结果是否满足目标”，两者要分别成立。一次被允许的命令可以失败，一次成功退出的测试也可能没有覆盖新需求。

## 外部上下文要与项目中的事实对齐

本地代码能够回答“当前实现是什么”，却未必包含产品约定、问题背景和外部系统信息。文章提到通过 MCP 连接更多工具与系统，让这些材料进入任务上下文。

获取材料只是第一步。例如，一份接口说明和实际代码存在差异时，Agent 还需要识别冲突，而不能把两者混成一套确定事实。这里的工程要求可以归纳为：让任务相关材料可读，并让验证落到当前环境。来源越多，越需要保持信息与其适用范围的对应关系。

原文对“读取整个代码库”的表达描述了项目级访问能力，不能理解为每轮都应把所有文件装进上下文。它列出的实际过程是读取配置、检查测试、沿 imports 追踪依赖；这些按任务选择材料的动作，才是实施时可观察的步骤。

## Rakuten 案例说明了什么

文章引用 Rakuten 在 vLLM 中实现特定激活向量提取方法的案例：Claude Code 持续工作约七小时，工程师期间提供少量指导，最终实现相对参考方法达到原文所称的 99.9% 数值准确度。

这组数字应作为 Anthropic 转述的客户案例阅读。99.9% 描述的是该实现与参考方法的数值结果，不是任意代码任务的成功率；七小时说明这一任务的运行时长，也不证明全程无人工介入。本文没有独立复现该案例。

更便于迁移的是案例的验收形态：目标是一项具体实现，存在参考方法，运行结果可以比较。这样的反馈使 Agent 有条件持续迭代。若目标只有“改善架构”或“提高质量”，团队需要先把预期结果说清楚，才能知道循环何时应该结束。

对于开始采用这种工作方式的项目，原文建议从测试补充、文档、常规重构和需求明确的功能入手。它们通常更容易建立完成标准。开发者可以逐步观察 Agent 搜集了哪些依据、改了哪些文件、验证覆盖了什么，再决定把多大范围交给下一次任务。
