在一个已有十万 token 历史的会话里，把简单问题切给单价更低的模型，未必更便宜。Claude Code 团队在 [《Prompt Caching Is Everything》](https://x.com/trq212/status/2024574133011673516) 中用这个例子提醒：切换模型还可能失去此前的缓存，需要重新处理长前缀。

文章围绕当时 Claude Code 的实现，解释缓存约束怎样影响 Harness 设计。缓存复用降低重复输入的计算开销，但具体收益仍取决于请求布局与实际命中，不能只看模型标价或提示长度。

## 从共享最多的内容排到变化最多的内容

Prompt caching 按前缀匹配。请求开头的内容改变后，后续部分即使文字相同，也可能无法沿用原来的完整前缀。原文因此将静态系统提示与工具放在前面，随后是项目级 `CLAUDE.md`、会话背景和持续追加的消息。

这里的顺序体现共享范围：通用说明在多次调用间稳定，项目材料在同一项目内稳定，会话历史则随当前任务增长。它描述的是复用机会，不能据此推导缓存会跨越任意账户或权限边界。

团队列出的失效原因都很具体：静态提示里加入精确时间戳、工具定义顺序不稳定，以及更新工具参数。这些变化可能看起来很小，却出现在较长历史之前。排查命中率下降时，比较实际请求的前缀差异比只比较自然语言含义更有效。

## 让状态变化以新消息进入

用户修改了文件，或者会话进入另一个模式，都需要模型知道新状态。原文建议在后续用户消息或工具结果中加入更新，而不是反复改写早期系统提示。这样可以保留旧前缀，同时明确告诉模型哪些事实已经变化。

Plan Mode 的例子更进一步：保留工具定义，用 `EnterPlanMode` 和 `ExitPlanMode` 表示状态转换，再通过消息说明当前应探索、不要编辑等行为。这个实现避免因模式切换而替换整套工具定义。

但缓存友好的状态表达与权限执行不是同一件事。提示可以说明允许行为；若系统需要强制限制写入，还应由执行侧机制保障。原文介绍了保持前缀的方式，没有提供足以据此推断完整权限实现的细节。

工具很多时，文章介绍的 Tool Search 也采用类似思路：稳定保留轻量工具名称与延迟加载标记，需要时再取得完整 schema。目标是避免每次把所有说明塞进请求，也避免通过随意增删前部定义破坏缓存。

## 旁路任务也要检查前缀

会话压缩需要读此前历史并产生摘要。如果另起请求时换了系统提示、删掉工具定义，模型面对的前缀就与父会话不同，可能无法复用刚刚积累的缓存。

原文描述的 cache-safe fork 保留父会话的系统内容、上下文、工具定义和已有消息，在末尾追加压缩请求。对于缓存系统，这仍是原有前缀继续增长，新增部分主要是压缩指令。运行时还要预留 compaction buffer，为这条指令和摘要输出保留空间。

这并不意味着压缩后的新会话可以永远沿用全部旧历史缓存。文章解释的是“生成摘要这一旁路调用”怎样复用父前缀；拿摘要替代历史以后，请求内容已经发生变化，后续缓存效果需要重新观察。

## 模型切换要比较整次调用的账单

缓存与模型绑定，是原文“不在会话中途换模型”的依据。对于短任务，读取已有长前缀的费用可能低于让另一模型从头处理。但文中的十万 token 例子依赖当时价格和调用条件，不构成任何场景下都不能切模型的规则。

文章提出通过 subagent 传递较短交接材料，把某项工作交给另一模型。这样避免搬运整段会话，也增加了摘要与返回结果的成本。是否划算，需要把委派、执行、检查和可能的返工一起计算。

团队还把缓存命中率纳入告警，下降严重时按事件处理。这说明产品成本和延迟对请求稳定性敏感，但命中率本身不是任务质量指标。为了保留缓存而忽略新事实，或让无用历史不断膨胀，都可能损害最终结果。

可借鉴的做法是同时检查两条链：请求怎样变化，任务是否正确推进。稳定内容尽量复用，动态状态明确传递；需要重建上下文时接受合理的失效，再用真实费用、延迟和任务结果确认收益。
