让 Coding Agent 参与三维创作，怎样把“房间更有生活感”这样的要求变成可以持续修改的作品？Thomas Ricouard 在 OpenAI 的 [《Architectural visualization with Astra》](https://developers.openai.com/blog/architectural-visualization-with-astra) 中，用住宅项目 Solace 展示了一条从设计意图走向场景、渲染和交互的路径。

这个案例适合从 Agent 工程的角度阅读：任务的输出具有视觉和空间属性，执行者需要通过不同形式的反馈判断下一步。下面先概括案例，再讨论它对任务组织和验收的启发。本文没有复现该项目，后文的工程方法是基于案例的延伸分析。

## 原文展示了怎样的工作流

作者在 Codex 中让 Astra 通过 Blender 的 Python API（`bpy`）建立可编辑场景。住宅扩大前，双方先审阅平面图；建模过程中，Astra 检查预览并修正问题，也通过 computer use 查看 Blender。后续产物包括 Cycles 镜头导览与 Unreal Engine 5 漫游。

迁移到 Unreal 时，Astra 用 FBX 承载几何，用 JSON 描述场景关系，并处理单位、坐标和材质转换。漫游还需要角色、碰撞与行走测试；更新版加入了门、抽屉和灯光等交互。作者用匹配的机位比较两个引擎的结果，同时保留了材质近似、反射瑕疵和建筑专业审查的边界。[来源：原文](https://developers.openai.com/blog/architectural-visualization-with-astra)

这些事实串起了三个问题：修改落在哪里，反馈怎样帮助定位问题，以及换一种交付形式后还要验证什么。

## 可编辑产物让反馈有具体落点

可以把这类任务理解为对一个持续存在的项目做修改。用户提出“灯光更柔和”，执行者需要找到相关灯光、材质和相机设置，修改后再生成可比较的视图。项目保留得越完整，下一轮要求就越容易对应到具体对象。

设想一个餐厅场景，用户要求“餐桌附近更亮，但窗外保持黄昏”。这是本文构造的例子。若只看最终画面，整体提高曝光也许能让桌面变亮，却可能破坏窗外的氛围。可编辑场景允许把问题拆开：先检查桌面附近的光源，再检查材质反光，最后判断是否需要调整曝光。每一步都有明确的修改对象和观察结果。

这里的工程价值在于缩小下一次修改的范围。此前已经认可的房间布局可以继续作为约束，灯光变化则需要新的证据。对 Agent 的任务描述也可以相应具体化：保留什么、调整什么、用哪个视角检查变化。这样，用户无需枚举每个参数，也能把设计意图传递到执行层。

## 在合适的阶段问合适的问题

从工程上看，平面布局、几何细节和最终画面对应不同的决策。早期若主要关心房间之间的关系，就应提供能看清布局的材料；如果问题已经缩小到某个表面，则需要局部视图。增加检查次数本身没有保证，检查材料必须能回答当前的问题。

例如，“门口走起来拥挤”至少有几种解释：门的位置不合适，附近家具占据通道，或者交互环境中的碰撞范围过大。远景渲染可能无法区分它们。把同一处空间放到平面视图、几何视图和实际行走中分别检查，才能判断该改哪一层。

这也影响人和 Agent 的分工。用户可以在阶段转换时判断方案是否符合目的；Agent 则围绕已确定的方向修正可观察的问题。需要保留的是设计决定与检查结果之间的联系。如果一轮反馈改变了布局，之前基于旧布局完成的行走检查就需要重新判断是否仍然有效。

对长任务而言，一份有用的进度记录可以写明：当前采用哪个版本，哪些决定已经确认，还有哪个问题等待验证。这样的记录比笼统的“场景已优化”更容易支持后续工作，也能减少在不同版本之间反复猜测。

## 跨工具迁移要保留关系和行为

案例中的场景描述文件提供了一个值得展开的思路：跨工具交付需要明确对象之间的关系。把它推广到一个假设的抽屉模型，抽屉面板、把手和内部物品可能都显示正常，但交互时仍需要知道它们是否一起移动、沿哪个方向移动，以及移动到哪里停止。

这意味着检查迁移结果时，可以分别看外形、组织关系和运行行为。文件能被目标工具读取，解决的是入口问题；对象摆放是否正确、组合运动是否正确，需要各自的检查。自动化流程最好把这些阶段的结果分别保留下来，方便失败时定位。

同样，渲染影片和实时漫游应有不同的交付约定。下面是本文提出的验收划分，适用于这类视觉项目，并非原作者公布的测试清单。

| 交付对象 | 主要检查问题 | 可保留的证据 |
| --- | --- | --- |
| 可编辑场景 | 对象与布局能否继续修改 | 场景文件、对象关系、检查视图 |
| 渲染影片 | 指定镜头的构图与运动是否合适 | 预览、最终帧序列或视频 |
| 实时漫游 | 自由移动与操作是否符合预期 | 目标程序中的行走和交互记录 |

这张表的用处是明确检查责任。影片通过验收后，仍需在目标程序中验证漫游；某个抽屉可以打开，也只能支持这一处交互的结论。交付证据应跟随用户实际要使用的对象。

## 把视觉反馈接回修改过程

对于类似项目，一个可采用的起点是：先选一个范围有限的场景，约定要保留的源文件和用于审阅的视角，再逐步增加细节与交互。遇到问题时，要求反馈说明看到什么、涉及哪个对象、准备怎样修改，以及修改后如何确认。

还需要考虑这种方法的成本。每一轮都制作完整高质量成片，可能让局部试错过于昂贵；只检查小范围预览，又可能漏掉整体关系。因此，预览的范围和精度应随问题变化，阶段结束时再检查完整交付物。这是工作流设计上的取舍，不能从一次演示推算出通用的效率收益。

阅读这个案例时，更值得带走的是一组可检查的问题：Agent 是否能修改真实项目，是否拿到了足以定位问题的反馈，下一步是否针对该问题，以及最终证据是否覆盖用户的使用方式。把这些问题接起来，视觉创作才有条件从一次生成延续为可审阅、可修订的工程过程。
