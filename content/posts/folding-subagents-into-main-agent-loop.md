一个助手查完库存，再找定价专家，最后请另一个 Agent 写报价。每个角色都完成了自己的任务，客户却收到一份漏掉交货条件的方案。排查这类问题时，除了看提示词，还需要检查信息在何处被交接、压缩和重新解释。

Diane Sarkis 在 [《Building agents: When to fold subagents into your main agent loop》](https://claude.com/resources/articles/building-agents-when-to-fold-subagents-into-your-main-agent-loop) 中建议：部分领域子 Agent 可以改为主循环按需加载的 Skills 与工具，减少有损交接；独立上下文和并行执行有明确收益时，仍应保留子 Agent。迁移应逐个进行，用端到端评估比较结果。

下面用一个假设的报价助手推演这个建议。这是本文构造的设计案例，并非原文的客户部署或实验结果。

## 先查下一步需要哪些细节

假设客户要采购一批设备，提出三个条件：先交付部分数量、总价包含运费、替代型号必须提前确认。如果库存 Agent 只返回“现货不足，可以替换”，定价 Agent 即使算对了单价，也可能忽略首批数量和替代限制。最后负责写作的 Agent 看到的是一个貌似完整的报价，已经不知道还缺什么。

这个流程中的库存、价格、交付条件会反复影响彼此。让同一执行者保留原始需求和工具结果，可以少设计几份跨角色摘要，也方便在发现运费过高后重新选择方案。

判断是否合并时，可以检查一条生产轨迹：后续角色是否经常追问先前角色已经看到的信息？交接文档是否越来越像整段会话的复制？这两种现象都提示，当前任务可能难以仅靠紧凑结果独立完成。角色名称清楚，并不代表信息依赖已经划分清楚。

共享上下文也有成本。如果库存查询返回几千条商品记录，持续保留全文会挤占后续推理空间。这个假设系统可以先提供按型号筛选、分页和明细回查接口，让主循环保留候选商品及证据位置。这样，是否另开一个上下文，才有更公平的比较基础。

## 合并以后，流程知识放在哪里

在这个例子中，可以把报价流程整理为一个 Skill：说明何时使用、如何处理分批交货、哪些条件需要客户补充、如何组织报价草案。主循环先看到简短描述，需要做报价时再读取详细规则。新增售后能力时，也不必让每次报价都预先携带全部售后说明。

工具很多时，也可以通过 tool search 按“报价”意图发现相关能力，再加载库存、运费和保存接口的定义。这个设计需要检查描述能否被正确检索：若助手始终找不到运费工具，减少初始上下文也无法让报价完整。

库存和计价仍由工具读取实际系统。这里可以进一步区分“指导怎样做”与“系统允许怎样做”：Skill 提醒检查折扣资格，报价保存接口则实际校验资格、价格版本和必需字段。即使模型漏读了某条提醒，接口也能返回具体缺项，让它继续补齐。

## 给保留的子 Agent 一个可验收的任务

同一个报价助手也可能遇到适合独立执行的工作。例如，客户提供一份很长的设备兼容性报告，主循环只需要知道候选型号是否满足几项要求。可以让子 Agent 阅读报告，按要求返回判断、页码和待确认项，主循环再据此处理报价。

这里值得隔离的是一次材料阅读任务。它的输入可以写清，输出可以复核，大部分阅读过程也不必持续参与后面的计价。相反，如果每次挑选型号都要重新协商客户的预算、交期和替代意愿，这个任务就很难独立完成。

验收格式同样影响收益。只有“兼容”的结论会迫使主循环盲目信任；附上证据位置和未覆盖条件，才能支持后续追查。交接内容应由下一步决策需要什么来决定。

## 用约束是否保留来验收迁移

这个假设系统可以先挑一条常见报价路径，只移除其中的定价 Agent，其他部分保持稳定。测试既检查报价内容，也检查保存结果，避免回复写着“已包含运费”，实际保存的金额却没有运费。

| 测试情形 | 需要检查的结果 |
|---|---|
| 现货只能满足部分数量 | 草案明确首批数量和剩余部分的处理方式 |
| 替代型号价格更低 | 在客户确认前保留原型号要求 |
| 运费接口暂时不可用 | 标出缺项，避免生成貌似完整的含运费报价 |
| 计算后价格版本发生变化 | 保存接口要求重新计算，并返回可处理的原因 |

这些测试是本文针对案例提出的验收设计。比较时应逐条查看哪些任务由成功变为失败，再看整体耗时和调用成本。若只有平均分，少见但必须遵守的条件容易被常见简单任务掩盖。

合并完成的标志，是原有业务约束仍然得到执行，信息交接更容易检查，后续维护也有明确负责人。子 Agent 的数量只是结果；值得持续记录的是，每一次独立执行究竟减少了哪些负担，又增加了哪些交接要求。
