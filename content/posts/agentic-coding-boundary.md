代码能编译、测试也通过，距离任务完成还差什么？tisonkun 的 [Agentic Coding 的边界](https://mp.weixin.qq.com/s/x_FUUG4wBUqYs1H5DUtpgQ)从实践经验出发，讨论“看起来合理的实现”如何变成经得起使用的产品。差距不一定在生成能力，而可能在需求是否完整、抽象是否合适，以及结果能否得到充分检查。

作者也保留了需求尺度的区别：简单任务只需要一个足够用的结果，复杂产品则必须承担更高的验证与维护要求。因而不能用同一套质量标准推断所有 AI 编程任务的收益。

## 代码结构本身也在提供上下文

原文认为，模型容易模仿现有代码中的短期补丁、过度复用和复杂分支。这是作者对当时实践的归纳，不是关于所有训练数据或模型行为的定量结论。不过，它指向一个可观察的机制：Agent 会从当前仓库寻找可沿用的写法，已有结构会影响下一次修改。

因此，领域术语、模块边界和随代码更新的文档都有助于表达任务背景。若同一个词在不同模块含义不一，或某个公共函数依靠许多开关兼容不同需求，模型需要同时理解更多隐含条件，局部修改也更容易波及别处。

作者尤其反对把 DRY 当作无条件抽象的要求。两段代码相似，可能只是实现碰巧接近，业务含义并不相同；过早合并之后，新需求往往继续增加配置和分支。Agent 再模仿这个结构，就会沿错误抽象扩展。

可迁移的判断是先确认复用对象的语义，再决定是否抽取。原文给出重复到第三次再考虑抽象的个人准则，但次数本身不是正确性的保证；最终仍要看它是否减少概念负担，而非只减少重复行数。

## 测试应说明行为，而非追随实现

AI 降低了编写测试的成本，作者也表示自己因此补上了更多原本懒得写的测试。但数量与覆盖率并不自动代表验收充分。

原文偏重行为测试和回归测试：前者描述软件对外应呈现的结果，后者保留历史故障的触发条件。相较之下，某些测试只是逐项复刻当前实现，内部结构一变就必须一起改，难以作为独立约束。

这对 Agent 特别关键。若任务反馈只有“让测试变绿”，模型可能围绕现有断言调整代码，却没有解决原始需求；若连测试本身也被随意修改，反馈就失去参照。检查测试覆盖了什么、断言是否独立于实现，与检查测试是否通过同样必要。

这不意味着自动测试作用有限到可以忽略。它能让明确的错误迅速反馈给下一轮执行，但产品体验、架构取舍和部分业务边界，仍需要其他证据补齐。

## 高质量判断未必已经写在需求里

原文的登录鉴权例子很具体：只要求登录，模型可能选一种常见账密方案；补充“使用一次性密码”后，它又可能只写一个模拟实现。缺失的不只是技术名词，还包括真实交付需要的服务、状态与完成标准。

熟悉业务的人往往能提前补上这些条件。看似“不写代码就完成开发”的过程，可能仍包含大量需求澄清、边界判断和方案选择，只是劳动没有表现为手写函数。

作者还以同事能够迅速找到合适 Rust 库、论文或标准接口为例，说明经验组合的价值。这类知识未必都存在于当前上下文，也未必能通过一次搜索召回。将它写成说明、例子或技能可以提高可用性，但文件存在仍不能证明 Agent 在正确时机采用了它。

## 审查带宽怎样成为限制

当生成补丁的速度超过检查速度，人会积累越来越多尚未充分理解的修改。作者认为，高质量软件中的主要时间本就用于需求、设计和验证，因此代码生成加速可能把瓶颈进一步推向 review。

这种压力不能单靠增加另一个审查 Agent 消除。自动审查能提供线索，但发现的正确性、遗漏范围，以及审查是否覆盖原始需求，仍需验证。输出更长的检查意见，并不等于减少了人的判断工作。

沿着原文的分析，一个可行的工作分配是让 Agent 探索候选、生成局部实现、补足行为与回归测试，再由人维护关键设计和验收边界。这里没有要求所有代码都手写，也没有要求所有任务都采用同一审查强度；投入应随失败代价和需求复杂度调整。

文章提供的判断标准很务实：计算收益时，要看从需求到可信结果的总工作量。输入了多少提示、生成了多少代码，只描述过程的一部分；遗漏的约束能否被发现，错误是否能被回归覆盖，才决定后续维护是否轻松。
