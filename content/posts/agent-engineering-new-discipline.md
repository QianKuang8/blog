一个 Agent 可能始终在线，工具调用也没有报错，却持续回答错问题，或在不需要操作时反复调用工具。服务可用率无法完整描述这类失败；团队还要判断它有没有按用户意图完成工作。

LangChain 的 [《Agent Engineering: A New Discipline》](https://blog.langchain.com/agent-engineering-a-new-discipline/) 用 Agent Engineering 概括一组工程实践：构建、测试、上线、观察、修订，再重复这一循环。文章强调的是怎样管理非确定性行为，并不要求另设一种职位，也没有使既有的软件测试和运行保障失去作用。

## 从最终答案回到执行轨迹

多步 Agent 的下一步取决于刚收到的上下文和工具结果。一个错误可能早于最终答案出现：漏读了约束，选错了工具，或者把失败的调用当成成功。仅保存最后回复，通常无法分辨这些原因。

原文要求 tracing 覆盖完整对话、工具调用，以及每次决策时可见的上下文。这给调试提供了可检查的过程证据：模型当时读到了什么，实际发出了什么参数，工具又返回了什么。Trace 能还原这些外部行为；至于模型为什么作出某个内部判断，仍需从观察和对照中推断。

因此，“Agent 出错”可以进一步拆成不同的修改入口。如果相关信息从未进入上下文，要检查检索与工具；如果工具返回含糊，要检查接口和错误表达；如果任务本身有多种合理解释，要补充目标与验收标准。先分类失败，再决定改提示还是改实现，会比反复增加一条“请认真检查”更可检验。

## 产品、工程与数据共享同一组任务

文章把实践所需能力分为三类。产品工作定义用户究竟要完成什么，以及什么产物可接受；工程工作提供工具、可恢复执行、人类介入和记忆管理；数据工作通过评估、实验和错误分析衡量质量。

这些分工相互依赖。例如，工具按预期返回了数据，却没有覆盖用户需要的时间范围。它既可能是接口能力不足，也可能是任务范围未说明。只有把用户目标、调用轨迹和实际产物放在一起，才容易判断问题应由谁处理。

提示在这里也成为需要维护的行为规范。产品人员调整一句范围说明，可能改变调用路径；工程人员修改工具描述，也可能改变模型选择工具的方式。两类变化都应进入同一套任务评估，避免各自局部看起来合理，组合后却导致回退。

## 让一次线上失败变成可重复检查的材料

原文给出的循环可以具体理解为：先用已知场景测试基础行为，上线后观察真实输入，从失败中找出重复模式，再调整提示、工具定义或工作流，并把问题案例补进回归集。

回归材料的用途，是回答下一次修改有没有解决旧问题、是否损害其他任务。真实 trace 提供输入和过程，评估标准提供结果判断；只有两者连起来，记录才会成为改进依据。若只收集大量轨迹而没有分析与复测，数据量本身不会带来可靠性。

文章提到准确性、延迟和用户满意度等指标。这些指标未必同步改善：更长的检查过程可能提升正确率，也增加等待。团队需要根据任务价值确定接受条件，而非把某一个分数当成所有场景的统一目标。

## 怎样理解“上线以学习”

作者主张，真实用户会带来团队预先想不到的输入，因此上线是继续学习的起点。这是一种开发节奏，不是对所有任务都应立即开放自主执行的证明。原文同时把人类介入、执行恢复和按需选择确定性工作流纳入基础能力。

从这一框架可以推导出一条实践原则：先定义允许 Agent 决策的范围，再让生产观察帮助修订范围。需求明确且步骤固定的部分，可以保持确定性；需要根据环境探索的部分，再交给模型。两者的边界也应随着失败证据调整。

这篇文章没有提供一组对照实验，证明某个循环速度必然对应多少可靠性提升。它提供的是组织方法：让一次行为偏差留下可定位的轨迹，让修复进入可比较的评估，再观察上线后的实际效果。工程纪律体现在这些证据是否接得上。
