Agent 每运行一轮，通常只新增少量动作与工具结果，但下一次请求仍会带上系统规则、工具定义和此前历史。如果每次都重新处理这些内容，输入越长，重复计算的开销越明显。

Lance Martin 的 [《Prompt auto-caching with Claude》](https://x.com/RLanceMartin/status/2024573404888911886) 解释了如何复用这些稳定部分，以及自动缓存怎样减少开发者移动断点的工作。本文依据归档时的说明讨论机制，涉及 API 行为与价格的数字均属于该材料的历史口径。

## 无状态请求与计算复用可以同时成立

原文以 Claude Messages API 为例说明，API 不会替应用自动保留全部行动历史。Harness 仍需把过去消息、工具说明和新反馈组织成下一次请求。Prompt cache 并不代替这个状态管理职责。

它复用的是对相同输入前缀已经完成的计算。推理通常包含处理输入的 prefill 和逐步生成输出的 decode；如果新请求开头与之前一致，prefill 中对应部分就有机会复用。模型仍要处理新增材料，也仍需生成新的输出。

因此，缓存命中不能理解为“模型已经记住了，不用再传历史”，也不意味着返回同一个答案。它改变相同前缀的处理成本，后续输入和生成过程仍可以不同。这一区别有助于把应用记忆、请求构造和底层缓存分别设计。

## 断点标记的是一个前缀

原文介绍，块级 `cache_control` 指定缓存断点，缓存范围包括该块及之前的内容。材料还说明，匹配依赖一致的内容，并描述了从断点向前检查既有缓存写入点的行为。

假设第一轮请求由稳定规则和消息 A、B 组成，下一轮追加 C。只要前面的内容仍一致，系统就有机会复用旧前缀；如果在开头的规则中插入一个新时间戳，即使后面的 A、B 没变，它们所在的完整前缀也已经不同。

这个例子解释了为什么“内容大部分一样”不够。缓存关注的是从开头连续匹配到哪里，而非在整段输入中任意寻找相同句子。工程上要保持稳定的不仅是文字，还包括会影响请求前缀的组织方式。

## Auto-caching 自动处理什么

手动使用断点时，随着对话增长，开发者需要决定新的写入位置。原文介绍的 auto-caching 允许在请求级提供一个 `cache_control` 参数，让断点移动到请求中最后一个可缓存块；它也能与明确设置的块级断点配合。

自动化的是断点推进，不是任意历史改写后的语义对齐。如果每轮重排消息或修改早期内容，系统不会因为开启 auto-caching 就把两个不同前缀视为相同。应用仍要决定哪些信息长期稳定，哪些以新消息追加。

对于修正旧事实，也不能为了命中率继续让错误内容支配任务。可以明确追加纠正说明，或者在需要时重建上下文。选择哪一种方式，应同时检查模型是否正确理解新状态与实际缓存效果。

## 价格比例不能直接换成整次任务折扣

原文提到，当时缓存读取的输入 token 价格为普通输入的 10%。这个比例适用于命中的输入部分，不能直接得出一次 Agent 任务总费用下降 90%。首次缓存写入、未命中的新增输入和输出生成，都仍是需要统计的部分。

由机制可推导出，缓存收益与重复程度和调用形态有关：稳定前缀较长、重复调用较多时，可复用的计算更多；一次性短请求则未必有同样收益。本文没有重测当前计费规则，也不将历史比例作为新的报价。

判断缓存是否有效，应观察请求中实际读取和写入的缓存 token、总费用与延迟，而非只检查参数是否存在。若命中率突然下降，再沿请求差异定位：系统内容是否变化、工具是否重排、历史是否被改写，或调用是否使用了不同配置。

Auto-caching 减少了维护断点的工作，但稳定输入仍要由 Harness 组织。应用保存完整任务状态，请求选择下一步需要的材料，缓存复用相同前缀；这三层职责分清后，成本和行为变化才容易解释。
