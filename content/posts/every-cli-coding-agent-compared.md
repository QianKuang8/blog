面对几十种终端 Coding Agent，按功能数量挑选很容易遗漏实际工作中的限制。Michael Livs 的 [Every CLI coding agent, compared](https://michaellivs.com/blog/cli-coding-agents-compared) 收集了 36 个项目，并按模型、许可证、工具扩展、隔离与协作能力展开比较。它适合作为寻找候选产品的索引，也提供了分析 Agent 运行环境的线索。

本文依据 2026 年 4 月 9 日保存的原文归档整理，没有重新安装或逐项测试这些产品。原文中的 Star、免费额度、版本能力和推荐排序属于当时的盘点，不作为当前购买或部署依据。下面保留的是比较方法。

## 终端为什么适合承接执行循环

原文强调 CLI 的价值，是因为代码任务常需要连续访问文件、执行命令、运行测试和操作版本控制。这些动作已有命令行接口，Agent 可以将其接成“检查—修改—执行—读取结果”的循环。

不过，界面形态与运行能力不能直接画等号。一个 IDE 前端也可以连接相同的执行引擎；一个 CLI 程序也可能只提供有限操作。因而选型时应继续往下问：工具在哪台机器执行，使用哪个工作目录，进程能访问哪些文件，结果又怎样回到会话？

这些问题比“终端还是编辑器”更能解释系统是否适合既有开发流程。若日常需要查看大量 diff，界面审查能力可能很重要；若任务从 CI 触发，无交互执行与退出结果则更相关。

## 功能相同，承担的工作可能不同

原文表格列出 MCP、子 Agent、headless、计划模式和项目记忆等能力。逐项比较前，可以先把它们映射到任务中的环节：

| 比较维度 | 要进一步确认的问题 |
| --- | --- |
| 模型接入 | 是否支持所需模型、凭据方式和部署位置？ |
| 上下文获取 | 如何搜索代码，何时读取项目说明，长任务怎样保存状态？ |
| 工具扩展 | 外部工具如何注册、发现和返回结果？ |
| 执行控制 | 文件、命令与网络访问由什么机制约束？ |
| 自动化入口 | 是否能无交互启动，并返回可判断成败的产物与状态？ |

这些是依据原文维度整理的核验问题，不是本次已完成的产品测试。它们可以帮助解释为什么表格里同样写着“支持”的两个工具，实际集成成本仍可能不同。

## 隔离、审批和恢复需要分别检查

原文将容器、操作系统级限制、网络策略与检查点放在不同产品的对照中。阅读时需要区分其作用：执行隔离限制进程能够接触的资源；审批决定动作是否获准；检查点帮助保存或恢复代码状态。

三者可以配合，却不能互相替代。例如，能够恢复文件修改，并不能据此推导外部操作也能撤销；列出沙箱能力，也没有说明所有运行模式都会启用相同限制。这些是从机制出发应当继续验证的条件。

同样，项目说明文件也不等于自动学习记忆。`AGENTS.md`、`CLAUDE.md` 等入口的价值，在于提供持久的仓库约定。是否被读取、按什么范围生效、与其他指令如何组合，要看具体实现，不能仅凭文件名兼容就认定行为相同。

## Agent 与编排工具处在不同层

盘点还列出了用于组织多个 CLI Agent 的工具。这一类产品主要管理会话、终端或 worktree；真正读写代码、调用模型的，仍可能是底下运行的 Agent。

区分这两层有助于定位需求。若单个任务已经能完成，只是同时处理多个任务困难，问题可能在工作区隔离和状态管理；若任务本身反复误解需求，增加一个并发界面未必改善结果。

模型中立、可修改源码、企业权限或多会话组织，也分别对应不同约束。它们不能简单相加成为一个“最强产品”分数，必须与使用场景匹配。

## 让同一组任务补完功能表

沿着这份盘点继续选型，可以先用少量代表性任务缩小候选：一次跨文件修改、一次测试失败后的恢复，以及一次需要项目约定的任务。保持仓库状态、目标和验收标准一致，记录最终修改、人工介入、耗时与费用，再观察失败发生在哪个环节。

这是本文提出的验证方法，原文没有报告这样的统一横向实验。功能表回答“值得看哪些项目”，任务结果才回答“哪种配置适合当前工作”。将两者连起来，才能避免把项目热度、语言选择或功能数量误当作交付质量。
