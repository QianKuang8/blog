当 Coding Agent 把推理服务的吞吐改低了，一句“性能回退 20%”能告诉它结果，却很难告诉它下一步该查什么。问题可能出在算子、通信、内存管理，也可能是上层调度让设备一直等不到任务。

Z.ai 的 [《How GLM Built Its Own Inference Infrastructure》](https://z.ai/blog/glm-built-its-inference-infrastructure) 讨论了怎样填补这段诊断过程。作者报告，团队与 GLM-5.3 驱动的 Infra Agent 合作，在超过十万张国产 AI 加速卡的集群上建设 GLM-5.3-Flash 推理服务，从初始适配到生产就绪用时不到两周，端到端吞吐达到初始基线的约 3 倍。这些是原文报告的项目结果，本文未独立复现；更值得展开的是结果背后的反馈组织方式。

## 让一次实验回答一个具体问题

推理工程已有测试、日志、profiler 和 microbenchmark。困难在于，这些工具往往分散在不同环节，需要工程师根据当前现象决定下一步看什么。只把代码库和最终性能指标交给 Agent，会留下同样的诊断缺口。

原文把解决办法称为 dense feedback，本文译为“密集反馈”。它有三个条件：能定位到具体代码路径或输入条件，获取成本足够低且及时，以及能通过参考实现或对照实验客观验证。“密集”描述的是反馈对决策的支撑程度。给出某个请求在两条计算路径上的输出差异，就比追加一批没有上下文的错误日志更有用。

![Infra Agent 的反馈循环：工程师定义目标与边界，Agent 提出假设和修改，实验环境提供数值、时序与性能证据；候选修改经过端到端验收，结果继续反馈给 Agent。](/blog/images/glm-built-its-inference-infrastructure/dense-feedback-loop.svg)

*根据原文整理的职责与反馈关系。三类局部验证按当前假设选择，没有固定执行顺序；通过局部验证的修改仍需端到端验收。*

这也改变了测试的用途。测试既是验收手段，也是选择下一步动作的依据：数值对照缩小错误范围，时间线揭示等待关系，性能实验判断一个改法在哪些条件下成立。Agent 每轮拿到的应当是足以保留、修订或推翻当前假设的证据。

## 数值错误：把部署配置映射到计算路径

第一个案例发生在 KDA kernel 的 Context Parallelism（CP，上下文并行）路径。并行策略会改变输入如何切分、状态如何传递、结果如何合并，因此，单独测过未切分版本，不能覆盖实际部署中的全部计算。

团队先建立“推理引擎并行配置 → kernel 实现”的映射，再让 Agent 对同一输入比较切分与未切分路径。比较前需要对齐计算语义和输出位置，结果则按数值误差容限判断。这样，一次失败便能指向特定切分方案和合并逻辑。

原文中的偏差出现在跨上下文分片的状态合并与更新。相关 `tl.dot` 调用即使接收 FP32 输入，原实现仍默认用 TF32 计算，误差沿状态传播累积，长上下文下更明显。修复是在这两处运算中显式指定 `input_precision="tf32x3"`，用更高精度的计算方式控制累积误差，同时尽量保留 Tensor Core 的性能优势。

这里可迁移的方法是先把“部署中究竟执行什么”变成可测对象。局部对照把模型级异常收敛到了具体计算路径，但修复后仍要回到目标部署，检查模型精度和服务性能。数值正确与性能可接受，需要分别给出证据。

## 并发问题：异步传输也可能迟迟没有被提交

第二个案例展示了怎样从性能差距追到调度机制。工程师分别定义 Prefill 单独运行、Prefill 加 KV Transfer、Decode 单独运行等场景，并要求同一负载下，前两种场景的性能差距不超过 5%。Agent 却在部分场景中观察到超过 20% 的差距。

这一对照把调查范围缩到了新增传输带来的开销和并发关系。随后，执行时间线暴露出异常：Python 侧 KV Transfer 的执行，总是避开 DeepEP 的 dispatch/combine 调用区间。沿调用链继续查看，才定位到 Python/C++ 边界。

原文使用的 DeepEP v1.2.1 中，`intranode_dispatch` 和 `intranode_combine` 没有显式释放 Python GIL；其中 dispatch 在需要接收 token 数量时，还会由 CPU 等待 GPU 返回信息。进入 C++ 本身不会自动释放 GIL。同一进程中负责 Mooncake Transfer 的 Python 线程拿不到锁，传输任务的调度和提交就被推迟了。底层具有异步能力，也无法补偿上层迟迟不提交任务造成的空隙。

修复是在相关 C++ 执行区间释放 GIL。团队再检查两件事：时间线是否出现预期的重叠机会，以及原先的性能差距是否收敛。作者报告，同等测试条件下，Prefill 加 KV Transfer 与 Prefill 单独运行的差距降到了 1% 以下。

这条证据链值得保留完整：场景对照定义异常，时间线提出并发假设，代码检查找到持锁范围，修改后的实验再验证效果。仅凭“两个事件没有重叠”就宣布根因，会跳过最后的因果检验。

## 优化经验要连同适用条件一起复用

第三个案例涉及 KDA Decode kernel 的优化。团队让 Agent 从 SGLang、Flash Linear Attention、DeepGEMM 等项目的既有实现中学习，并通过增量和消融实验，整理出包含适用条件、变换方法、资源约束及验证证据的“优化骨架”。新任务可以从这些候选方法出发，再按目标硬件和负载重新测量。

原文给出的版本演进尤其能说明局部指标的边界：

| 变化 | 原文报告的局部结果 | 阅读时应保留的条件 |
| --- | --- | --- |
| v0 → v1：引入 ReplaySSM，以计算换内存 | kernel 执行时间上升 | 局部变慢可能服务于更大的内存目标 |
| v1 → v2：优化除法 | 执行时间减少 9.6% | 比较基线是 v1 |
| 在 v2 基础上合并重复计算 | 速度达到 v2 的 1.71 倍 | 指该代表性 kernel，相对 v2 的结果 |

最后一步的线索来自“计算是主要瓶颈”的反馈。Agent 发现，原实现沿 V 维度分块，导致相同的 FP32 归一化和门控计算重复四次。它把这些分块合并到一个线程块中，将共享中间结果留在寄存器里，并用一次 warp 级归约替代各块的重复计算。牺牲部分并行度，换来了减少冗余计算的收益。

但这些局部收益不能直接等同于整套服务的提升。一个计算 kernel 占用更多资源，也可能挤压 KV Transfer 的资源，拖慢整体流水线。因此，优化骨架需要保存“在什么条件下成立”，候选修改仍须放回真实执行环境测量。单个 kernel 的 1.71 倍，与整套服务约 3 倍吞吐，是不同范围、不同基线的结果。

## 自我改进的边界仍由工程流程决定

原文用 Recursive Self-Improvement（RSI，递归自我改进）描述更远的方向，同时明确表示尚未达到这一阶段。当前展示的是模型参与优化推理基础设施，以及经验被整理后支持下一轮工程工作。目标选择、系统边界和风险评估仍由人负责。

从这几个案例可以归纳出一个 Harness 设计重点：把诊断能力做成 Agent 可以重复调用的实验流程。工程师要说明什么结果值得优化，提供能区分候选原因的观察与对照，并审查数值语义、异步并发和生产风险等关键改动。模型负责提出假设、实现修改、运行实验，再依据结果调整方向。

“不到两周、约 3 倍吞吐”描述了这次协作的总体结果；原文没有给出将模型能力、反馈环境和工程师投入各自贡献分离出来的对照实验，因此不能把全部增益归给其中一项。对于借鉴者，更容易落地的起点，是从一个反复出现的故障或瓶颈出发，把输入、观察、对照和验收连起来，让下一次实验能够回答当前问题。
