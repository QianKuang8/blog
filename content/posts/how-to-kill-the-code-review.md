当 Agent 生成修改的速度高于团队阅读 diff 的速度，审查队列就会增长。增加一个自动评论工具可以帮助发现问题，但仍需回答：团队究竟依据什么证据批准这次变化？

Ankit Jain 在 Latent Space 的客座文章 [《How to Kill the Code Review》](https://www.latent.space/p/reviews-dead) 中提出，把人类检查前移到 spec、约束和验收标准，并让机器执行更大部分验证。这个激进主张代表作者的立场；编辑按语明确表示尚未完全认同。文章可以作为工作流设计提案阅读，不能当作人工代码审查已经失去作用的事实结论。

## 提前审查意图，要产出什么

作者希望人先确认要解决的问题、不能破坏的边界，以及可检验的预期行为。代码随后成为实现这些约定的产物。这样，审查者有机会在大批实现生成之前发现方向错误。

但“有一份 spec”并不等于需求已经清楚。文档需要让验证者判断输入条件、预期输出和边界情况。原文借用 BDD 的思路，将自然语言行为约定转换为可自动执行的检查；其收益取决于约定是否覆盖了业务含义，而非文档长度。

一个直接的要求是验收标准先于实现确定。如果 Agent 写完代码后，再按现有实现生成一组测试，测试可能只是确认自己已经做出的选择。执行可以是确定性的，测试是否问对问题却仍需要判断。

## 把“看起来能用”换成可检查的产物

原文主张让 Agent 编写并运行验证脚本，留下通过或失败的结果，而不只让它口头确认完成。验证可分为编码规则、组织不变量、领域契约和任务验收。例如，禁止硬编码凭据是组织级约束，金额统一使用 Money 类型是领域约束，某个行为是否满足当前请求则属于任务层。

这些检查有不同覆盖范围。类型检查能发现类型不一致，却不能独立判断业务逻辑；测试通过说明给定断言成立，却不意味着未覆盖路径也正确。把检查分层的价值，是明确每项证据回答了什么问题。

作者还提出多方案竞争，按验证结果、diff 大小或新增依赖等信号挑选候选方案。此处的排序标准也需要符合任务：更小的 diff 可以降低检查成本，但并非所有问题都应该用最少行数解决。候选数量增加，仍不能替代验收标准。

## 权限与独立验证限制不同的失败

权限系统控制 Agent 可以触及什么。原文建议按任务缩小文件范围，并对认证逻辑、数据库结构或新增依赖等变化设置升级检查。这能限制一次错误操作的影响，但不会自动证明允许范围内的修改正确。

独立验证负责另一件事：让实现者之外的执行者检查结果。原文提出编码 Agent 不预先知道验证 Agent 的具体检查，而验证 Agent 不能修改实现来让检查更容易通过；还可以由第三个 Agent 寻找边界条件和破坏路径。

这些是职责与访问边界的设计。两个 Agent 使用相似模型或共享同一份含糊规范时，仍可能犯相同错误。因此，分开上下文只能提供独立检查的条件，不能直接推导统计意义上的错误独立。

## 多层检查需要防止共同盲点

作者用“瑞士奶酪”比喻多个不完美的防线：单层有孔洞，组合后可能截住更多失败。这个比喻成立的前提，是各层能够补充彼此，而非重复同一个判断。

假如需求遗漏了时区边界，实现与所有测试都按同一遗漏展开，再多一次“按 spec 审查”也可能看不到问题。这是依据原文框架可以推导出的限制：团队还需要检查规范本身是否完整，必要时保留对高风险实现和设计的直接阅读。

原文没有给出足以证明所有团队可以取消人工审查的对照实验。更可操作的采用方式，是先选择验收清晰、反馈可靠的一类任务，逐步记录自动检查覆盖了什么、人工又发现了什么，再决定哪些检查可以前移或自动化。人类注意力的重新分配，需要由实际漏检和交付结果支持。
