当 Agent 生成修改的速度高于团队阅读 diff 的速度，审查队列就会增长。增加一个自动评论工具可以帮助发现问题，但仍需回答：团队究竟依据什么证据批准这次变化？

Ankit Jain 在 Latent Space 的客座文章 [《How to Kill the Code Review》](https://www.latent.space/p/reviews-dead) 中提出，把人类检查前移到 spec、约束和验收标准，并让机器执行更大部分验证。这是作者的主张；编辑按语说自己“还没走到那一步”，但认为这一天显然不远了。本文也把它当作一份工作流设计提案来读。

## 提前审查意图，要产出什么

作者希望人先确认要解决的问题、不能破坏的约束，以及可检验的预期行为。代码随后成为实现这些约定的产物。这样，审查者有机会在大批实现生成之前发现方向错误。

有了 spec，需求也可能仍然含糊。文档要让验证者能判断输入条件、预期输出和边界情况。原文借用 BDD 的思路，将自然语言行为约定转换为可自动执行的检查；其收益取决于约定是否覆盖了业务含义，而非文档长度。

一个直接的要求是验收标准先于实现确定。如果 Agent 写完代码后，再按现有实现生成一组测试，测试可能只是确认自己已经做出的选择。执行可以是确定性的，测试是否问对问题却仍需要判断。

## 把“看起来能用”换成可检查的产物

原文主张让 Agent 编写并运行验证脚本，留下通过或失败的结果，而不只让它口头确认完成。验证可分为编码规则、组织不变量、领域契约和任务验收。例如，禁止硬编码凭据是组织级约束，金额统一使用 Money 类型是领域约束，某个行为是否满足当前请求则属于任务层。

这些检查的覆盖范围各不相同：类型检查发现类型不一致，业务逻辑要靠别的检查；测试通过说明给定的断言成立，没覆盖的路径仍是未知。分层的价值在于说清每项证据回答了什么问题。

作者还提出多方案竞争，按验证结果、diff 大小或新增依赖等信号挑选候选方案。排序标准也要贴合任务：更小的 diff 降低检查成本，但有些问题本来就需要较大的改动。候选再多，也要先有验收标准才能挑。

## 权限与独立验证限制不同的失败

权限系统控制 Agent 可以触及什么。原文建议按任务缩小文件范围，并对认证逻辑、数据库结构或新增依赖等变化设置升级检查。这能限制一次错误操作的影响；允许范围内的修改是否正确，还要靠前面的确定性检查和下面的独立验证。

独立验证负责另一件事：让实现者之外的执行者检查结果。原文提出编码 Agent 不预先知道验证 Agent 的具体检查，而验证 Agent 不能修改实现来让检查更容易通过；还可以由第三个 Agent 寻找边界条件和破坏路径。

这是在职责和访问权限上做隔离。两个 Agent 用相似的模型、读同一份含糊的规范时，仍可能犯相同的错误：分开上下文为独立检查创造了条件，错误本身却可能是相关的。

## 多层检查需要防止共同盲点

作者用“瑞士奶酪”比喻多个不完美的防线：单层有孔洞，组合后可能截住更多失败。这个比喻成立的前提，是各层能够补充彼此，而非重复同一个判断。

![瑞士奶酪模型：spec 与 Agent 依次穿过多方案比较、确定性护栏、验收标准、权限系统和对抗式验证五层，每层都有孔洞，叠在一起才建立信任。](/images/how-to-kill-the-code-review/swiss-cheese-layers.png)

*图 2：原图，来源同上。箭头只有在五层的孔洞恰好对齐时才能一路穿过；本节讨论的共同盲点，正是让多层孔洞对齐的那类错误。*

假如需求遗漏了跨时区的情况，实现与所有测试都会沿着同一个遗漏展开，再多一次“按 spec 审查”也很可能发现不了。我的推论是：团队还要检查规范本身是否完整，高风险的实现和设计仍值得直接阅读。

原文没有给出对照实验。比较稳妥的采用方式，是先选择验收清晰、反馈可靠的一类任务，逐步记录自动检查覆盖了什么、人工又发现了什么，再决定哪些检查可以前移或自动化。人类注意力的重新分配，需要由实际漏检和交付结果支持。
