采购合同上的 GPU 数量，怎样变成研究和产品真正能用的算力？[Stanford MS&E 435 Week 5](https://www.youtube.com/watch?v=4k53z3Ysjg0) 把这段过程称为算力交付问题：芯片、电力、建设、运行与任务调度共同决定何时能够提供有效服务。

嘉宾是 Sachin Katti（OpenAI，负责 industrial compute，前 Intel CTO），由 Apoorv Agrawal 主持。视频由 Stanford Online 发布于 2026 年 5 月 27 日，时长 46 分 06 秒。本文依据 957 条人工英文字幕及 2026 年 9 月 23 日修订的 22 页课程笔记整理。

## 四个核心判断

1. 算力约束的不是采购合同而是交付时间：从投资决策到算力真正上线（time to compute）是关键路径。
2. 按 Katti 的口径，推理包括 RL 后训练采样、合成数据和产品调用；他称当时已占多数，并预测未来可能超过 80%。
3. 智能体工作负载把推理从单次模型调用扩展为包含工具、搜索、数据库和外部执行的计算图，改变了硬件需求。
4. 局部加速可能使其他环节成为主要约束，需要重新测量端到端路径。

## 算力为何先于收入

Katti 描述了一个看似矛盾的现象：前沿实验室的收入在快速增长，但算力投入增长得更快。[00:00:49–00:08:43](https://www.youtube.com/watch?v=4k53z3Ysjg0&t=49s) 原因是前沿模型训练本身就是一种"投资"——它不直接产生当期收入，而是创造下一代能力。推理收入需要等模型部署后才开始回收。

更重要的是，推理的定义已经扩大。传统理解中推理是"用户发一个请求，模型返回一个答案"；但现在推理还包括 RL 后训练中的大量采样、合成数据生成和 reasoning（思维链推理）。RL 后训练采样、合成数据生成和产品服务是并列的大量推理用途，不能画成必经的串行阶段。Katti 预测推理最终会占 80% 以上的计算，但这个数字是预测而非审计事实。[00:06:01–00:07:00](https://www.youtube.com/watch?v=4k53z3Ysjg0&t=361s)

token 有三个独立的优化杠杆：每个 token 的成本（硬件效率）、每个 token 的质量（模型能力）和每个任务需要多少 token（模型效率和编排设计）。三者提供不同的观察维度，但实际优化可能相互影响，需要联合测量。

## 一吉瓦算力的交付挑战

Katti 把 1 GW 用约 50 万 GPU 的口头估算建立规模直觉。[00:08:43–00:15:38](https://www.youtube.com/watch?v=4k53z3Ysjg0&t=523s) 但他立即指出，寻找“唯一瓶颈”会忽略交付中的相互依赖：芯片、电力、冷却、互联、建筑和劳动力会交替成为约束。GW 在这里采用设施级功率口径，不能用这句话反推某一型号 GPU 的单卡功耗或采购数量。

上线后的名义容量还要经过可用性和调度检验。新版笔记用“安装容量 × 可用率 × 可用期间的利用率”作教学近似：可用率描述观察期内能运行多久，条件利用率描述能运行时有多少容量被使用。如果日常统计的利用率已经把停机时间算入分母，就不能再乘一次可用率。这一拆分也尚未计入降频、通信和任务质量造成的损失。[00:10:56–00:11:44](https://www.youtube.com/watch?v=4k53z3Ysjg0&t=656s)

同步训练也是电网问题：大量 GPU 在训练阶段之间同步切换，会带来显著的功率波动。电力系统既要满足平均功率，也要应对动态负载；讲者讨论的是条件性风险，没有给出已发生大范围停电的案例。[00:12:20–00:13:20](https://www.youtube.com/watch?v=4k53z3Ysjg0&t=740s) 这与部分可分散调度的推理请求不同，但不能据此认为所有推理负载都具备相同弹性。

他还区分了三种量级的算力扩张状态：30 GW 是讲者描述的愿景目标，约 100 GW 是他对美国 hyperscaler 规划的即席估算，7 TW 是“每人一块 GPU 等效智能”的思想实验。三者的状态和范围不同，可能存在重叠，不能相加成为已规划或已建成容量。

## 智能体计算图改变硬件需求

当产品从"单次问答"变成"代理完成一个任务"，推理就从单次模型调用变成一张包含多次模型调用、工具执行、搜索和数据库查询的计算图。[00:17:36–00:27:29](https://www.youtube.com/watch?v=4k53z3Ysjg0&t=1056s)

Katti 引入"人的 flow"作为基础设施指标：如果用户正在连续工作，代理的响应延迟会打断这种状态。因此 TTFT（首 token 延迟）和端到端延迟不只是技术指标，而是产品体验指标。

异构计算由此成为一种设计方向——不同计算图节点有不同的计算特征（prefill 是计算密集、decode 是内存带宽密集、工具调用可能是 I/O 密集），用单一硬件服务所有节点不一定最优。

## 先分清首 token 等待，再看瓶颈迁移

Katti 用约 400–500 ms 说明智能体负载处理输入上下文的量级，并在追问中澄清，部分应用与网络延迟还要另加。因此，这个数字不能写成完整端到端 TTFT 的测量值。[00:29:02–00:31:43](https://www.youtube.com/watch?v=4k53z3Ysjg0&t=1742s)

TTFT 是请求发出到首个输出 token 出现的全部等待；prefill 是处理输入的阶段；decode 的 tokens/s 则描述之后持续生成的速度。应用处理、分词、网络、路由，以及可能的排队和调度，都会影响首 token 等待。后续输出很快，仍可能让用户在开头等很久，这些指标需要分别测量。

这一区分也解释了讲者为何当时仍倾向集中部署：按他的量级判断，处理上下文的数百毫秒开销，比靠近用户所节省的传输时间更大；建设规模和劳动力又有利于大站点。这个判断依赖当时的负载和成本，模型变小、输入处理更快后，权衡可能改变。

课堂中的具体加速例子是 Cerebras 让输出 token 生成更快，随后应用和 API 中原本不起眼的延迟显现，团队需要继续优化其余层。[00:31:43–00:33:13](https://www.youtube.com/watch?v=4k53z3Ysjg0&t=1903s) 这直接支持 decode 加快后瓶颈迁移的观察；讲座没有提供 Cerebras 的 prefill 倍数或 TTFT 降幅，也没有规定每个系统都会沿同一顺序遇到瓶颈。

他还讨论了模型-芯片-软件协同设计：让一代模型参与设计下一代基础设施。[00:33:13–00:36:22](https://www.youtube.com/watch?v=4k53z3Ysjg0&t=1993s) 这是一种递归优化——AI 辅助芯片设计和编译器优化可能加速整个迭代周期。

## 沿任务路径寻找当前约束

Time to compute 关注从决策到算力可用的时间，任务级指标关注这些算力能否交付达到要求的结果。前者揭示供应链和建设中的等待，后者揭示模型调用、工具执行与系统调度中的等待，二者需要连接起来观察。

据此可以把基础设施改进分成两步：先找到当前限制交付的环节，再检查优化后整条任务路径是否改善。某个 kernel 或阶段变快，收益可能被后续等待抵消。课程强调的全栈视角，要求每次局部优化都回到运行负载验收。
