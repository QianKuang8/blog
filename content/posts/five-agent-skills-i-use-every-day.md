开发者反复提醒 Agent“先确认需求”“拆小任务”“按行为测试”，说明这些要求已经成为稳定的工作习惯，却仍在每个会话里重新表达。把它们整理成 Skill，可以减少重复说明，也让流程更容易一起修改。

Matt Pocock 的 [5 Agent Skills I Use Every Day](https://www.aihero.dev/5-agent-skills-i-use-every-day) 介绍了自己常用的五个流程。作者认为它们改善了代码质量，但文章没有给出量化对照。以下聚焦每个流程解决什么问题，并不声称已经安装或实测这些 Skills。

## 先消除会改变设计的歧义

`/grill-me` 的输入是尚未定型的想法，目标是达到足够清楚的共同理解。原文用搜索页面举例：选择简单输入框还是高级搜索，会决定是否还需要讨论过滤与排序。问题沿设计依赖展开，回答一项以后，才知道哪些后续问题有意义。

这个 Skill 还有一条容易被忽略的要求：能通过查看代码库回答的问题，先去查代码。它避免把现有接口、目录或实现状态都交回用户口头说明，使追问集中在真实偏好和决策上。

原文展示过几十个问题的长讨论，这是作者处理复杂功能的经验，不是衡量澄清是否充分的目标。一个问题值得问，是因为答案会影响范围、方案或验收；如果答案可以合理推定或直接核查，继续追问反而会增加协作成本。

## PRD 保存目标，Issue 安排到达路径

需求澄清后，`/to-prd` 将讨论转换为产品需求文档。原文流程包括检查仓库中的事实、补充访谈、勾勒主要模块，再按模板形成 GitHub issue；已经完成的澄清可以跳过。用户故事承担描述预期行为的职责，让执行阶段仍能回到使用目标。

随后，`/to-issues` 把 PRD 转换为可领取的工作项，并记录阻塞关系。它特别强调 vertical slice，也就是贯穿必要集成层的薄切片。切片尽量早地跑通一条行为，使未知接口或依赖问题提前暴露，而不是先分别做完所有底层模块，再在最后拼装。

例如，针对一项带持久化的界面功能，可以先完成最小输入、保存和回读路径，再扩展其他操作。这是对纵向切片的说明性例子，并非原文展示的具体任务。它的验收对象是一个端到端行为，范围仍然可以很小。

阻塞关系也决定能否并行。两个 Issue 名称不同，不代表可以同时独立实现；如果它们共同修改尚未确定的接口，就需要先协调契约。将依赖显式写出来，能减少执行者各自作出不兼容决定的机会。

## TDD 为每一步实现提供反馈

作者的 `/tdd` 从确认接口变化与需要测试的行为开始，再进入一次一个测试的 red–green–refactor 循环：先观察测试失败，做足够的实现使它通过，随后检查重构机会。

一次只推进一个行为，有助于让失败与当前修改保持接近。若先生成一大批测试，再实现一大片代码，最后出现的失败就可能跨越多个假设，定位成本随之上升。

原文也强调接口的可测试性。这把测试从实现后的检查，前移到设计时的问题：外部调用者应观察哪些行为，哪些细节可以留在模块内部。Skill 提供执行方向，但并不是强制执行器；是否先观察了合理失败、是否用有效断言验证需求，仍要从运行与代码审查中确认。

## 架构改进针对理解与集成成本

第五个 Skill `/improve-codebase-architecture` 查找结构上的摩擦：理解一个概念是否需要来回阅读许多小文件，为方便单测抽出的纯函数是否掩盖了调用方式里的错误，紧耦合模块是否让集成难以判断。

作者借 deep module 表达改进方向：用较小、稳定的接口封装更充分的实现职责，减少调用方必须理解的细节。这里的“深”不是文件越大越好，而是接口带来的能力是否足以抵偿理解它的成本。

架构 Skill 因此先提出候选，再讨论哪些边界值得调整。它与 TDD 的关系也更具体：更清楚的行为边界帮助写测试，测试反馈又能暴露抽象是否合理。单纯为了让 Agent 少读几个文件而合并代码，未必改善维护性。

## 每个 Skill 都要留下下一阶段可用的产物

把五个流程连起来，交接物依次是已澄清的决策、产品规格、带依赖的任务、经过验证的实现，以及待评估的架构改进。它们不必每次全部调用，也没有必要让小修复经过完整仪式。

更适合复用的是这些交接条件：实现前是否知道要完成什么，拆分后是否仍能验证使用行为，测试是否覆盖真实要求，改进建议是否针对已观察到的结构问题。Skill 把习惯写下来以后，还需要用实际任务检查它是否减少误解和返工。若某个步骤持续没有提供新信息，就应调整它，而不是因为已经成为 Skill 就永久保留。
