Agent 连续搜索、读文件和运行工具以后，上下文会积累许多只在某一步有用的内容。继续全部保留，会增加成本，并可能让旧结论、无关结果和相互冲突的材料影响后续动作；简单清空，又会丢掉目标、约束和已经确认的发现。

Lance Martin 的 [《Context Engineering for Agents》](https://rlancemartin.github.io/2025/06/23/context_engineering/) 用四类动作整理这个问题：Write、Select、Compress、Isolate。它们分别回答信息存在哪里、何时取回、如何缩减，以及由哪个上下文负责处理。把上下文窗口类比为工作内存有助于理解容量约束，但其中的信息会影响模型判断，管理它还需要检查内容质量。

## 先决定什么值得保存，再决定何时读回来

Write 是把有用信息放到当前窗口之外。原文区分了任务内的 scratchpad 与跨会话记忆：前者可保存计划和阶段发现，后者可保存未来任务仍可能需要的事实、偏好或经验。它们既可以是文件，也可以是运行时状态字段。

保存不会自动让信息在下一步生效。Select 负责把相关内容重新放回模型输入。少量稳定的项目规则可以固定加载；更大的记忆集合则需要检索。文章区分了用于示范行为的经历记忆、指导操作的流程记忆和提供事实的语义记忆，这些材料进入上下文后承担的作用不同。

这一拆分暴露出两个独立问题：写入内容是否正确，以及检索出来是否与当前任务有关。错误记录被反复读取，会让原来的误判延续；真实但无关的偏好也会干扰结果。原文引用了位置信息被意外带入图片请求的例子，说明“记得住”与“该不该使用”需要分别评估。

## 检索代码与选择工具都在控制输入范围

代码库索引只是候选材料的组织方式，不能直接等同于检索质量。文章引述 Windsurf 对 AST 分块、embedding、文件搜索、图关系和重排序的组合使用：先找到可能相关的片段，再决定哪些值得进入当前上下文。

工具说明也占据窗口。大量职责重叠的工具会让模型难以选择，因此可以根据任务检索工具描述，按需暴露相关能力。这样减少了干扰，但也带来漏选风险：如果必要工具没有被取回，模型可能使用不合适的替代路径。工具选择同样需要用任务结果验收。

原文讨论的 context poisoning、distraction、confusion 和 clash，分别指向错误信息进入轨迹、上下文过载影响行为、多余材料影响回答，以及内容相互冲突。这些是分析失败的不同角度，不宜全部归为“长度太长”。增加窗口容量并不会自动修复错误事实或矛盾约束。

## 压缩历史，需要保留下一步所依赖的内容

Compress 包含摘要和裁剪。摘要用模型提取历史中的重要信息；裁剪可以直接移除较旧或不相关的消息。两者减少 token 的方式不同，也具有不同的信息损失。

文章列举了整段对话压缩、搜索工具结果后处理，以及 Agent 之间交接时的摘要。共同要求是让下一步仍拿得到所需事实。对于一个排障任务，可以据此推导出有用的检查项：当前假设是什么，哪些实验已经否定它，哪些约束不能改变，原始证据在哪里。只留下“已经尝试很多方案”，无法帮助接手者继续判断。

原文没有提供一套适用于所有任务的压缩配方。摘要是否合格，应看压缩后的执行能否保持方向、避免重复失败，而不能只比较压缩率。保留可回查的原始材料，也有助于补充摘要遗漏的细节。

## 隔离决定谁需要接收细节

Isolate 可以通过子 Agent 实现：每个执行者在自己的窗口探索一项较窄的任务，再返回结果。主 Agent 不必接收全部搜索噪声，但需要承担任务说明和结果交接的成本。原文引用多 Agent 研究系统的高 token 开销，提醒这种隔离并非免费收益。

另一种隔离发生在运行环境里。CodeAgent 可以把图片、音频或工具返回对象保存在变量中，按需操作，只把选定结果反馈给模型；结构化状态对象也可以把 `messages` 与其他字段分开。数据属于任务状态，并不意味着每轮都要把数据内容放进提示。

这四类动作能够组合使用：把大对象留在环境中，把进度写成笔记，下一轮只选择有关内容，必要时压缩长历史。设计是否有效，要沿信息流检查：有用事实是否还在，需要时能否取到，传递给下一位执行者以后是否足以作决定。
