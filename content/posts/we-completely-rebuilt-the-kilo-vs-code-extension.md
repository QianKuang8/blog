同一款 Coding Agent 有 CLI、VS Code 和 JetBrains 多个入口时，底层能力应当怎样复用？Kilo 的 [扩展重构说明](https://blog.kilo.ai/p/we-completely-rebuilt-the-kilo-vs-code-extension) 从一个具体问题出发：旧架构让这些入口都依赖 VS Code 内部实现，连 JetBrains 环境也需要携带这套依赖。

新版 VS Code 扩展转而使用与 Kilo CLI 相同的 OpenCode server 核心。这份文章介绍的是预发布版本，功能与迁移状态均按原文时点理解；本文未安装该版本，也未测量性能。

## 共享核心改变能力从哪里接入

旧架构以编辑器实现为中心，其他入口需要适应其依赖。重构后，执行核心独立于某个编辑器，CLI 和扩展连接同一套能力，Agent Manager 也使用这一核心。

这对维护的含义是，并发执行、会话和工具能力可以在共同基础上实现，界面则负责展示与交互。原文也介绍了终端与编辑器之间的会话延续。但共享引擎只能说明架构有了统一入口，不能单凭这一点推导所有端的功能已经同步完成。

原文恰好给出了反例：预发布扩展当时还没有原生 provider 配置界面，需要先在 CLI 配置，再让扩展使用这些设置。架构统一和迁移完整，是两个不同的交付状态。

## 三种并行分别解决什么问题

文章同时介绍并行工具调用、并行子 Agent 和多个独立会话。这三种机制相互关联，但不能混为一次自动分工。

并行工具调用用于同时执行多个独立动作，例如读取文件或搜索，从而缩短串行等待。子 Agent 委派则把较大的任务拆成局部工作，由执行者保留自己的过程，再将结果汇总给主 Agent；原文举了实现、测试与文档分工，也允许自定义子 Agent。

Agent Manager 的多个标签页则代表独立会话。用户可以给不同会话分配不同任务，或用同一个提示比较不同模型的结果。这些会话的组织与子 Agent 的内部调度处在不同层，不意味着所有标签页都会由某个主 Agent 自动合并。

并行的收益还取决于依赖关系。彼此等待同一项输出的任务，无法仅靠同时启动而消除等待；多个执行者修改重叠内容，还会引入协调工作。因此，原文的速度描述应视为产品方说明，文章没有提供统一负载下的对照数据。

## Worktree 隔离修改，合并仍需处理

为避免多个会话在同一个工作目录里相互覆盖，Agent Manager 支持创建 Git worktree。每个 Agent 可以在独立工作区处理任务，完成后再应用变更、提交或创建 PR。

这让并发修改更容易组织，但隔离工作区不等于自动解决语义冲突。两个任务即使没有改到同一行，也可能对同一个接口作出不兼容假设。因而原文描述的完成流程中仍有结果合并与审查，不能把 worktree 简化为“多个 Agent 无需协调”。

原文也允许共享 worktree，主要用于读取较多的场景，例如一个 Agent 修改代码，另一个查看 diff 或调查实现。这里减少了合并开销，但审查者看到的是持续变化中的状态；使用时仍需要清楚自己审查了哪个阶段的修改。

## 将审查意见变成定位明确的输入

Agent Manager 提供统一或分栏 diff 视图，以及文件树导航。比展示修改更进一步的是行级评论：用户在具体代码行留下意见后，可以一次发送回会话，连同文件路径、行号和相关代码一起作为上下文。

这种反馈保留了问题定位。相比让用户描述“某个函数那里不太对”，模型更容易把意见关联到当前产物；用户也可以逐项检查修改是否回应了评论。它没有替代审查判断，而是缩短了发现问题与下一轮编辑之间的信息交接。

同一个设计逻辑也适用于会话面板：展示多个 Agent 的状态，让用户知道何时需要介入。并发越多，查看结果、确认范围和传达反馈的工作越需要明确入口。

## 如何理解这次重构的意义

Kilo 的案例说明，当多个产品入口已经承担相同执行能力时，将核心从单一编辑器依赖中分离出来，能够为共享能力提供更直接的路径。并行与审查功能再围绕这条路径组织，而不是各自维护一套旁路。

它仍是一份预发布公告。原文把设置迁移、原生 provider 配置和正式发布列为后续工作，不能将路线图视为已经完成的生产验证。借鉴这类架构时，也应分别检查核心能否独立运行、入口是否接通、历史设置是否迁移，以及用户能否完成审查与结果整合。
