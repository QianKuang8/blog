一个 Agent 能独立修复问题之后，人仍可能忙于另一类工作：在群聊、代码评审和多个会话之间找回进度，转述刚刚改变的要求，再提醒正在执行的任务。DeepSeek Harness 团队的 [Super-agent 设计探索：迈向更自主的 Agent 系统](https://mp.weixin.qq.com/s/zoS7GlReWPhfCjENGxXCdg) 关注的正是这部分组织成本。文章由 Yujia Qiao 撰写，讨论团队内部实践形成的架构思路；微信原页无法访问，本文依据 [UIED 同文转载](https://www.uied.cn/posts/922127) 阅读。

作者的出发点是一个观察：一个人通常只能同时跟进 3 到 5 个活跃 Session。Agent 以单个 Session 为工作单位时，单任务的上限取决于模型能力，多任务的上限取决于人的注意力。

为此，作者把目标概括为连续、高效、主动、持久：同一任务换到另一个工作渠道仍能继续，多项任务可以并行，系统能根据环境事件推进工作，并在长期运行中恢复异常。理解这篇文章时，值得沿着一条消息追问：它由谁判断、送到哪里、带多少上下文，任务执行时人又怎样介入？

## 全局协调保持轻量，执行上下文按任务隔离

所有消息进入一个 Session，方便共享上下文，却容易因长任务阻塞响应；每条消息各开一个 Session，又难以知道新要求属于哪个旧任务。作者采用逻辑上的双层架构处理这项取舍。

Router 汇总跨渠道的信息与决策，负责分派工作和对外回复。它不直接承担具体执行，甚至可以不提供 Bash 工具。Worker 则配备执行工具，在独立上下文中完成任务，再向 Router 汇报。复杂任务内部仍可创建 Subagent 或 Agent Team。

![环境事件经过两级过滤进入 Router；已订阅事件可直通 Worker，所有 Session 状态存入数据库，Worker 接入执行环境，外部 Watchdog 负责监控。](/images/deepseek-super-agent/architecture.jpg)

*图 1：原图，来自 DeepSeek Harness 团队文章，经 [UIED 转载](https://www.uied.cn/posts/922127)保存。图中编号对应原文章节；重点观察 Router、Worker 与持久化状态的职责分工。*

这种安排使 Router 可以只保留跨任务的关联与决定，具体调试日志留在 Worker 内。与单个任务中的 Team Lead 相比，它较少介入子步骤规划。作者据此认为，Router 往往可使用较轻量的模型，Worker 则需要更强的执行能力。

我的理解是，这项设计首先规定了谁负责什么，再让模型决定如何完成职责。用户仍需要任务视图和项目管理，但不必按底层上下文窗口的划分来组织工作。

## 归属已经明确的消息，用订阅直接送达

持续接入群聊、评审和 CI 后，大量输入与当前任务无关。原文先用程序检查来源、群组范围等确定性条件，再让模型判断候选消息的语义与行动价值。这分别对应低成本的 Fast Path 和需要推理的 Slow Path。

路由也采用相同思路。一个 PR、IM 话题或邮件往来构成一条 Thread，其中每次消息或状态变化是一个 Trigger。新任务交给 Router 判断；Router 创建的 Worker 订阅相关 Thread 后，后续事件由程序直接投递。

![同一 Thread 的初始事件经过 Router 创建 Worker 并建立订阅，后续事件沿直通路径进入已订阅的 Worker。](/images/deepseek-super-agent/subscription-routing.jpg)

*图 2：原图，来源同上。首次判断任务归属需要 Router，确定归属后的重复转发可以由程序完成。*

例如一个修复任务同时涉及群聊和 PR，Worker 可以订阅两条 Thread；评审意见到达时，不必再等 Router 调用转发工具。若新消息超出任务范围，Worker 可以取消订阅或交回 Router。Router 仍可观察全局事件，关键结论与对外回复也继续由它汇总。

订阅是多对多关系，所以同一 Thread 的多个 Worker 能收到相同通知。但收到彼此的操作消息，只提供了发现冲突的机会；共享文件与任务结果仍需协调。这也延续了[Agent Swarm 解读]({{< relref "from-agent-team-to-agent-swarm.md" >}})中的问题：并发之后，谁负责确认结果能够共同工作？

## 连续性依靠可追索的对象关系

Router 不可能永久携带所有 Worker 的完整历史。原文采用 Inline & Spill：把近期很可能需要的短内容放进窗口，把长内容留在外部，并保留继续读取的入口。

这里有价值的细节是对象之间的引用。Trigger、Thread、Worker 都有唯一 ID，每次读取对象时，同时返回关联对象的 ID 和摘要。模型于是可以从当前消息找到所属 Thread，再找到 Worker，继续追到该 Worker 处理过的另一个代码评审。

这种链式召回为跨渠道接续任务提供了具体路径。与[文件系统承接上下文]({{< relref "filesystems-for-context-engineering.md" >}})相比，这里进一步强调了保存对象之间的关系：留下全文之外，还要留下下一步去哪里查的线索。作者也明确指出，这主要解决近期任务和会话历史的按需检索，跨月的长期记忆仍是开放问题。

## 执行可以持续，交互仍要及时响应

即使拆出了 Worker，同步工具调用也可能阻塞某个会话。原文将耗时工具改成异步的 `start()` 与 `stop()`：启动后立即返回 Started，任务在后台继续，完成结果再作为事件送回会话。新输入可在当前推理步结束后处理，无需等待后台命令完成。这一机制已在 DeepSeek Harness 中实现，但尚未默认开启。

![同步 ReAct Loop 在工具执行期间等待；异步 ReAct Loop 收到 Started 后可处理新消息，后台完成结果随后作为事件投递。](/images/deepseek-super-agent/async-react-loop.jpg)

*图 3：原图，来源同上。异步机制缩短的是前台等待后台工具的时间；当前模型推理步仍需结束后才能处理新输入。*

对外沟通也有不同节奏。Router 在 IM 中只在需要决策或验收时发消息，给出简短结论或直接的问题；团队验证过的一条硬性规定是单次回复不超过 100 词。在 PR 等异步渠道中，它则留下完整背景、改动和验证结果。后台提前尝试复现问题、准备修复，只在有价值时交付，是作者所说的投机执行；额外计算换来更少的人类等待，是否值得做仍取决于任务价值与资源预算。

长期运行还需要拆开计算、状态与执行环境。Agent Loop 可以在云端无状态容器中推进，会话状态存入数据库，真实开发机则通过轻量 daemon 提供执行能力。这样既保留本地未提交修改和工具链，也允许云端在设备重新上线后继续相关任务。作者把这种做法与 Anthropic 的“脑手分离”对照：两者都让 Harness 保持无状态、把会话日志放在 Harness 之外；区别在于那篇讨论的是托管服务里按需创建的沙箱，这里首先要接入用户日常使用、可能间歇在线的个人机器，即 BYOM（Bring Your Own Machine）。

最后，独立的 Watchdog Session 由定时消息驱动，在主系统外部检查基础设施和任务进展。它要识别进程仍活着、任务却反复绕圈或偏离目标的情况，并尝试恢复。由于 Watchdog 本身是有完整工具的 Agent Session，维护者可以用自然语言问它故障原因，也可以让它在线调整主系统的提示词和触发规则。我的理解是，引入模型判断也意味着监控本身可能误判，修复动作与任务状态的记录需要保留下来，才能复查它为何介入。

## 实验支持调度取舍，成本也随之变化

原文用约 300 条合成消息驱动四种方案，其中约 20 条是工作请求，每种运行 5 次。编码工作被替换成只消耗时间的工具，消息间隔和工作时长按四分之一缩放，模型调用保留真实耗时。因此，这项实验衡量的是调度与协作效率。

| 方案 | 任务完成时间 p50 / p95 | 单次实验读缓存 token，全部 Session |
| --- | --- | --- |
| Super-agent | 12.4 / 15.7 分钟 | 2323 万 |
| Super-agent，去掉直通 | 12.6 / 15.5 分钟 | 3177 万 |
| 单 Session + Subagent，中性提示 | 20.4 / 29.5 分钟 | 605 万 |
| 单 Session + Subagent，提示优先委派 | 13.8 / 29.0 分钟 | 1082 万 |

表中数据来自原文第 7.1 节的结果表；完成时间从工作请求到结果消息计算。中性提示下，主 Session 在五次运行中都未调用 Subagent；提示优先委派后，四次进行了委派，另一次仍选择自行执行。这解释了为什么“提供委派工具”和“由架构分离交互与执行”会出现不同的长尾表现。

另一方面，完整版与去掉直通的完成时间接近，但去掉直通后 Router 要做的决定增加约 30%，读缓存 token 约多 37%；完成时间没有变慢，是因为 Router 仍未触及吞吐上限（见下文的批处理压测）。这组负载下，直通的主要收益是减少路由推理开销；多 Session 方案整体仍以更多读缓存 token 换取较短的完成时间。这里统计的是缓存读取量，评估实际费用还要计入模型价格、其他输入输出用量与运行环境。

Router 单独压测的结果解释了单个常驻 Router 为什么够用。Router 每步是长输入、短输出，上一轮推理期间积压的 Trigger 会合并进下一次调用，主要增加的是 Prefill 阶段的并行计算。需要决定的 Trigger 到达速率从每分钟约 1 条升到约 40 条时，平均 batch 从 1.0 升到 2.8，单次请求耗时只从 2.5 秒增到 3.9 秒，单个决定分摊的推理时间从 6.4 秒降到 1.6 秒。因此在团队当前规模下，可以保留一个常驻 Router，先维持全局连续性。任务数量和耦合程度进一步增加后，何时分片、Worker 是否需要直接通信，仍需另测。

这篇文章最值得带入工程实践的，是把重复发生的决定逐步落到系统机制中：任务已有归属就直通，长操作启动后继续接收输入，历史材料通过 ID 按需找回。验收也应分别观察响应延迟、调度开销和任务质量。原文展示了前两者的初步证据，真实代码交付仍需要自己的评测；而在更大组织中共享上下文、连接带凭据的设备，还需要解决权限隔离与提示词注入风险。文章讨论的是内部架构探索，部分设计的实现原型也明确不是正式产品。
