一处代码修改经常需要其他位置跟进：定义变了，使用它的代码可能也要调整；当前文件改完，工作区里还可能残留旧写法。编辑建议若只盯着光标，能减少输入，却难以减少寻找遗漏的工作。

Augment 的 [The AI research behind Next Edit](https://www.augmentcode.com/blog/the-ai-research-behind-next-edit) 围绕这一问题介绍了三项设计：从编辑历史推断任务，用检索模型定位需要变化的代码，再生成可以应用的修改。原文披露的是这条处理链的设计与定性结果，没有提供足以独立复现的完整模型、训练集或性能评测协议。

## 编辑历史先要成为可解释的输入

“用户刚刚改过什么”并不等于一个干净的补丁。复制粘贴后再改写、来回切换文件、撤销与重做，都会产生混杂的操作序列。模型既要看到最新方向，又要区分一次探索性操作和用户打算保留的改动。

Augment 从 GitHub commit 和 PR 的说明、初始状态、最终状态出发，合成常见编辑场景。这里需要纠正一个容易产生的理解：原文没有把训练数据简单替换成真实交互日志；它使用提交材料模拟开发过程，让样本更接近推理时看到的中间状态。

编辑差异的粒度也是训练内容。粒度太细，模型容易被琐碎操作干扰；粒度太粗，又难以区分新变化与旧变化。直接把一个完成任务的 diff 切成若干块，也可能教出错误规律，例如避开已经修改过的区域，尽管下一步恰好还需要继续改那里。

另一个失败是撤销用户最新修改。团队通过调整训练样本抑制这种行为，使模型沿着近期改动继续推进。原文没有证明它来自某一种单独的数据偏差，因此更稳妥的理解是：意图推断需要同时约束“该跟进哪里”和“哪些新变化应该尊重”。

这层还有无法回避的取舍。建议覆盖面越大，越可能猜出用户没有表达的意图；只输出高置信度修改，则可能漏掉有价值的提醒。对持续工作的编辑器而言，错误建议还会消耗用户注意力，召回率和准确率要结合交互成本衡量。

## 定位与补充上下文是两项检索任务

意图明确后，系统仍需找到代码位置。对于有数万文件的 monorepo，每次都让通用模型翻目录、读文件，可能很难满足频繁触发的延迟预算。

Augment 为定位训练专用 retriever，结合当前上下文返回可能需要更新的文件和代码片段。光标周围的代码始终进入候选集合，并优先处理。这使系统可以先响应正在编辑的区域，再探索工作区中的相关位置。

找出位置以后，还需要知道在那里如何写才符合项目约定。原文描述了第二层用途：复用 completion 和 chat 的 RAG 基础设施，检索自定义 API、代码模式和相关上下文，供修改生成使用。前者回答“哪里可能要改”，后者补足“这里应该怎样改”。它们都涉及检索，但评价对象不同：找到相关文档，不一定意味着找全受影响位置；定位正确，也不保证模型正确调用项目 API。

这种拆分让故障更容易诊断。建议遗漏时，可以检查候选位置是否进入检索结果；建议出现在正确位置但写法不对，则继续检查上下文与生成。这个诊断方式是根据原文架构作出的工程归纳，并非原文公开的内部监控实现。

## 用紧凑 diff 控制生成成本

最后一段处理链把意图与候选代码变成修改。Augment 没有要求模型每次重写整个大文件，而是训练一种紧凑、能够无歧义应用到原始代码的 diff 格式。输出只描述必要变化，以减少生成 token 和等待时间。

原文报告，这一设计把生成延迟从数秒降到数百毫秒，但没有给出负载、分位数和完整基线，因此不能据此推导所有工作区里的稳定延迟。原文也没有公开格式细节，无法从文章还原其补丁协议。

这里的工程要求可以说得更具体：压缩输出不能让定位变模糊。一个很短、却无法判断该替换哪一段代码的补丁，最终仍需要额外修复。专用格式承担的是同时表达变化和应用位置的职责；RAG 则帮助变化符合仓库已有用法。

## 跨文件建议不等于一次完成全部传播

按原文介绍，Next Edit 的能力延伸到整个工作区；同时，支持更大规模变化、跨多文件批量编辑和更深的 chat 集成，仍被列为后续探索方向。读这类产品文章时，需要保留这条边界：系统可以发现远离光标的候选，不意味着已经证明能完整处理所有依赖传播。

这套架构可借鉴之处在于把不同错误拆开处理。训练历史解决意图误读，位置检索解决搜索范围，代码上下文解决项目用法，diff 解码解决修改表达与延迟。最终仍需通过实际建议和用户反馈检验整条链：预测的任务是否正确、关联位置是否充分、补丁是否有用，以及提醒是否打断工作。
