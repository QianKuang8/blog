同一个模型，用不同的工具、记忆和执行流程，可能表现出很不一样的任务能力。如果 Agent 能修改这些组件，再用执行结果检验修改，改进对象就从当前答案扩展到了产生答案的方法。

Lilian Weng 在 [Harness Engineering for Self-Improvement](https://lilianweng.github.io/posts/2026-07-04-harness/) 中梳理了这条路线：模型周围的运行系统怎样支持自我改进，又有哪些机制可以交给 Agent 搜索。本文重点看优化对象、失败反馈和候选接纳；研究结果按这篇综述转述，未逐篇复现实验。

## 先让执行过程留下可恢复的状态

原文中的 Harness 包含规划、工具调用、上下文管理、产物存储和结果评估，也管理权限与持续运行的状态。它决定模型在每一步能看到什么、能做什么，以及做完以后怎样得到反馈。

作者归纳的几个设计模式有一个共同前提：运行过程应当可检查。任务在“计划、执行、观察、调整”的循环中推进；长日志、实验结果和代码差异保存在文件里；子 Agent 和后台任务的进度也有持久记录。主 Agent 可以按需读取细节，中断后还能恢复。

这些记录也为改进 Harness 提供依据。只留下最终答案，就很难区分模型没有想到验证、工具无法执行，还是验证结果被误读。文件系统保存的不只是记忆，还有下一轮定位问题所需的证据。若并行任务只返回一段聊天结论，没有日志、状态和产物，恢复与归因都会更困难。

## 从积累经验到修改经验的管理方法

上下文优化可以发生在不同层次。原文用 ACE（Agentic Context Engineering）、MCE（Meta Context Engineering）和 Meta-Harness 展示了优化对象怎样逐步扩大：

| 方法 | 主要改变什么 | 怎样使用反馈 |
| --- | --- | --- |
| ACE | 带编号的经验条目 | 从执行轨迹提炼经验，增量合并、去重与修订 |
| MCE | 管理上下文的方法及其产物 | 内层优化上下文，外层依据验证集表现演化 Skill |
| Meta-Harness | 组织信息与执行的 Harness 代码 | 编程 Agent 读取历史、提出候选，再通过评估筛选 |

ACE 的关键设计是避免反复重写整段提示。生成器执行任务，反思器提炼经验，整理器给出条目级更新，再由确定性逻辑合并。这样可以减少多轮摘要逐渐删掉细节的问题，但“怎样更新经验”仍由设计者规定。

MCE 再向前一步：让 Skill 描述如何检索、筛选和组合信息，并让外层 Agent 搜索这些方法。内层在当前 Skill 指导下改进上下文函数，外层用验证集表现挑选更好的 Skill。它同时处理“保存哪些信息”和“用什么方法组织信息”。

![MCE 框架：上层演化管理上下文的 Skill，下层优化包含静态知识与动态操作的上下文函数，训练与验证反馈分别支持两层优化。](/images/harness-engineering-for-self-improvement/mce.png)

Meta-Harness 则直接把周围的代码系统交给编程 Agent 修改。候选的代码、分数、轨迹和状态都保存在文件中，优化者按需查询。由此可以理解这条路线的工程意义：经验条目再丰富，如果检索或调用方式不合适，信息仍可能用不上；允许修改机制，才能触及这类问题，同时也扩大了需要验证的范围。

## Self-Harness 怎样决定一项改动能否留下

Self-Harness 把自我改进组织为三个阶段：挖掘弱点、提出有限范围的修改、验证后决定接纳。这里最值得关注的是每个阶段需要交付什么证据。

首先，错误标签不足以说明原因。两次运行都显示“超时”，一次可能陷入重复探索，另一次可能等待一个过慢的工具。原文强调从执行轨迹中寻找验证器支持的失败模式，再优先处理重复出现、能够通过局部修改解决的问题。

接着，提案者会同时看到允许修改的组件、失败模式、需要保留的成功行为，以及此前尝试过的修改。成功记录的作用是提醒优化者：补上一个检查，也可能破坏原先能完成的任务。历史提案则帮助避免重复尝试已经失败的方法。

![Self-Harness 流程：固定模型下，从执行轨迹聚类失败，提出 Harness 修改，经回归测试决定接纳；全部拒绝时保留当前版本。](/images/harness-engineering-for-self-improvement/self-harness.png)

*图 2：原图，来源同上，原文转引 Zhang 等人的 Self-Harness 研究。注意底部的接纳与拒绝路径，以及两侧始终固定的模型：产生候选以后，仍要经过回归测试才会更新 Harness。*

最后，候选分别在用于检查已知弱点的 held-in 数据和用于检查其他问题的 held-out 数据上测试，两边都没有回归才接纳。拒绝的提案也会留下记录。这里的 held-out 数据参与了候选接纳，若要评估最终版本的泛化，还应另留未参与选择的任务；这是从筛选流程推导的评测建议。

进一步看，AHE（Agentic Harness Engineering）把改动与失败归因绑定：可编辑组件在文件系统中有明确表示，逐任务分析汇总成可查询的失败证据，每个修改还要写出预期解决的问题和可能引入的回归。下一轮因此可以检查一个具体假设，而不只是比较总分。

例如，假设多次失败都发生在最后一次编辑后遗漏验证，可以提出“调整退出前检查”的候选，并预测遗漏率下降、额外调用增加。这个例子是工程展开；它说明一项提案应同时给出改哪里、为什么改，以及用什么观察判断改动有效。

## 进化搜索时，要先说清谁在被改进

当候选可以自动执行和评分，就可以保留多个版本，让模型从历史方案生成修改，再筛选下一代。但“用了进化搜索”和“Agent 改进了自身”描述的是不同事情。

原文中的 AlphaEvolve 主要搜索任务程序，例如算法实现；DGM（Darwin Gödel Machine）则让编程 Agent 修改自身的 Harness 仓库。两者都使用候选池和评估反馈，改动的对象却不同。再往上一层，STOP 搜索的是改进器本身，即执行改进任务的方法。讨论递归自我改进时，应分别记录任务产物、执行系统和优化器发生了什么变化。

这些过程也可以在模型权重固定时发生。作者把 Harness 与参数联合更新视为后续方向，但对 SIA 的实验保留判断：提出方案、提供反馈的模型强于任务执行模型，基线也使收益归因较困难。选择了一个更新参数的循环，还需要说明收益来自哪些组件。

模型能力同样影响结果。原文转述，STOP 在 GPT-4 上获得改善，在 GPT-3.5 和 Mixtral 上却出现退化。另一项研究又区分“写出有用的 Harness 修改”和“利用新版 Harness 做好任务”的能力。这里可以得到一个直接的部署建议：候选的价值要由目标执行模型验证，提案者能写出看似合理的 Skill，并不足以证明执行者能在合适时机使用它。

## 评估与权限应怎样约束搜索

作者强调，评估器和权限控制应放在 Harness 演化循环之外。AHE 给出了具体做法：只允许修改 Harness 工作区，运行记录、追踪器、验证器和模型配置保持只读。这样可以排除关闭验证器、更换模型或增加推理预算等提分途径，使观察到的变化更容易归因。

固定规则之后，规则本身的质量仍决定搜索方向。单元测试可能只覆盖局部，判分模型可能奖励表面特征，研究价值也常常没有快速而准确的评分方式。原文因此提醒保存负结果、维持候选多样性，并关注仓库长期维护等短期沙箱成绩难以覆盖的目标。

据此落地，可以先选择一类反复出现、容易验收的失败，限定可修改组件，保存轨迹、旧版本和失败提案，再运行候选筛选。比较时记录质量与成本，最终冻结版本，用未参与选择的任务复查。有关预算对等与递归证据的区别，可继续看站内的 [Agent 自进化与 RSI 解读]({{< relref "/posts/self-evolving-agents-rsi.md" >}})。

这篇综述提供的研究视角，是让 Agent 的执行方法成为可搜索、可验证的对象。工程上值得保留的约束也很具体：修改依据能够回查，成功行为有回归检查，优化者无法改写验收标准，而最终结论来自目标模型在后续任务中的表现。
