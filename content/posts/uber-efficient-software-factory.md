Uber 的 [《Running a Software Factory Efficiently at Uber Scale》](https://www.uber.com/us/en/blog/efficient-software-factory/) 值得读，因为它把一个常见的预算问题拆成了可以逐项改进的工程问题：当 Agent 开始持续处理代码审查、CI 修复和日常维护，怎样知道钱花在哪里，又怎样判断优化没有损害交付质量？

作者 Uday Kiran Medisetty 给出的背景是，2026 年 2 月到 8 月，Uber 各类 agent 产品的周活跃员工数增至原来的 7 倍，周请求量增至 9.4 倍，而 AI 总支出自 4 月起相对稳定。这里的用户包含工程师和非工程师。按同一个模型的口径比较，每千次请求成本较峰值下降近 34%，单会话成本较 6 月峰值下降 52%。

这些数字来自 Uber 自己的工作负载。我的理解是，更值得迁移的是它的分析方法：先把成本归因到具体环节，再用完成任务的成本和质量一起验收。

## 先把账单拆到能采取行动的地方

原文把总成本拆成六个相乘的因素：

> 总成本 = 用户数 × 每用户会话数 × 每会话交互轮数 × 每轮模型请求数 × 每请求 token 数 × 每 token 价格。

用户数和会话数代表采用与使用，Uber 希望它们继续增长。中间几项则让团队看见执行过程中的开销：一次任务为什么需要这么多请求，每次请求为什么携带这么多内容，其中多少帮助了任务完成。

这个拆分的价值，在于同一张上涨的账单可能要求完全不同的动作。更多人开始使用工具、任务变复杂、模型反复搜索失败，都会增加支出；只有后两类继续拆开，才知道该改善执行路径还是接受合理的工作量增长。

Uber 同时跟踪每次合并 PR、每次审查和每次告警处理的成本，并配合回滚率、审查 F1 等质量指标。这样，请求变便宜之后，仍然可以继续追问：完成同样的工作花了多少钱，结果是否可靠？

## 用真实任务决定模型分工

Uber 为代码审查 Agent uReview 建立了真实 PR 评测集，其中包含已知缺陷，并按难度分组。模型除了接受精确率（precision）、召回率和 F1 的检验，还要比较单次审查成本、延迟、超时和噪声。文章报告，切换模型后，F1 提升的同时，每个 PR 的审查成本明显下降。

这里的选型依据是任务上的 Pareto 前沿：综合质量、成本与可靠性，寻找没有被其他配置全面胜出的方案。它依赖真实任务评测和能切换模型的运行框架，也需要随着模型变化反复测量。

交互式使用中，Uber 还调整了子 Agent 的默认模型。主模型负责拆解和评估，输入与职责明确的子任务默认交给成本更低的模型，同时保留人工覆盖。这给我的启发是，任务边界本身也是成本设计的一部分：只有说清楚子任务要交付什么、怎么判断完成，模型分工才有可验证的依据。拆分含糊时增加子 Agent，未必能获得同样的收益。

## 让脚本承接确定的工具流程

工具接入是原文里最具体的一组优化。在 Uber 原先预加载工具定义的接入方式下，安装超过 100 个工具，会给初始上下文增加约 5 万到 7 万个 token。即使本次任务用不到这些工具，定义也已经进入会话。

Uber 提供了两种改进路径：通过 tool search 搜索目录、按需载入工具；或者让模型调用 CLI，由 CLI 在调用时经统一 MCP Gateway 解析并执行工具。后一条路径仍然使用 MCP 服务，并保留网关的集中认证与策略执行。

Code-mode 在此基础上进一步改变了流程由谁推进。以数据仓库查询为例，提交 SQL 后，还要轮询状态数次，再获取结果。如果每一步都需要模型发起工具调用，轮询响应就会不断进入上下文。Code-mode 让模型生成脚本，由脚本执行这些步骤，最后返回摘要。

| 做法 | 减少的开销 |
| --- | --- |
| 按需发现工具 | 预加载工具定义 |
| 脚本执行轮询 | 模型逐步推进流程 |
| 返回处理后摘要 | 反复读取中间响应 |

原文在同一个会话中比较了五条 SQL 的两条执行路径。即使只返回一行的 `SELECT 1`，token 消耗也从 903 降到 402。小结果同样能节省，说明收益包含工具定义和流程推进的开销。

我认为，这个案例适合用来判断哪些动作值得交给模型反复决策。查询是否完成、未完成时继续等待，这类规则明确的步骤可以写进程序；模型负责决定查什么，以及如何理解结果。这个分工也有前提：脚本必须能识别失败并报告异常，否则省掉交互也可能让问题更难被发现。这里的 SQL 测量说明了特定流程的收益，不能直接当成任意 MCP 工作负载的节省比例。

## 减少无效搜索，也要保留有用上下文

工具流程之外，Agent 还可能把大量请求花在找信息上。Uber 的 AI Context Graph 把服务、团队、PR、设计文档、数据集和历史查询等信息连起来，让 Agent 可以通过自然语言查询关系。

文章给出一个对照案例：同一个模型处理同一个问题，有图谱时通过历史使用记录找到目标数据表，38 秒给出答案；没有图谱时，Agent 检查服务代码、启动两个子 Agent 并遭遇三次错误，约 20 分钟后仍错误地判断数据无法查询。这是一个案例，但它解释了上下文工程怎样同时影响质量和成本：提前找到可靠入口，可以减少后续试探。

上下文也需要管理重复传输的代价。Uber 在交互工具中把自动压缩阈值设为 400K token，默认采用 Medium 推理强度；针对常有较长停顿的人工交互会话，将文中所用的缓存保留时间从 5 分钟改为 1 小时，短时子 Agent 任务则保留 5 分钟。

这些是 Uber 根据自身任务和会话节奏选择的配置。我的理解是，应当一起衡量信息价值、重读次数和缓存成本。更早压缩需要考虑关键信息能否保留，更长缓存也要由实际的会话间隔支持。具体阈值需要在自己的任务上验证。

## 我的判断：托管任务让优化能够持续复用

原文最后把方向落在 managed agents，也就是由平台统一运行、负责明确任务的托管 Agent。代码审查、CI 修复这类反复出现的工作，可以共用运行环境、模型选型和评测标准，必要时交给人审查或处理升级。

我认可这个方向的原因是，明确的任务边界让优化更容易积累。一次工具流程改进可以被同类任务重复使用；切换模型时，也可以重新跑同一套评测。相比逐个分析工程师用途各异的终端会话，平台有了更稳定的比较对象。

但这也要求团队持续维护评测集、工具和上下文资料。对尚未掌握自身成本结构的团队，我会先选择一个高频、可验收的任务，记录完成成本、失败与重试，再根据证据决定投入哪一层。Uber 的会话分析面板提供了一个有用的参照：它把模型选择不合适、上下文膨胀、缓存过期等模式关联到具体会话和改进动作，帮助工程师找到下一步。

这也是我从文章中最想保留的实践顺序：定义交付结果，定位无效开销，修改执行方式，再用相同任务检查质量和成本。只有这条循环能够持续运行，单次降本才会成为可复用的工程能力。
