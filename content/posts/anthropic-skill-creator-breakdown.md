一份 Skill 写得再详细，也还要验证两件事：该用的时候会不会被用上，用上之后结果是否比原来更好。Riba 的 [skill-creator 拆解文章](https://blog.riba2534.cn/blog/2026/%E6%8B%86%E8%A7%A3anthropic%E7%9A%84skill-creator-ai-agent%E7%9A%84%E6%8A%80%E8%83%BD%E5%B7%A5%E5%8E%82%E6%98%AF%E6%80%8E%E4%B9%88%E8%BF%90%E8%BD%AC%E7%9A%84/)介绍了 2026 年 2 月更新后的工具链：它把创建初稿、执行样例、评价产物和修改说明连接起来，并另行优化触发描述。

本文依据这份第三方源码解读及其中的代码片段整理，没有复跑工具，实现细节以 2026 年 2 月的版本为准。阅读重点是每种评估回答什么问题，以及哪些结果仍需人工判断。

## 先定义产物，再建立比较基线

流程从任务意图开始：Skill 做什么，哪些请求应该触发，最终输出是什么，适合怎样验收。表单填写这类有客观答案的 Skill 适合写测试用例，写作风格这类主观性强的 Skill 则以人工审查为主，不能都简化成通过率。

初稿产生后，每个样例至少有两组执行：新 Skill 与不使用 Skill 的基线；修改旧 Skill 时，也可以用旧版比较。各组保存独立产物、执行记录、耗时与 token 用量。

基线用于回答“新增说明带来了什么”。如果不用 Skill 也能完成，新增包可能只是增加成本；如果两组都失败，则需要继续判断是需求、输入、工具还是模型能力的问题。有了基线，才能把 Skill 的作用与这些因素区分开。

## 断言通过，需要对应实际证据

Grader 读取执行记录，还要打开输出文件，逐条检查断言。Agent 声称“已生成 PDF”与存在一个可用 PDF，必须分别验证。原文举例：文件里有公司名称、整体却是乱码时，Grader 应判失败，因为这只是字符串碰巧匹配。

它还检查执行者的额外声明，例如字段数量、使用过的工具和完成范围，并评价断言本身是否有意义。只检查文件存在，会放过空产物；所有配置都能通过的断言，也区分不出 Skill 的作用。

能程序化验证的条件可以交给脚本，但脚本只覆盖已经编码的要求。文件格式有效、字段正确、版面可读是三个质量层，要分别检查。因此 Grader 的输出除了分数，还要列出证据和没有覆盖到的部分。

## 比较输出与解释多次运行

Comparator 将两份产物标记为 A、B，在不知道配置身份的情况下比较内容和结构。这样能减少“新版本应该更好”的预设，但评价者本身仍可能看错。

Analyzer 则查看多次运行的聚合结果，寻找共同失败、缺少区分度的断言，以及高波动样例。它还结合耗时和 token 开销，说明质量变化的代价。原文展示的数字是解释输出结构用的示例，没有对应某个 Skill 的公开实验。

评审页面把产物、评分和前轮结果交给用户查看，收集具体反馈。这个入口很重要：许多问题只有打开实际文件才看得出来，执行日志和评分摘要里都看不到。

## Description 优化测的是入口

描述优化处理另一条链路。查询集中同时包含应触发与不应触发的请求，工具运行模型，再检测它是否选择读取目标 Skill。按照原文的实现，检测到相关调用后即可判断触发，无需等待整项任务完成。

这让评估更快，也限定了指标含义：触发成功只说明选中了 Skill，正文执行得对不对，要靠前面的产物测试。两类测试各管一段，需要配合使用。

原文展示的循环按正负样本分层，约 60% 用于生成修改反馈，40% 留出。改进模型看训练部分的失败与历史描述，尝试归纳遗漏的用户意图，而非不停追加测试关键词；最终按留出部分成绩选择候选，未必取最后一轮。

这里有一个统计细节（我的分析）：代码把留出部分称为 test，但它参与了候选选择，实际承担的是验证集的作用。要估计对全新请求的效果，还需要一组没有参与修改和选择的样例；原文没有提供这样的实验。

## 让修改回应失败模式

产物评估帮助发现正文与资源问题，触发评估帮助发现描述范围问题。修复时应保持这一对应关系：技能未被选中，先检查触发条件；已加载却漏掉验收，检查流程与验证资源；每次都重写相同脚本，考虑把重复逻辑收进包内。

原文还建议删掉持续造成无用工作的指令，避免只针对少数样例补丁式修改。这使 Skill 维护更接近普通软件迭代：有输入、有基线、有实际产物，也有对失败原因的解释。

skill-creator 本身仍由模型执行，也依赖评价标准和用户反馈。它的贡献是让改进过程可以观察：每次修改都有基线、产物、评分证据和用户意见可查。结果是否可靠，取决于这些检查环节一起工作，以及团队持续校正检查标准。
