一份 Skill 写得详细，不代表它会在正确时机被使用；被使用，也不代表结果比原来更好。Riba 的 [skill-creator 拆解文章](https://blog.riba2534.cn/blog/2026/%E6%8B%86%E8%A7%A3anthropic%E7%9A%84skill-creator-ai-agent%E7%9A%84%E6%8A%80%E8%83%BD%E5%B7%A5%E5%8E%82%E6%98%AF%E6%80%8E%E4%B9%88%E8%BF%90%E8%BD%AC%E7%9A%84/)介绍了 2026 年 2 月更新后的工具链：它把创建初稿、执行样例、评价产物和修改说明连接起来，并另行优化触发描述。

本文依据这份第三方源码解读及其中展示的代码片段整理，没有复跑工具，也不把当时实现当作当前版本指南。阅读重点是评估分别回答什么问题，以及结果在哪里仍需人工判断。

## 先定义产物，再建立比较基线

流程从任务意图开始：Skill 做什么，哪些请求应该触发，最终输出是什么，适合怎样验收。可客观检查的表单填写与主观写作风格，需要不同评价方式，不能都简化成相同通过率。

初稿产生后，每个样例至少有两组执行：新 Skill 与不使用 Skill 的基线；修改旧 Skill 时，也可以用旧版比较。各组保存独立产物、执行记录、耗时与 token 用量。

基线用于回答“新增说明带来了什么”。如果不用 Skill 也能完成，新增包可能只是增加成本；如果两组都失败，则需要继续判断是需求、输入、工具还是模型能力的问题。单看新版本某次成功，无法分离这些因素。

## 断言通过，需要对应实际证据

Grader 读取执行记录，还要打开输出文件，逐条检查断言。Agent 声称“已生成 PDF”与存在一个可用 PDF，必须分别验证。原文用包含公司名称却整体乱码的文件说明，表面匹配字符串不能算完成填写任务。

它还检查执行者的额外声明，例如字段数量、使用过的工具和完成范围，并评价断言本身是否有意义。只检查文件存在，可能放过空产物；一个所有配置都能通过的条件，也未必能区分 Skill 的作用。

能程序化验证的条件可以使用脚本，但脚本只覆盖已编码的要求。文件格式有效、字段正确、版面可读是不同质量层，某一层通过不能代替其他层。Grader 的输出因而应包含证据与未覆盖之处，不能只留下一个分数。

## 比较输出与解释多次运行

Comparator 将两份产物标记为 A、B，在不知道配置身份的情况下比较内容和结构。这有助于减少对“新版本应该更好”的预设，但评价者仍可能误判，盲评不能自动保证结论正确。

Analyzer 则查看多次运行的聚合结果，寻找共同失败、缺少区分度的断言，以及高波动样例。它还结合耗时和 token 开销，说明质量变化的代价。原文展示的示例数字用于解释输出结构，并非某个 Skill 的公开效果实验，不能当作真实增益引用。

评审页面把产物、评分和前轮结果交给用户查看，收集具体反馈。这个入口很重要：许多问题只有看到实际文件才能判断，执行日志与评分摘要都不能替代产物本身。

## Description 优化测的是入口

描述优化处理另一条链路。查询集中同时包含应触发与不应触发的请求，工具运行模型，再检测它是否选择读取目标 Skill。按照原文的实现，检测到相关调用后即可判断触发，无需等待整项任务完成。

这让评估更快，也限定了指标含义：触发成功仅说明选择了技能，无法证明正文执行正确。入口优化与前面的产物测试需要配合，不能用其中一个代替另一个。

原文展示的循环按正负样本分层，约 60% 用于生成修改反馈，40% 留出。改进模型看训练部分的失败与历史描述，尝试归纳遗漏的用户意图，而非不停追加测试关键词；最终按留出部分成绩选择候选，未必取最后一轮。

这里还有一个统计边界：虽然代码把留出部分称为 test，它参与候选选择后，实际也承担了验证集作用。若要估计对全新请求的泛化效果，还需要未参与修改和选择的样例。这是依据展示流程作出的分析，原文并未提供独立泛化实验。

## 让修改回应失败模式

产物评估帮助发现正文与资源问题，触发评估帮助发现描述范围问题。修复时应保持这一对应关系：技能未被选中，先检查触发条件；已加载却漏掉验收，检查流程与验证资源；每次都重写相同脚本，考虑把重复逻辑收进包内。

原文还建议删掉持续造成无用工作的指令，避免只针对少数样例补丁式修改。这使 Skill 维护更接近普通软件迭代：有输入、有基线、有实际产物，也有对失败原因的解释。

skill-creator 本身仍由模型执行，也依赖评价标准和用户反馈。它提供了让改进过程可观察的结构，并没有证明系统能自动判断所有任务质量，或能够无限自我改进。可靠性来自这些检查环节共同工作，以及团队持续校正检查标准。
