给一个方法增加参数，往往只是修改的开始：调用点要补实参，方法内部可能也要调整。传统补全可以接着光标写代码，却很难主动把这些相关位置串起来。GitHub Next 的 [Next Edit Suggestions（NES）](https://githubnext.com/projects/copilot-next-edit-suggestions/) 项目把任务定义为：观察开发者刚做的修改，预测接下来可能需要的编辑，再按顺序交给开发者接受。

原文主要记录原型阶段的设计与开放问题，末尾另有已进入 Visual Studio Code 和 Visual Studio 的更新。下面讨论的是这份研究说明里的机制，不把原型设想当作所有版本已经实现的能力。

## 编辑历史增加了什么信息

仅看当前文件，模型能知道代码的结构，却不一定知道开发者正往哪个方向改。修改前后的差异提供了额外线索：增加字段、调整方法签名、复制配置块后更换名称，分别暗示不同的后续工作。

NES 因此需要同时回答两个问题：下一处修改在哪里，以及那里应当怎样变化。相较于光标处补全，搜索范围扩大了；但它也拿到了按时间排列的编辑信息，可以用刚发生的变化约束候选答案。编辑历史提供的是意图线索，并不等于用户已经授权了某个完整重构计划。

原文的三个案例能说明这种差别。给 Python dataclass 增加字段后，普通补全可以填默认值，NES 则继续建议文件内的相关修改；新增 `remoteName` 配置时，用户复制既有配置块并改名，模型据此推测余下调整；给方法增加参数时，模型还尝试为不同调用点生成合适的实参，并修改方法实现。

最后一个案例与 IDE 的标准重构存在交集，但关注点不同。标准重构擅长传播已明确的结构变化，NES 尝试结合语义提出具体内容。也正因内容来自预测，开发者仍需要检查每个实参是否符合调用场景。

## 一次展示多少修改，决定审查的负担

建议离开光标以后，开发者需要先切换注意力，再理解局部上下文。即使最终改动正确，频繁跳转也可能抵消节省下来的输入时间。

原文比较了字符级、单行和多行建议，却没有给出一个通用最优粒度。小建议容易逐个判断，但可能把一项连贯修改拆得太碎；大建议能一次展示更多关联，却要求用户同时审查更多内容。这里的取舍需要结合任务衡量：更少的按键不必然意味着更低的认知成本。

因此，NES 的交互需要同时说明“建议改什么”和“接下来去哪里”。原文把如何传达高层计划列为开放问题，而不是假定开发者可以从连续 diff 中自行还原计划。

## 最终结果正确，编辑路径也可能别扭

GitHub 展示过一段原型执行：最后代码效果不错，中途却先删除一行，稍后又加回来。这类现象把评估对象从最终代码扩大到了编辑序列。

对于逐步接受的产品，每一步都是用户要作的一次判断。如果中间状态令人困惑，用户可能在正确结果出现之前就停止跟随。建议顺序、粒度和导航方式需要一起设计，不能只根据最终 diff 是否正确来评价系统。

原文由此讨论了与 Copilot Workspace 结合的可能：Workspace 已经形成仓库级计划，能否在交接到 IDE 时把计划作为 NES 的上下文？这是帮助局部建议理解全局目标的方向，但原文没有证明它已经成为稳定的端到端工作流。同样，项目愿景涉及整个工程，文中具体讨论和演示主要落在文件内，不宜据此推断完整的跨文件覆盖能力。

## 质量、延迟与控制权要一起看

原型团队还在权衡模型大小：大模型的建议质量较好，但延迟更高；小模型响应更快，质量则有取舍。这对 NES 尤其敏感，因为等待期间开发者可能已经继续输入，原先的预测随之失去价值。

从这些问题可以推导出一组更贴近体验的评估方向：建议是否匹配当前修改意图、用户能否理解下一步、接受过程是否产生多余跳转，以及结果出现时是否仍然及时。这些是依据原文整理的观察维度，并非 GitHub 披露的完整评测协议。

NES 展示了一种保留开发者逐步控制权的协作方式。它承接近期编辑带来的局部工作，尚不能由此推导出自主规划、执行测试或保证整个任务完成的能力。读这篇文章的价值，也正在于把“预测下一次编辑”作为独立问题来设计和验证。
