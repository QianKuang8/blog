团队反复遇到同一类 Agent 错误时，怎样避免每次重新解释？Thariq Shihipar 的 [How We Use Skills](https://x.com/trq212/status/2033949937936085378)整理了 Anthropic 内部使用 Skills 的经验：把任务所需的说明、参考、脚本和资源放在可发现的目录里，再根据实际失败持续修改。

这是一份实践经验集，而非完整的效果评测。本文按归档时点解释其中设计，也保留作者对早期探索的限定。

## 从工作类型确定 Skill 边界

文章把常用 Skill 分为九类，覆盖库与 API 参考、产品验证、数据分析、业务自动化、代码模板、代码审查、交付部署、故障运行手册和基础设施操作。作者的观察是，边界清楚的 Skill 较容易理解，跨越太多工作类型的往往令人困惑。

分类的作用是让输入与预期产物明确。例如，库参考 Skill 解释某个接口的陷阱和正确例子；运行手册接收告警或症状，指导查询并输出调查结果；产品验证 Skill 则驱动应用，检查流程是否到达预期状态。

原文的支付验证例子很能说明最后一点：执行界面操作以后，还要确认发票进入正确状态。按钮点击完成和业务结果正确，是不同证据。相应脚本可以在流程各阶段作断言，录像则帮助人理解实际测试了什么。

这样的任务边界比一个笼统的“帮助开发”描述更容易维护，也更容易判断输出是否完成了工作。

## Description 负责让模型找到入口

会话开始时，模型看到可用技能名称及描述，再决定哪个与请求有关。因此，description 应说明何时使用，不能只摘要内部实现或列出宣传性能力。

触发之后，`SKILL.md` 提供主要流程，更细的接口说明放进引用文件，模板放进资源目录，重复操作放进脚本。模型只在需要时读取或调用，避免把所有细节预先装进上下文。

作者尤其强调 gotchas：把反复出现的具体错误写下来，而非堆叠模型本来就知道的通用原则。例如，库的特殊输入限制或团队常见失败点，比“编写高质量代码”更能改变下一次行动。

同时，说明应留下适应输入的空间。若每项任务都被迫走完全相同的路径，边缘情况可能引发无用工作。边界与验收标准可以明确，内部步骤则应解释其目的，让模型知道何时需要调整。

## 脚本、配置与历史数据各有位置

Skill 中的脚本把确定性操作封装起来，让模型把轮次用于组合和判断。数据分析任务可以复用取数函数，再按当前问题生成分析代码，减少反复重写凭据处理或查询样板。

某些 Skill 还需要用户配置，例如例行报告的目标位置。作者建议先保存必要配置，缺失时再获取信息。运行历史也有价值：日报任务读取之前的记录后，才能判断这次新增了什么。

但原文提醒，升级 Skill 可能清理技能目录内的数据。需要长期保留的状态应放在稳定的数据位置，不能假定与代码一起分发的目录永远不变。这区分了三种资产：可更新的技能内容、因用户而异的配置，以及跨运行积累的数据。

原文还介绍按需 hook，在调用 Skill 后于会话期间启用，例如限制修改目录。它把特定约束接到工具执行处；是否适用仍需结合当前任务，不能仅因存在 hook 就认定工作结果已经验证。

## 分发以后，还需要观察使用与结果

小团队可以把 Skill 放进仓库，让相关项目直接使用；规模更大时，插件市场让成员按需安装。作者描述的流程是先让少量用户试用，再将有使用反馈的技能纳入市场，并提醒冗余或低质量 Skill 很容易积累。

组合也有条件。原文说可以按名称引用另一个技能，但当时并没有原生依赖管理，只有被依赖的技能已经安装时，模型才能调用它。说明里写下名称，与依赖实际可用，仍要分别检查。

团队通过 PreToolUse hook 记录使用情况，发现热门技能或触发不足的技能。这回答的是“有没有被用到”，尚不能独自回答“是否改善结果”。若要进一步评价，可比较任务产物、失败类型和执行成本；这些是从使用观察延伸出的检查项，原文没有公布统一的量化成绩。

这套实践的起点可以很小：一项重复任务、一个已知陷阱，以及一个确认结果的方法。之后沿实际运行补充说明或脚本，删掉造成无用工作的指令。这样保存下来的团队经验，才更可能在下一次任务中产生具体作用。
