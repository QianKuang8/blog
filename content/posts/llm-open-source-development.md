一张生态图上新增和消失的项目，能否直接说明技术方向的兴衰？机器之心的 [大模型开源生态全景图 2.0 报道](https://mp.weixin.qq.com/s/D58GfDHogMS43Dl75fostw)提供了丰富材料，也提醒读者先检查制图方法。榜单记录哪些项目被这套方法选中，与整个行业里哪些项目仍有价值，是两个不同问题。

本文依据 2026 年 6 月保存、回顾 2025 年生态变化的报道整理，保留其历史口径，不将项目热度和功能说明视为当前选型数据。

## 60 个项目移出，首先发生了什么

报道说，2.0 图谱收录 114 个项目，比上一版少 21 个，其中 39 个新增、60 个移出。这组变化容易被读成大规模淘汰，但两版筛选方法也发生了明显变化。

1.0 从 PyTorch、vLLM、LangChain 等已知项目出发，沿协作与依赖关系扩展，门槛是 OpenRank 月均值至少 10。2.0 则从 GitHub 全域排名中筛选大模型相关项目，并把阈值提高到当月 OpenRank 大于 50。

起点改变、指标时间范围改变、门槛提高，都会影响入选集合。因此，名单变化不能全部归因于社区衰退。移出图谱不等于项目停止维护，更不等于不再适合某个工程场景。报道中的“出局”等措辞，应放回这个统计边界理解。

## 分层比总榜更接近实际依赖

新版将生态划成 AI Agent、AI Infra 和 AI Data 三个板块。这个分类便于追问项目在系统里负责什么，而不只是比较谁有更多 Star。

Agent 层进一步分成 Coding、Workflow Platform、Framework 和 Tool。编码应用承接开发任务，工作流平台组织应用流程，框架提供编排构件，工具则补足浏览器操作、记忆或外部连接等能力。它们可能在同一产品中组合，也可能存在功能重叠，不能因为归在相邻格子里就认定互相替代。

报道观察到 AI Coding 和一些工具项目活跃，而部分通用框架指标回落，并将其解释为注意力向具体应用转移。这是一种基于所选样本的趋势解读。框架已经被广泛采用后，新增关注降低，也可能与成熟度有关；仅凭活跃度曲线无法区分这些原因。

## 推理、运维与数据承担不同约束

AI Infra 中，报道重点讨论 Model Serving 和 LLMOps。前者面向模型如何高效运行，涉及推理吞吐、成本和部署；后者把监控、提示评测、可观测性等纳入应用生命周期，使团队能够发现输出与运行状态的变化。

二者对 Agent 的作用不同。Serving 影响一次调用怎样被执行，LLMOps 帮助团队观察和评估系统表现。模型调用更快，不能直接证明任务更准确；能够记录 trace，也不自动意味着评价标准已经建立。

AI Data 层则包含存储、集成、治理、向量检索等长期存在的组件。报道认为，这些项目较成熟、偏企业场景，因此社区热度可能不如新应用明显。这里应保留“可能”的性质：成熟基础设施的使用量、可靠性与 GitHub 新增关注，并没有一一对应关系。

这也是分层的实际用途。一个项目是否值得采用，需要放回它承担的约束中判断；相同的活跃度指标，放在新应用与成熟数据库上，含义可能不同。

## 开放了哪部分，也要单独确认

报道还关注开源与商业模式之间的张力。有些项目开放源码却设置使用条件，有些模型开放权重但没有完整训练材料，还有些 GitHub 仓库主要收集反馈，并不包含产品核心源码。

这些对象可以共同出现在生态讨论中，但“在 GitHub 上可见”不足以说明拥有同样的使用与修改权限。具体许可证和授权范围还需要按目标版本核查。本文不沿用报道中的项目级许可归类作为当前法律或商业使用判断。

由此看，生态图适合生成调查方向：先明确所需层次，再寻找候选，接着检查维护、依赖、可集成性和开放范围。它不能替代对实际任务的验证，也无法单凭热度预测项目会长期留下。

这份报道最可复用的内容，是把大量项目放回系统关系中观察。若同时保留筛选口径，就能既利用图谱发现变化，又避免把榜单变动误写成技术淘汰的证据。
