Agent 修复代码后测试通过，把失败经验写进 Skill，或者生成训练数据并更新参数，都可能被称为“自进化”。这些过程改变的对象和能证明的事情各不相同。把它们放在一起讨论之前，需要知道：什么被改了，改动由什么反馈驱动，又怎样确认后续任务确实受益。

周星星的[《自进化（Self-evolving／RSI），一篇就够了》](https://zhuanlan.zhihu.com/p/2065227313973825752)整理了多条研究路线。本文沿着其中的分类和案例，重点讨论反馈回路与评测。具体研究结果按原文转述，未逐篇独立复现。

## 先定位改变的对象

原文借用的分类，把优化对象分成三个层面：

| 层面 | 改变什么 | 改动怎样影响后续执行 |
| --- | --- | --- |
| Artifacts | 代码、算法、论文等任务产物 | 下一轮继续修改和评估这个产物 |
| Harness | prompt、工具、Skill、记忆、路由与协作流程 | 后续任务加载新的执行方法 |
| Model | 模型参数 | 后续推理使用更新后的模型 |

![自进化的三个方向：Harness 自我改进，Models 在没有标准答案时学习，Artifacts 优化产出，每个方向都画成指向自身的循环。](/images/self-evolving-agents-rsi/rsi-three-layers.jpg)

*图 1：原图，来源：[自进化（Self-evolving／RSI），一篇就够了](https://zhuanlan.zhihu.com/p/2065227313973825752)。三个循环分别对应上表的三层：改进执行方法（Harness）、在没有标准答案时学习（Models）、优化产出物（Artifacts）。*

例如，原文中的 autoresearch 让 Agent 修改 `train.py`，运行训练，再依据验证指标决定保留或丢弃改动。优化对象是训练程序和配置，执行研究的 Agent 可以始终使用同一个模型。这里需要分清研究者与实验对象：实验中发生训练，不等于研究者自己的参数也更新了。

Harness 则改变执行者可调用的方法。一次错误若被归纳进 Skill，下一次任务便有机会读取新的判断条件。这个“有机会”很关键：写入文件之后，还要确认它能被正确检索、在合适情形下触发，并帮助模型完成任务。原文把改 Harness 概括为后续任务都会受益，这更适合视为设计目标，实际收益仍有任务范围。

模型层的变化又多了一步：经验进入参数。原文介绍的 SIA 根据轨迹反馈选择修改 scaffold 或更新 LoRA；Continual Harness 则把任务内的 Harness 调整与跨轮次的参数学习组合起来。三层可以相互连接，分类时应逐项记录改变了什么。

## 反馈怎样进入下一版 Harness

原文对 RHI（Recursive Harness Self-Improvement）的介绍，给出了一个具体回路：用当前 Harness 执行任务，将本轮与上一轮输出交给评估器成对比较，保存偏好反馈，再由优化器读取历史、提出下一版 Harness。

![RHI 循环示意（论文 Figure 2）：第 i 轮 Harness 执行任务得到输出，评估器把它与上一轮输出成对比较，偏好反馈存入自我比较历史，优化器据此更新出下一轮 Harness。](/images/self-evolving-agents-rsi/rhi-loop.jpg)

*图 2：原图，来源同上，为原文转引的 Sakana RHI 论文 Figure 2。编号 ①–⑤ 依次是：执行任务、得到输出、与上一轮输出成对比较、把偏好写入历史、优化器据历史生成下一版 Harness。图中文字较小，可点击查看原图。*

这条链里有两个不同产物：执行者交付任务结果，优化器交付执行方法的修改。当前答案变好，只能直接说明本轮结果改善；若要判断 Harness 是否更好，还要在其他输入上重新执行。

RHI 对执行方法的拆分也有启发。除了角色与指令，它还区分 **contract** 和 **hop**：前者规定 Agent 与编排器之间传递哪些信息，后者规定协作经过哪些步骤。原文介绍，该方法优先调整这部分工作流。

信息交接本身就影响成本。下游 Agent 若只需要结论、证据和未解决问题，传入完整交互历史可能增加重复阅读。明确交接内容，有机会减少冗余上下文；但删掉关键依据，也可能让接收者无法核查。因此，接口调整需要同时看任务质量与资源消耗，不能只用上下文缩短证明成功。

评估器同样决定搜索方向。偏好比较能够指导候选筛选，却不能自动保证事实正确、代码可运行或业务约束满足。由此推导，落地时应把能够客观检查的要求接入测试或验收，并保留失败轨迹，让修改能回到具体问题上。

## 保存经验之后，要验证它能否迁移

原文用 Hermes 说明经验如何进入 Skill 和记忆，也提到 Skill 的审查、合并和归档。这类机制解决了经验的保存与维护；收益要在下一次调用时检查。

假设某次任务因为工具缺少参数而失败，可以先修复当前调用，再归纳工具的必填条件。若把当前任务的具体参数直接写成通用规则，下一次输入不同就可能出错。这个例子说明，从失败轨迹到可复用方法之间，还有一次对适用条件的概括。

多 Agent 协作也需要这样区分。原文中的 Apodex 把检索、冲突核对和最终验证分给不同角色，这描述了任务执行时的协作结构。要据此讨论自进化，还需进一步看到反馈是否改变了以后使用的结构或方法。增加执行者、改正当前报告、更新后续流程，分别需要不同证据。

站内的 [Warp Skill 改进案例]({{< relref "/posts/how-warp-builds-self-improving-agents-on-claude.md" >}})可以补上更具体的文件视角：反馈怎样成为一份可审查的 Skill diff，以及合并之后还要验证什么。

## 预算对等和留出任务决定提分怎样解释

自动优化会消耗额外的候选生成、任务执行与评估预算。若新版系统搜索了很多次，基线只执行一次，两者分数的差距就混合了方法变化与搜索投入。

原文转述 Ai2 的研究指出，在其 Terminal-Bench 2.1 实验中，自动 Harness evolution 没有稳定超过预算对等的简单 test-time scaling 方法。另一个问题是，若搜索时用于挑选 Harness 的任务，也是最终汇报成绩的任务，改进可能只适应该任务集合。

![Terminal-Bench 2.1 预算对等对照柱状图：Parallel Sampling 72.3，Sequential Refinement 69.3，Harness Evolution 67.4，Harness Scaling 71.8，虚线为初始 harness 基线 68.2。](/images/self-evolving-agents-rsi/terminal-bench-budget-matched.jpg)

*图 3：原图，来源同上。虚线是初始 Harness 的 68.2 分；在相同预算下，Harness Evolution（67.4）低于基线，并行采样（72.3）最高。*

这给工程评测提供了两个相互独立的问题：同样的预算，用来修改方法是否比多采样、反复完善答案更划算？冻结方法后，未参与搜索的任务能否继续受益？前者检查投入的去向，后者检查迁移。

原文中的 AIDE² 尝试回应这些问题：外层研究 Agent 修改内层 Agent 的代码，候选需通过评估才被接纳，并用固定预算、公私分数分离和外部基准检查效果。作者转述，实验运行八天、迭代一百步，约一成提案被接纳。

这里值得借鉴的是筛选机制。一次提案可以进入候选列表，是否保留则取决于结果。固定预算让不同方法具有可比性，留出评测帮助检查候选是否只迎合了搜索反馈；两者都不能保证对所有任务有效，但能让提分的含义更清楚。

## RSI 还需要改进能力本身的证据

原文在分类处曾把三类变化都称为 RSI，结尾又给出更严格的口径：自进化覆盖各种反馈驱动的改善，递归自我改进还要求“变好的能力”也继续改善。本文采用结尾的口径，分别判断优化对象和递归性质。

按这个理解，Agent 反复修改某个产物，可以证明它完成了迭代优化；更新 Harness 后在新任务上表现更好，可以支持方法收益的判断。要继续论证递归，还需说明更新后的系统，是否更擅长提出、筛选和验证下一轮改进。

据此可以提出一项更严格的验证建议：把改进后的 Agent 放回优化者的位置，在相同预算下比较它与旧版发现有效改动的能力。也应检查收益能否延续多个周期，以及哪些评测规则、任务选择和接纳决定仍由人设定。这些是从递归定义推导的检查方向，并非原文所有案例都已完成的实验。

模型权重变化与递归证据也应分别记录。更新参数说明经验进入了模型；改 Harness 也可能改善研究方法。两者是否形成持续的递归收益，仍取决于后续实验。可解释性研究可以帮助理解模型行为，但不能仅凭观察到内部表征，就认定递归自我改进已经发生。

## 从可检查的小循环开始

沿着这些案例落地，可以先选重复发生、结果容易验收的任务，把优化范围限制在一份 Skill、一个工具接口或一段协作流程。保存失败依据和旧版本，明确质量、成本与接纳条件，再让 Agent 提出候选修改。

搜索过程中保留回退能力，结束后冻结版本，用未参与优化的任务检查质量与回归；若要声称递归，再单独比较新旧系统的改进能力。这样得到的记录能解释：改了什么、解决了什么、对哪些任务有效，还有什么尚未得到证明。

原文梳理的三层框架有助于定位改进对象，RHI 展示反馈如何作用于工作流，Ai2 与 AIDE² 则把注意力引向预算和迁移。继续研究时，可以结合 [Harness 行为评估解读]({{< relref "/posts/harness-engineering-behavioral-evaluations.md" >}})，把过程中的行为断言与端到端任务结果一起检查。
