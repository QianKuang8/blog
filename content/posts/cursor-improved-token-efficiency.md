Agent 连续工作几十轮时，一段工具说明、一份文件内容或一次探索记录，可能随历史被反复送入模型。长任务的成本因此取决于每轮请求装入了什么、哪些内容能复用，以及中间过程是否一直留在主会话里。

Cursor 在 2026 年 9 月 23 日发布的[《提升长时间智能体运行的 token 效率》](https://cursor.com/cn/blog/improved-token-efficiency)中，介绍了五项 Harness 改动。团队报告，这些优化共同让用户的 token 成本降低了 7%，且 Agent 质量没有下降。这个数字来自 Cursor 自己的评估；文章更有参考价值的部分，是把成本追溯到具体的上下文组织方式。

## 常驻上下文要重新证明自己的必要性

系统提示和工具定义会持续出现在会话请求中。模型能力较弱时，为了约束工具使用、任务管理和代码修改，Harness 往往积累大量细节指令。模型升级后，旧指令仍然占据位置，却未必继续改善行为。

Cursor 报告，随着模型能力提升，很多任务只需清楚定义工具行为，原先冗长的操作约束便可以移除，最终精简了约 66% 的系统提示。工程上的启发是：模型升级后，要逐条重新评估已有指令的贡献，删除前确认这条指令承担的约束已由工具定义或模型自身行为覆盖。

工具定义还涉及使用频率。原文列举后台 shell 监控、云端子智能体、网页访问等新增能力，并指出其中大部分工具各自只在不到 20% 的对话里用到。全部常驻意味着没有使用它们的会话，也持续携带完整说明。

![Cursor 工具调用分布：read、grep、glob、shell 和 edit 被较多会话使用，web_fetch、create_plan 等工具的使用比例较低。](/images/cursor-improved-token-efficiency/tool-invocation-share.png)

*图 1：原页面图表截图，来源：[Cursor](https://cursor.com/cn/blog/improved-token-efficiency#improved-token-efficiency-most-invoked-tools-graphic)。横轴是至少调用过一次该工具的会话占比，并非工具调用次数或 token 消耗占比。高频读取、搜索和执行工具与低频能力的差异，为按需加载提供了依据。*

Cursor 因此保留读取、搜索、编辑和 shell 等高频工具，其他工具按需加载。但频率并非唯一依据：`ask_question` 被保留，是因为部分模型容易幻觉出对它的调用；规划模式中的 `create_plan` 则因产品流程需要而保留。由此可以归纳，静态上下文既要考虑调用频率，也要考虑定义缺席是否会引发错误、流程是否要求模型一开始就知道该能力。

站内的[动态上下文发现解读]({{< relref "/posts/dynamic-context-discovery.md" >}})可以补充按需加载的背景：完整资料保持可访问，当前请求先携带发现入口。加载被延后之后，仍要检查模型能否找到并正确使用工具。

## 缓存收益取决于前缀是否真的稳定

精简内容之后，剩下的系统提示、工具定义和历史消息仍会重复发送。Prompt caching 可以复用未变化的前缀，但请求中内容的排列方式会影响复用机会。

原文称，自 GPT-5.6 起，OpenAI API 允许客户端在隐式缓存之外显式标记缓存断点。Cursor 将断点放在稳定内容之后、不断增长的对话之前；同时让前面的工具和系统指令只保留极少变化的内容，把更多可变设置移到断点之后。

这些设置通过所谓的“幻影用户消息”承载，包括技能、子智能体和环境信息。它们是 Harness 组装进请求的用户级和请求级上下文，并非用户真的又输入了一条消息。显式断点是 OpenAI API 提供的接口，其他模型提供方的缓存接口各有不同。

![Cursor 缓存断点前后对比：右侧在稳定的工具和系统指令之后、setup 之后设置显式断点，并保留最新消息处的隐式边界，将可复用前缀与持续增长的对话区分开。](/images/cursor-improved-token-efficiency/cache-breakpoints.png)

*图 2：原图，来源：[Cursor](https://cursor.com/cn/blog/improved-token-efficiency)，为显式缓存断点示意。右侧分别标出工具与系统指令前缀、setup 前缀的结束位置；最末尾仍保留最新消息对应的隐式边界。可沿图比较哪些内容能够复用、哪些内容继续增长。[查看完整图](/images/cursor-improved-token-efficiency/cache-breakpoints.png)。*

断点和布局要一起调整：前缀本身频繁变化时，标记断点也复用不了什么。Cursor 报告这些改动让冷缓存未命中率降低了 20%。这是冷缓存未命中率的降幅，原文没有给出总 token 数或命中率的对应变化。

缓存优化与内容精简还作用于不同环节。前者降低重复处理的开销，后者减少进入请求的信息量。两者可以配合；没用的内容即使命中缓存、处理更便宜，也仍然占着上下文。[Claude Code 的稳定前缀设计]({{< relref "/posts/claude-code-prompt-caching-is-everything.md" >}})提供了另一组案例，说明动态状态怎样在保留旧前缀的同时继续传给模型。

## 文件读取的格式也会累积成成本

除了常驻说明，工具输出还不断向历史加入内容。Cursor 的 `Read` 工具原先给每一行代码都加行号，帮助模型引用具体位置。单个行号约占三到五个 token，读到数万行时，这部分定位信息就形成了可观开销。

团队改为每十行标注一次，并报告缓存读取 token 减少了 1.6%，质量没有下降。这里压缩的是返回格式中的辅助信息，文件正文仍是模型需要读取的内容。

这项改动提示，优化工具输出时可以检查哪些字段在高频重复出现，再验证减少它们是否影响任务。行号密度要保留足够的定位能力；省下的字符如果换来错误引用、重复读取或编辑偏移，收益就可能被抵消。每十行标一次是 Cursor 在自己任务上验证过的间隔，换一套工具需要重新测。

## 子智能体节省上下文，也带来交接成本

子智能体通常从新的上下文窗口开始，不必带上父智能体的完整历史；汇报后，主会话也不必保留它的全部探索过程。这给长任务提供了隔离中间上下文的机会。

但隔离会减少信息共享。子智能体可能重复父智能体已完成的探索，或者在任务变化后继续做不再需要的工作。是否值得委派，需要比较节省的重复输入与新增的交接、执行和检查开销。

Cursor 做了两项收紧：移除强烈鼓励使用子智能体探索代码库的指令，让模型更均衡地决定何时委派；调整模型选择参数，只在用户或 Harness 明确指示时使用其他模型。原文认为，模型训练已逐渐覆盖子智能体模式，因此额外的强提示不再总有帮助。

原文仍认为不同模型可以互补，例如组合昂贵的规划模型和较便宜的实现模型；收紧的只是切换时机。这部分改动没有单独报告降幅。

## 用同一批任务检查成本与行为

这些数字的分母不同：约 66% 对应系统提示的精简比例，20% 对应冷缓存未命中率，1.6% 对应缓存读取 token，7% 才是组合优化后的用户 token 成本降幅。所以它们不能相加，也换算不出某个用户的账单变化。

Cursor 用 A/B 测试选择工具加载配置，同时跟踪 token 用量、成本、延迟、工具调用错误和整体 Agent 用量。作者指出，离线 evals 适合快速迭代，但题目往往偏难，与实际请求的分布不同。文章没有公开完整的实验协议。

据此落地，可以先检查一批真实轨迹：哪些静态说明反复出现却很少使用，哪些前缀变化导致缓存失效，哪些工具格式占用大量历史，哪些委派造成重复劳动。每次调整都同时观察任务结果和整次运行成本，才能判断减少的 token 是否转化为可持续的效率收益。
