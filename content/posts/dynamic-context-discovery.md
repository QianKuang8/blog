工具返回几万行日志时，全部塞进上下文会占用窗口，直接截断又可能丢掉后续排障所需的细节。Cursor 的 [Dynamic context discovery](https://cursor.com/cn/blog/dynamic-context-discovery) 介绍了一种折中：完整资料留在文件中，先向 Agent 提供足够的索引，再让它按需读取。

这项设计改变的是信息进入窗口的时间。系统仍需保存资料，只是不再假设所有资料都应立即成为当前推理输入。原文以工具结果、对话历史、Skills、MCP 和终端五个场景说明这一模式。

## 长输出与摘要都有回到原始材料的路径

对于自研工具，Cursor 可以直接优化响应格式。第三方工具和 shell 则可能返回很大的 JSON 或命令输出，很难统一控制。

原文描述的处理方式是把长输出写入文件，允许 Agent 先用 `tail` 查看末尾，再按需要继续读取。模型先获得最可能与完成状态或错误有关的部分，若仍不足以判断，就沿文件路径获取更多证据。完整信息不必持续驻留在窗口里，也没有因截断而消失。

对话摘要采用类似思路。窗口用满后，系统生成摘要供新上下文继续工作，同时提供完整历史文件的引用。若 Agent 发现某项约束或细节缺失，就可以搜索历史找回。摘要负责帮助它迅速恢复任务，历史文件负责提供可追溯的细节，两者各有用途。

这也保留了一个条件：Agent 必须意识到自己还缺信息，并能找到相应记录。原文并未证明文件引用能消除摘要损失，它提供的是恢复机会。如果模型把一份不完整摘要当成全部事实，文件即使存在，也不会自动改善结果。

## 名称常驻，正文按需读取

Skills 和工具说明面对的是另一类浪费：定义可能很长，而一次任务只用到其中一小部分。

Cursor 将 Skill 的名称与描述放入静态上下文，具体执行说明和配套脚本留在文件里。Agent 根据任务识别可能相关的 Skill，再通过搜索或读取加载内容。这要求名称与描述能够承担发现入口的职责；若描述含糊，节省的正文加载可能变成寻找能力的额外工作。

MCP 工具也采用分层加载。模型先看到包括工具名称在内的小段静态信息，详细描述同步到按服务器组织的目录，需要时再读。目录结构保留同一服务器工具之间的关系：列出一个目录，就能看到该服务器提供的相关能力，避免把全部工具放进扁平索引。

这里的文件还承载状态。原文举例，当 MCP 服务器需要重新认证时，过去工具可能直接从模型视野中消失；文件化的说明让 Agent 有机会知道能力仍存在、只是需要恢复认证，从而向用户解释阻塞原因。发现机制因此也影响错误能否被正确理解。

## 终端文件让用户指代有了落点

原文还介绍了将集成终端输出自动同步到本地文件系统。用户询问“为什么我的命令失败”时，Agent 可以去看相关会话，而不再完全依赖用户手动复制输出。

长时间运行的服务尤其适合定向搜索：先确定终端会话，再按错误、时间或相关内容查找，读取小段上下文。与静态注入历史相比，这把窗口消耗推迟到了实际诊断时。

从这五个场景可以归纳出一条输入路径：轻量索引告诉模型资料在哪里，文件保存完整内容，搜索与局部读取把相关证据送进窗口。文件在这里既是存储，也是模型已熟悉的访问接口。

## 46.9% 描述了什么

Cursor 报告，在一次 A/B 测试中，对会调用 MCP 工具的运行采用按需加载后，Agent 的总 token 消耗减少了 46.9%。原文称该结果具有统计显著性，也明确指出收益随已安装 MCP 数量有较大波动。

因此，这个数字不能直接套到所有 Agent 任务。工具说明原本占得越多，可延迟加载的空间通常越大；如果任务几乎用遍全部工具，还要反复搜索描述，收益可能不同。原文没有在这段结果中给出对应的任务成功率变化，token 减少本身也不能单独证明质量提高。

动态发现把一部分预先组织信息的责任转给了运行中的模型，同时增加搜索和读取步骤。是否划算，需要把任务质量、延迟和总消耗一起比较。应当常驻的关键约束，也不能仅因为能保存成文件就全部移出当前输入。

原文最后保留了开放判断：文件是否会成为最终接口形式尚不清楚。可迁移的原则更简单——让大块资料保持可访问，让当前窗口保留正在使用的内容，并给遗漏的信息留下一条可回溯路径。
