Agent 能修改代码后，为什么仍频繁需要人接手？OpenAI 的 [Harness Engineering 文章](https://openai.com/zh-Hans-CN/index/harness-engineering/)把调查方向放在执行环境：目标是否明确，工具是否够用，规则能否被发现，以及修改以后能否获得有效反馈。

文章发表于 2026 年 2 月，介绍一款内部 beta 产品的五个月实验。团队从空仓库开始，坚持由 Codex 生成代码；约 1500 个 PR 被打开并合并，仓库累计约一百万行，涵盖应用、测试、基础设施、文档与内部工具。最初推动工作的有三名工程师，后来增加到七名。数字描述这次项目的规模，不能单独证明交付效率或长期维护质量。

## 从“再试一次”转向补齐缺失能力

早期任务推进缓慢时，团队发现 Agent 缺少完成高级目标所需的工具、抽象和结构。人的工作因此包含拆分目标、定义验收，以及让 Codex 把缺失的支撑能力补进仓库。

例如，给出“修复界面错误”以后，若 Agent 只能读源码，却不能启动页面、触发行为和查看结果，它就缺少验证这一目标的入口。继续强调认真检查，无法提供新的证据；需要先让运行环境可访问。

这项实验的“不手写代码”是团队主动选择的约束，用来探索工程师如何设计条件，并非所有项目的必要规则。人仍负责优先级、用户反馈和结果判断，Agent 则执行实现与验证工作。

## 将应用行为接回修改循环

团队让应用按 Git worktree 独立启动，再把 Chrome DevTools Protocol 接入运行时，提供 DOM 快照、截图和导航能力。Agent 可以针对某个变更启动实例，复现问题，查看状态，修改代码后再次检查。

可观测性也采用相同方式。每个 worktree 有临时的日志、指标和 trace 环境，Agent 通过 LogQL 与 PromQL 查询。这样，“启动在 800ms 内完成”才能从一句目标变成可测条件：执行启动，读取对应指标，与要求比较，再决定是否需要继续修改。

这些数值在原文中是可验证目标的例子，不是文章报告的统一性能成绩。更值得借鉴的是反馈接口：代码变化之后，系统能否提供足够明确的运行证据，让 Agent 区分修复有效、测试未覆盖和环境异常。

## 用知识地图连接长期约束

团队曾把大量规则放进一个巨大的 `AGENTS.md`，后来发现它挤占上下文、难维护，也不便检查。新的组织方式让约百行的入口文件充当目录，具体知识放在结构化的 `docs/` 中。

设计记录解释决策背景，产品规格说明预期行为，执行计划记录进度和未决问题，技术债务则有独立跟踪位置。Agent 从短入口逐步找到任务相关材料，任务结束后，计划和决策仍保留在版本历史里。

这项设计回应的是知识可发现性。团队在聊天或头脑中达成的约定，如果 Agent 运行时无法访问，就不会稳定影响下一次修改。把约定写入仓库后，还要维护其与代码的一致性；原文因此引入文档检查和定期清理任务，扫描过时内容并提出修复。

文档提供解释，但无法独自强制架构。规则需要继续落到能执行的检查上。

## 哪些自由留下，哪些边界机械执行

原文按业务域划分 Types、Config、Repo、Service、Runtime 和 UI 等层，并用自定义 linter 和结构测试限制依赖方向。认证、遥测等横切能力通过明确接口接入，避免各模块自行绕过边界。

结构化日志、命名、文件大小等要求也被编码成检查规则；错误信息中包含修复提示，使一次失败直接成为下一轮行动的输入。人不必每次重新指出相同问题，Agent 也能在提交前获得一致的反馈。

与此同时，团队保留实现层面的选择空间。例如，要求在边界解析数据，不等于指定每一处必须使用同一个库。可执行约束关注正确性和长期结构，局部表达只要可维护、可理解，就不必与某位工程师的偏好完全一致。

## 高吞吐需要同步维护纠错能力

原文描述了较少的阻塞合并门和很短的 PR 生命周期。这种策略依赖作者给出的成本关系：在该环境里，反馈快、纠错便宜，而等待消耗更多人类注意力。它不构成跳过任意测试或审查的通用建议。

另一个配套机制是持续清理。Agent 会模仿仓库中的现有模式，包括不理想的模式；生成越快，旧问题也可能扩散越快。团队把反复出现的审查要求写成规则，再让后台任务扫描偏差、更新质量记录并提出小范围重构。

由此，维护工作形成回路：一次用户问题或审查发现，先修复当前结果，再判断是否值得转成文档、工具或检查，供后续任务重复使用。规则本身也要接受效果检验，不能仅因它被自动化就认定正确。

文章最后明确限定，端到端执行能力高度依赖这个仓库的结构和工具投入，长期架构连贯性仍在观察。借鉴时更可操作的起点，是选择一种经常需要人工接手的失败，补足信息或验证接口，再用类似任务检查是否减少接手。这样才能把环境改进与实际效果联系起来。
