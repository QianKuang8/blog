一个能读邮件、操作浏览器和执行 shell 的个人 Agent，会同时接触私人数据与外部不可信内容。一封邮件或一个网页里的恶意指令，可能诱导它调用原本合法的工具。即使模型已经接受反提示注入训练，系统仍要回答：当模型判断出错，谁能阻止下一步动作？

Meta 的 Tarek Sheasha 在 [《How We Built Safety Into Muse》](https://research.meta.ai/blog/security-and-safety-for-ai-agents-our-approach-with-muse) 中，给出了一套围绕权限边界的设计：把 Agent 放入受限执行环境，把凭证和授权服务放在环境之外，再控制每次对外请求。本文依据这篇 2026 年 9 月 8 日发表的文章，解释其发布时架构；其中的安全效果属于 Meta 的设计说明，不能据此认定所有实现都已得到独立验证。

## 把执行能力与宿主权限分开

Muse 为每位用户提供独立的 Linux 云端虚拟机。虚拟机内部又分为两个安全域：一边运行处理不可信输入的 Agent，另一边运行管理凭证、审批和安全检测的服务。

Agent harness、工作区和它执行的工具位于 `systemd-nspawn` 容器，原文称为 **runtime cell**。这个执行单元拥有独立根文件系统和虚拟网络接口，但容器里的 root 映射为宿主侧的非特权用户。系统还过滤部分系统调用，移除 `CAP_SYS_PTRACE`、`CAP_NET_ADMIN` 等能力。因此，Agent 可以在自己的环境里编写工具，却没有随之获得修改宿主安全服务的权限。

安全分类器、凭证服务 `authd`、连接器 worker 和授权服务 Sentinel 都运行在 cell 外。跨域通信使用 Unix domain socket，通过 `SO_PEERCRED` 获取内核提供的对端身份，再执行访问控制。这让进程身份成为权限判断依据，减少依靠可被复制的共享秘密来识别调用方。

这层结构的意义是：把“Agent 可能被恶意内容说服”作为设计前提。即使它开始提出危险动作，负责限制动作的组件仍位于另一侧。

## 沿一次工具调用看三种权限

内置连接器在 cell 内暴露 CLI，但 CLI 只解析参数、打开调用方本来有权访问的文件，并把类型化参数和文件描述符传给外部 worker。真正的连接器业务逻辑在受 systemd 沙箱约束的 worker 中执行。

这条路径可以按职责拆开：

| 组件 | 负责的问题 | 主要约束 |
| --- | --- | --- |
| runtime cell | Agent 在哪里运行工具？ | 文件系统、系统调用和内核能力隔离 |
| `privsep` worker | 有凭证能力的连接器代码在哪里执行？ | 在 cell 外运行；以 cgroup 身份绑定凭证白名单 |
| `authd` | 已认证的调用方能获得哪类凭证材料？ | 凭证访问控制与 surrogate token 签发 |
| Sentinel | 这次动作和网络请求是否允许？ | 连接器策略、目的地、请求内容及用户授权范围 |

例如，日历 worker 的身份不能靠修改请求参数变成邮件 worker，因此不能向 `authd` 索取邮件凭证。这个限制独立于模型是否正确理解了任务。原文把这套 `privsep` 机制明确用于**内置连接器**；Muse 虽然也能生成自定义连接器，但不能据此假定后者天然具备相同的隔离结构。

凭证保护还多走了一步。需要认证的请求，在 cell 或 worker 中使用的是 `authd` 签发的 **surrogate token（凭证替身）**。只有具体网络请求获得授权后，Sentinel 才在出网边界向 `authd` 取得真实凭证，替换请求中的替身。模型和普通执行代码因而无需接触可直接复用的密钥。

不过，隐藏密钥只解决了一类风险。我的理解是，攻击者即使拿不到密钥，仍可能诱导 Agent 滥用已有服务能力，所以凭证替身必须和动作授权一起工作。邮箱连接器还过滤验证码、密码重置链接和免密登录链接，也是在缩小“允许读邮件”可能间接带来的账户控制能力。

## Sentinel 审核具体请求，用户通过独立通道确认

Sentinel 是 cell 外独立的宿主侧 Agent，也是连接器动作和网络出站的唯一授权主体。Muse 提出动作时，要提交连接器、方法、动作类别、范围及用户任务上下文。Sentinel 依据用户设置的策略，决定放行、拒绝或询问用户。

网络层的检查进一步落到真实请求。流量经受 Linux 网络机制约束的代理送达 Sentinel，它可以检查主机名、解析后的及最终目的 IP、端口、协议、HTTP 方法、路径和解码后的请求内容。SSRF 限制处理的是“域名看起来公开，解析结果却指向私有基础设施”这类问题。只审核工具名称，无法覆盖这样的目的地变化。

需要人确认时，执行停止，Sentinel 直接把待审批动作发到 Muse 客户端，用户的回答再直接回到 Sentinel。审批界面独立于与 Muse 的对话，权威授权状态也由 Sentinel 更新。由此，模型生成的“用户已经同意”不能直接充当一次批准。

批准还绑定具体连接器或目的地，以及用途。系统支持单次、会话、任务、限时和永久授权，由 Sentinel 决定向用户呈现哪些选项，并要求后续调用准确匹配范围。这意味着一次确认的价值取决于它到底授予了什么能力；范围过宽，即使审批通道可靠，也会留下较大的操作空间。

## 污染出网：减少审批必须保留前提

逐次弹窗会让后台执行失去意义。Muse 使用内核级数据流追踪，称为 **tainted egress（污染出网）**，帮助决定哪些网络请求仍能适用自动放行。

每个工具执行进程起初处于 clean 状态；读取用户数据后变为 tainted。实现利用 eBPF cgroup 程序进行网络拦截和进程归属判断，并在 Linux Security Module 钩子上跟踪污染传播。

这里最容易误读的是放行条件：**clean 状态只是一项前提**。请求还必须已经符合范围狭窄的自动放行策略，并通过出站 URL 的其他检查，才可以免于打扰用户。被污染或状态无法验证的进程会失去自动放行资格，退回正常审批流程。

这提供了一个比“这个工具通常很安全”更具体的判断维度：当前进程是否接触过用户数据。但它仍依赖正确的进程归属、污染传播和请求检查。原文没有给出足以评价覆盖完整性、性能开销或审批减少幅度的数据，因此适合从中学习机制，不宜据此推导实际拦截率。

## 浏览器也需要受限接口

浏览器能通过页面和表单完成大量有副作用的操作，必须纳入相同的权限设计。Muse 把 Chrome DevTools Protocol 连接交给 cell 外的独立 broker 管理，浏览器子 Agent 通过受控接口操作页面。

子 Agent 看到的是 accessibility tree（无障碍树）快照；接口不提供原始 DOM 读取、页面 JavaScript 执行或浏览器进程内命令执行能力，Chrome 开发者工具也被关闭。按原文设计，这同时限制了子 Agent 从 DOM 中取回已填入凭证的路径。

用户输入的用户名和密码通过客户端专用界面直接进入 `authd`，存于 cell 外，再在需要时填入浏览器。安全凭证填充期间，以及用户接管浏览器时，Agent 都会暂停，无法继续操作。额外的分类器检查无关个人数据外发、页面或下载文件中的提示注入，以及高风险表单提交，按风险阻止动作或要求人工复核。

我的理解是，这里明确选择了一个较窄的浏览器操作接口。它缩小了可滥用的能力，也限制了通用自动化常用的任意脚本执行。工程上需要持续维护 broker、页面语义接口和风险检测，不能只给一个权限很大的浏览器工具加上安全提示词。

## 纵深防御的边界还包括平台本身

Muse 同时使用模型训练、外部输入的不可信标记、独立提示注入分类器和人工审批。它们处理模型如何理解内容、如何识别攻击；runtime cell、凭证白名单和出网控制则约束被说服后的动作空间。各层承担不同职责，所以某一层出现漏判时，其他层仍有机会限制后果。

这些机制的组合会增加实现和运维复杂度：连接器需要类型化接口，权限要跨进程保持一致，浏览器能力被主动收窄，审批策略还要平衡打扰与风险。原文也承认 Muse 会犯错，提示注入仍是开放问题。其设计价值在于把权限拆成可检查的边界，而安全效果仍需结合实现、测试和真实攻击来判断。

还要单独看平台访问权。文章明确说明，当时的架构通过运营政策限制 Meta 人员访问，但 Meta 在支持、安全和服务运营需要下仍可访问数据。文中提出的 **Muse Confidential VM**，目标是用可验证的密码学机制限制这种访问；在文章发表时，它只面向少量受信测试者，并处于外部审计反馈阶段，计划年内提供。

数据训练也有独立政策：对话、工具调用和子 Agent 交接形成的轨迹，默认在移除关键个人身份信息后用于训练，用户可在设置中关闭。因此，评估个人 Agent 时，应分别追踪动作由谁批准、凭证在哪里暴露、数据最终由谁处理。Muse 对这些边界的具体拆分，提供了一份值得借鉴的系统设计样本。
