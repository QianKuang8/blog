“修好测试”只描述了目标，没有说明仓库在哪、应跑哪条命令、现有修改是否属于用户。一个能持续工作的 coding agent，需要先取得这些事实，再执行、读取失败，并决定下一步。

Sebastian Raschka 的 [《Components of A Coding Agent》](https://magazine.sebastianraschka.com/p/components-of-a-coding-agent) 用一个简化 Python Agent 解释六类组件：仓库上下文、提示与缓存、工具执行、上下文缩减、会话记忆和子任务委派。它是一份设计导览，讲的是组件分工，各家产品的具体实现会有差异。

## 从仓库事实构造下一次模型输入

模型负责生成回答或动作，Agent 循环把它放进反复观察和执行的过程，Harness 则提供组织上下文、调用工具、保存状态和控制流程的软件。

![Coding harness 的三层：模型族提供基础能力，Agent 循环按观察、分析、选择、执行反复推进，运行时支持提供仓库上下文、工具、权限、记忆和缓存。](/images/components-of-a-coding-agent/harness-layers.png)

*图 1：原图，来源：[Components of A Coding Agent](https://magazine.sebastianraschka.com/p/components-of-a-coding-agent) Figure 3。左侧模型提供“引擎”，中间的循环逐步推进任务，右侧的运行时支持对应本文讨论的大部分组件。*

第一类组件先收集工作区事实，例如仓库根目录、分支、Git 状态、项目说明和测试约定。这些材料帮助 Agent 找到正确入口，也能提醒它当前已有未提交变化。Live repo context 强调信息与实际工作区一致，按需读取即可，不必一次读完整个仓库。

第二类组件决定如何包装这些信息。稳定规则、工具说明和较稳定的工作区背景可以构成前缀，当前请求、近期历史与工作记忆随后进入输入。这样既给模型提供任务依据，也为重复调用保留缓存复用机会。事实收集和提示布局是不同工作：前者决定信息是否正确，后者决定如何高效传递。

## 动作先经过校验，再成为环境变化

第三类组件是工具链。模型输出一个命名动作及参数，Harness 检查工具是否存在、参数是否合法、路径是否在允许范围内，以及是否需要批准，然后执行并把结果送回循环。

![工具调用流程：模型输出结构化动作，Harness 校验工具与参数，必要时请求批准，执行后裁剪结果，再写入压缩后的历史，进入下一轮提示。](/images/components-of-a-coding-agent/tool-call-flow.png)

*图 2：原图，来源同上 Figure 8。编号 3–6 对应本节说的执行层：校验、批准、运行和裁剪都发生在模型之外，裁剪后的结果再进入历史，供下一轮使用。*

这些程序化检查能拒绝一部分无效操作，但看不懂意图：参数合法的命令仍可能做错事，允许执行的测试也可能没覆盖问题。所以工具反馈要让下一轮看清实际发生了什么，只回一句“成功”不够。

原文示例把路径检查和权限处理放在执行层，由可执行的规则承担。提示里的自然语言要求只能引导模型，路径是否越界要靠程序检查。

## 完整记录存在磁盘上，每轮只组装需要的部分

第四类组件控制工具输出和历史的体积。一次搜索可能返回很多文件，一条命令也可能产生长日志。示例通过裁剪大段文本、减少重复文件读取和压缩历史，避免一个冗长结果占满提示预算，并为近期事件保留更多细节。

第五类组件则解决存储与恢复。原文区分完整 transcript 和较小的 working memory：前者保留请求、模型回复和工具结果，后者维护当前任务、关键文件及重要笔记。压缩后的对话负责构造下一次输入，工作记忆负责延续任务状态，两者可以相关但不必完全相同。

![会话状态：新事件追加到磁盘上的完整 transcript，并整理进 working memory；下一次提示由稳定前缀、压缩后的历史、工作记忆和最新请求组装。](/images/components-of-a-coding-agent/session-memory.png)

*图 3：原图，来源同上 Figure 11。左侧是保存在磁盘上的会话状态，右侧是下一次实际进入提示的内容：完整记录不会整段重放，而是以压缩历史和工作记忆的形式参与组装。[查看完整图](/images/components-of-a-coding-agent/session-memory.png)。*

这个区分很实用：模型只看到截断后的日志，原始结果仍可以留在磁盘上；会话从磁盘恢复时，当前文件可能已经和保存时不同。我的推论是，恢复会话时要做两项检查：读取必要的记录，同时重新确认容易变化的工作区事实。

## 子任务需要上下文，也需要限定范围

第六类组件用于把旁支问题交给另一个执行者，例如定位符号、解释配置或调查一个测试失败。主任务获得整理后的结果，而不用携带全部探索过程。

委派至少需要说明目标、相关材料、允许操作和返回内容。原文特别强调 bounded subagents：可以限制只读权限或递归深度，避免重复工作、冲突写入和无界扩展。具体限制因产品而异。

文章也说明，Mini Coding Agent 的子任务目前同步运行。这个例子演示的是职责拆分和上下文隔离，没有测量并行加速；能否并行、能省多少时间，取决于调度实现与任务依赖。

## 用整条执行链解释质量差异

六个组件并非互相独立的功能列表。工具结果影响下一轮上下文，压缩决定哪些事实继续可见，记忆决定中断后怎样恢复，委派又引入新的信息交接。一个环节遗漏条件，后续模型即使推理正确，也可能基于错误输入行动。

原文猜想，把 GLM-5 这类最新、能力最强的开放权重模型放进类似的 Harness，表现可能与 Codex 中的 GPT-5.4 或 Claude Code 中的 Claude Opus 4.6 相当；作者明确说这是推测，没有给出同条件的对照实验。要检验这一点，可以固定任务和模型，观察每项系统改动是否减少具体失败，再在更换模型时重新检查配合效果。

这份导览的用途，是让“Agent 表现不好”变成可调查的问题：是否没找到文件、错误没有反馈、摘要丢了约束，还是委派缺少依据。组件边界清楚，才能知道下一次应修改哪里。
