“找不到匹配上下文”常常发生在代码逻辑已经想清楚之后：模型输出了一段修改，但真实文件已变，或者文件中存在几个相似片段，工具无法确认该改哪一个。

Fabian Hertwig 的 [《Code Surgery》](https://fabianhertwig.com/blog/coding-assistants-file-edits/) 从文件编辑这一步比较五个 coding assistant。原文对开源系统的描述来自当时的代码分析，对 Cursor 的描述来自公开讨论与访谈。以下沿用这份历史观察，重点看工具契约，不把它当作各产品当前版本的功能清单。

## 编辑工具要完成三次转换

模型先把意图转成一种文本协议，工具再把协议解析成文件操作，最后将执行结果反馈给模型。任一阶段都可能失败：格式无法解析、目标片段不匹配，或者部分修改已成功但重试又把它重复执行。

因此，编辑成功至少需要三个条件：知道操作哪个文件，能够在当前内容中定位目标，以及明确保留与替换的边界。行号直接，却容易随着文件变化失效；上下文片段能抵抗位置移动，却可能重复或已经过时。工具格式的选择实际是在分配这些约束由谁承担。

原文列出的 patch、diff、搜索替换、按行操作和模型辅助应用也并非互斥架构。一个产品可以支持多个格式，同一条执行链也可以先定位区域，再交给另一个模型重写。

## 上下文锚点怎样替代脆弱的行号

原文介绍的 Codex patch 用文件操作标记、`@@` 附近的代码文本，以及增删行描述修改。工具读取当前文件后，先按原样寻找上下文，失败时再尝试放宽空白匹配。这让模型主要提供“要改的内容及其附近是什么”，降低对行号计数的依赖。

Aider 把不同编辑格式封装成可替换的 coder，包括 Search/Replace、unified diff 和完整文件输出。搜索替换明确给出旧块与新块，便于检查修改边界；应用阶段还可依次尝试精确、空白或缩进相关的匹配策略。

这种设计没有消除状态差异。假如模型读完文件后，用户又改了同一函数，旧块就可能失效。宽松匹配可以容忍排版差异，却未必能判断两段相似代码是否语义相同。对工具作者而言，应用率和误匹配率需要一起观察，不能把“没有报错”直接当作定位正确。

## 缩进与部分成功也属于执行协议

RooCode 的例子把注意力放在定位与格式保留上。原文描述其从预期位置附近向外寻找候选块，再按相似度评分；替换时记录原代码的前导空白，同时保留新代码各行的相对缩进。对于 Python 一类依赖缩进的语言，这关系到程序含义；在其他语言中，也决定输出是否混入大量无关格式变化。

Aider 的失败反馈则展示了恢复过程需要哪些信息：哪个块没有匹配、当前文件有哪些相似行，以及其他块是否已经应用。最后一项尤其容易遗漏。若一轮有三个修改块、其中两个成功，下一轮应该只修复失败块。把整次操作简单归为失败，会让模型基于错误状态重新尝试。

一个有用的错误报告应帮助下一轮减少不确定性：重新读取文件，调整锚点，或缩小修改范围。只有错误码而没有当前内容，通常不足以让模型判断该怎样恢复。

## 让另一个模型承担合并工作

OpenHands 在传统编辑方法之外提供可选的 draft editor 路径：主模型指定区域，工具提取内容，将其与修改说明交给编辑模型，再把返回区域与文件前后部分拼接。编辑模型需要输出完整代码，不能用“此处不变”代替应保留的内容。原文把这一功能描述为可选、可能具有实验性质，不能据此认定它是所有任务的默认路径。

Cursor 则进一步把修改草图和应用分开：主模型表达变化，专用 Apply 模型负责与原文件合并。这样可以分别优化规划与应用，但也增加了一个需要评估的生成步骤。Apply 模型可能理解草图，也可能扩大修改范围，最终仍要检查落盘差异。

这几种方案的共同问题是交接是否完整。规则式编辑要有足够明确的锚点，模型式编辑要有足够清楚的约束；两者都需要返回可核验的执行结果。落盘成功只说明文件发生了变化，修改是否实现需求，还要由后续的 diff 审查、运行结果或测试回答。
