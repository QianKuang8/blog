通用 Agent 能搜索、写文件、执行命令，距离胜任一项专业工作仍有多远？周星星在 [2025 年 Agent 复盘](https://zhuanlan.zhihu.com/p/1983512173549483912)中把问题拆成两部分：输出是否符合行业判断标准，以及系统能否在多步骤任务里持续保持方向与质量。

原文以“架构之争已经结束”概括作者的观察，并将 Claude Code、Claude Agent SDK 与 Deep Agent 作为代表。这是实践者对当时技术形态的判断，文章没有提供覆盖行业的比较实验。更适合借鉴的是其拆解业务能力和执行机制的方法，不必把标题当作架构已经定型的事实。

## 专业能力需要明确的验收对象

作者用招聘和营销举例说明“够垂”的含义。招聘报告需要覆盖候选人的研究、项目等关键信息，并达到专业人员的判断要求；营销任务则不仅要列出网红，还要让名单与报价符合品牌定位和业务经验。

这些例子是在说明评价方式，并非公开的产品效果报告。它们指出了一个容易被工具列表掩盖的问题：接通搜索和业务 API，只提供了获取信息、执行动作的能力，尚未告诉 Agent 怎样判断一份结果是否合格。

作者将业务知识进一步分成标准流程、评分标准、成败案例和行业共识。它们进入系统之后，应当影响模型的具体选择，例如哪些信息必须查到、哪些条件需要复核，以及什么结果应当退回重做。由此看，专业化首先要求把业务中的隐性判断转化为可引用、可检查的材料。

## Skills 提供分层读取的知识入口

原文用 PDF 技能解释渐进式披露。Agent 起初只看到技能名称和描述，以判断是否相关；确认需要后读取 `SKILL.md`；遇到填写表单等具体任务，再读取被引用的 `forms.md`。脚本也可以与说明放在一起，供模型直接运行。

这样的组织把发现、理解和执行分开了。通用上下文不必包含所有细节，专业流程又能在需要时进入当前决策。确定性操作交给脚本，也能减少每次重新生成同一段处理逻辑的需要。

不过，“文件已经打包”与“模型正确使用了技能”是两个阶段。描述是否让技能被发现、说明是否足以执行、脚本是否适合当前输入，都需要分别检查。原文给出的不同模型触发率是作者经验性表述，未交代完整测试方法，不能据此建立跨模型的稳定能力排名。

## 长任务怎样分配上下文

作者围绕规划、子 Agent、文件系统和系统提示整理长任务设计。它们各自处理不同问题：计划记录当前目标和进度；子 Agent 承接局部工作；文件保存大块材料和中间产物；提示规定何时规划、委派及如何使用工具。

主 Agent 委派子任务后，局部搜索和试错可以留在子上下文，只把结果传回负责人。这减少了主上下文的负担，也支持独立任务并行。但高度压缩的返回内容可能遗漏限制条件。因而从这种结构可以进一步推导：委派时需要清楚的完成标准，回传时需要保留能够检查的依据，不能只传一句成功结论。

共享文件补充了消息通道。执行者可以写下完整产物，负责人按需读取；上下文压缩后，也能通过路径重新找到材料。文件提供存储位置，系统仍须处理命名、更新和交接约定，否则只是把混乱从消息历史搬到目录里。

## 工具分层降低的是哪一类开销

原文还描述了三层工具组织：少量高频原子工具负责基本交互，沙箱里的命令行程序提供更多能力，代码或软件包则封装可一次执行的连续操作。

例如，视频处理可以通过 shell 调用已有程序，不必为每个参数组合增加独立工具；一组重复查询与换算可以写成脚本，减少模型逐步往返。两者分别降低工具定义占用与调用轮次，但也要求环境里已经具备程序、依赖和可理解的使用说明。

自动压缩解决的是另一种开销：历史增长到窗口承受范围附近时，系统需要缩减活动上下文。摘要能够释放空间，却可能损失约束和失败信息。原文中的阈值只是一种实现示例，不能作为所有 Agent 的固定规则；是否还能正确继续任务，需要在压缩后验证。

## 架构可复用，业务判断仍需积累

作者认为，把流程图里的部分业务逻辑转为提示、技能和动态决策，可以更快迭代。但复杂度并没有因此消失：原先显式的分支，需要在新的系统里通过材料、接口和反馈继续表达。

这也限制了“把 Workflow 升级为 Agent”的适用范围。若流程已经明确、可稳定执行，动态决策未必带来收益；若任务经常需要根据新信息调整路径，通用循环与业务技能的组合才更值得实验。可以保留已有工作流作为比较基线，检查任务质量、人工介入与执行成本如何变化。

这篇复盘提供的是一组组织问题的视角：知识在哪里保存，何时被加载，任务怎样拆分，以及长链执行如何维持可检查的状态。把这些问题回答清楚，比宣告某个架构获胜更能帮助下一次实现。
