让模型运行一条命令，和让它持续修改一个仓库，中间隔着一套状态管理。模型要知道已经做过什么、工具实际返回了什么，以及当前应该继续执行还是交还控制权。

OpenAI 的 [《深入解析 Codex 智能体循环》](https://openai.com/zh-Hans-CN/index/unrolling-the-codex-agent-loop/) 沿 Responses API 请求展开了这套机制。以下讨论以原文记录的实现为准，重点是数据如何流动；配置项、端点和行为不作为当前版本的操作指南。

## 一轮用户请求包含多次模型调用

初始请求并非只有用户输入。原文将其组织为三个部分：`instructions` 提供模型指令，`tools` 描述可调用工具及参数，`input` 承载消息和其他输入项。Codex 还会加入权限说明、项目指令、技能元数据及工作目录等环境信息。

模型返回工具调用时，运行框架根据名称和参数执行工具，再把调用与结果送回下一次推理。原文中的一个最小闭环可以表示为：

```text
用户任务与环境
  → 模型输出 function_call（带 call_id）
  → 运行框架执行工具
  → function_call_output（关联同一个 call_id）
  → 更新 input，再调用模型
```

`call_id` 把“请求执行什么”与“得到什么结果”对应起来。下一次请求还需要保留相关的模型输出项，例如 `reasoning`；不能只把终端文字随意拼到一条消息里，就假定原有语义仍然完整。

Responses API 通过 SSE 流式返回事件。文本增量可以驱动界面显示，完成的输出项则进入后续请求的历史。显示给用户的文字和模型继续工作所需的结构化状态是两种用途，运行框架需要同时处理。

工具循环持续到模型给出面向用户的最终消息，或者请求用户补充信息。它标志这一轮控制权交还用户，并不单独证明代码正确。实际交付物可能是磁盘上的修改，是否满足任务仍要看产物及验证结果。

## 请求无状态，会话仍然有状态

原文介绍的 Codex 没有使用 `previous_response_id`，而是在后续请求中显式携带所需历史。这里的“无状态”指 API 请求不依赖服务端保存上一响应的会话数据；客户端仍然维护任务历史、工具调用和环境变化。

这个选择便于服务端实现，也服务于零数据保留配置。原文还说明，专有推理项可以通过 `encrypted_content` 随请求返回，由服务器解密使用。它让客户端能够携带后续推理所需的信息，而不要求客户端理解其中的内容。

代价是重复传输。如果每轮只追加一小段内容，后续却不断重发累积历史，总传输量会快速增长。网络传输成本与模型处理成本需要分开看：原文认为模型计算开销更值得优先优化，因此把提示缓存作为重要设计约束。

## 缓存复用依赖稳定的前缀

提示缓存能够复用此前相同前缀的计算。为此，原文中的历史更新尽量采用追加方式，让旧提示保持为新提示的精确前缀。

这个要求会影响看似无关的实现细节。原文提到，早期 MCP 工具枚举顺序不固定，造成了缓存未命中；更换工具集合、模型相关指令，或改写前面的权限与环境消息，也可能减少可复用范围。内容语义相同，并不等于 token 序列一致。

对于工作目录或权限变化，Codex 尽可能追加一条新的环境或权限消息，说明最新状态，而不是回写旧消息。这样同时保留变更历史与原有前缀。模型需要按新消息理解当前环境，缓存则仍有机会复用此前内容。

这里有两条不同的约束：状态必须准确，组织方式应尽量利于缓存。缓存收益不能成为隐瞒环境变化的理由；同样，命中缓存也不会缩短逻辑上的上下文长度，它减少的是重复计算，窗口容量仍然受限。

## 压缩会重建继续工作的输入

一次任务可能产生大量工具结果，即使缓存有效，历史也会逼近上下文窗口。原文介绍的 compaction 在达到阈值后，用更小的项目列表替换原有 `input`，使后续调用保留任务所需的历史表示。

早期实现依靠 `/compact` 请求模型生成摘要；后续引入 `/responses/compact` 端点，返回可继续使用的输入项，其中包括带不透明 `encrypted_content` 的 `compaction` 项。两者描述的是演进过程，不应混为始终同时运行的两套机制。

压缩解决容量问题，也改变此前的精确前缀关系。因此，历史追加和压缩服务于不同阶段：前者尽量复用未满窗口的上下文，后者在容量约束出现时重建输入。压缩后的运行能否继续正确完成任务，仍要看目标、约束、已执行动作和关键证据是否得到充分保留；“成功返回压缩对象”只是接口层面的成功。

原文还提醒，工具的执行边界并不完全相同：其描述的 Codex shell 沙盒不自动覆盖外部 MCP 工具，后者需要自己的防护措施。这进一步说明，工具名称出现在同一请求里，只统一了模型调用接口，并没有自动统一各工具的权限与执行保证。

沿这条循环检查系统，会得到几个清楚的排查位置：请求是否包含正确环境，工具结果是否关联到正确调用，历史变更是否破坏缓存，压缩后是否仍有足够信息继续任务。模型输出质量与运行时状态都可能影响结果，只有把两层分开观察，问题才容易定位。
