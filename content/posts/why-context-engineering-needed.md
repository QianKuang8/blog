一个子 Agent 开始工作时，不只需要一句任务说明。它还可能需要上游已经确认的事实、当前约束、可调用工具，以及尚未解决的问题。给少了，它无法判断；把所有历史搬过去，又可能掩盖当前任务。

周星星的 [《为什么我们需要 Context Engineering？》](https://zhuanlan.zhihu.com/p/1953085369328337945) 将这个问题放进 Write、Select、Compress、Isolate 四种动作中讨论。它们分别处理信息保存、进入窗口、缩减和分工，是作者引用的一种分析框架，并非上下文工程唯一的分类标准。

## 长度不能单独代表信息是否充分

原文一边讨论长上下文中的干扰，一边举邮件助手的反例：只看到“明天能否聊一下”，却不知道日程、双方关系和沟通习惯，模型也很难生成合适回应。需要的是支持当前判断的资料，不能单纯追求更长或更短。

作者提到，自己在 2024 年使用 Kimi 做观点聚类时，输入增加后出现遗漏、重复等问题。这是特定模型与任务下的使用观察，不能据此为当前模型设定统一的 32K 或 100K 有效窗口阈值。

文章引用的几类失败，更适合当作诊断提示：错误内容进入历史后被继续使用，无关旧任务拖住当前回答，多余工具描述影响选择，以及互相冲突的信息没有被澄清。它们都可能发生在窗口尚未耗尽时，因此容量检查不能替代输入质量检查。

## Write：先决定哪些状态值得保存

写入上下文在这里指把信息保存在当前窗口之外。原文区分长期记忆、scratchpad 和工作流 state：长期记忆供未来会话使用，scratchpad 记录当前任务的草稿与计划，state 则保存工作流需要的结构化中间变量。

例如，计划写进 `todo.md` 后，可以随任务调整，在需要时重新读取；一个 `todo` 状态变量也可以由不同步骤更新，而不是每次都重复放进 messages。存储载体不决定价值，关键是保存的内容是否足以支持下一次继续工作。

这要求保留信息的语义。已经验证的结果、尚待检验的猜测、用户明确约束和临时尝试，不宜都写成同一种“事实”。原文强调保存有用信息；从工程上延伸，还需要来源、时间和状态，防止临时判断在后续被当作稳定规则。

## Select：把相关资料与能力放进当前窗口

保存以后，系统要决定何时取回什么。原文把知识检索、记忆召回和工具选择放在这一类，因为它们最终都改变当前模型能看到的信息。

工具描述也是上下文。文章举了不同工具同用 `date` 参数名，却要求不同日期格式的例子。工具很多且语义相近时，模型可能混淆参数约定。按任务选择相关工具，配合清楚的命名与说明，可以减少这类干扰。

但筛选也有召回风险：如果把必要工具过滤掉，模型就可能只能猜测或寻找替代路径。因此，选择策略不仅要减少 token，还要检查关键资料与能力有没有保留。固定取前几个候选只是实现选择，数量本身并不构成质量保证。

同样，历史偏好应按当前任务使用。找到一条相关记忆后，还需要判断它是否仍然有效、是否被新要求覆盖。检索相似并不自动意味着应该执行。

## Compress：缩小表示，同时保留继续工作的条件

当历史越来越长，系统可以总结或裁剪。总结把多轮过程变成较短描述；裁剪则删除无关内容或只保留相关片段。两者都需要回答“下一步究竟依赖什么”。

原文以 Claude Code 的自动 compact 说明这一方向，但具体触发阈值属于历史版本行为，本文不将其作为通用参数。更值得检查的是压缩后的任务状态：当前目标、已完成的变化、失败证据和未解决约束是否仍然清楚。

压缩率高，可能只是丢掉了难以概括的细节。一个可用的设计是给摘要保留回查入口，让后续发现疑点时能定位原始资料。这是根据四分法提出的应用建议；它也把压缩与前面的 Write、Select 连起来，避免所有信息都只能从摘要恢复。

## Isolate：按职责分配信息，并保留交接证据

隔离可以发生在 state 字段、代码执行环境或不同 Agent 的窗口中。原文讨论了把一串操作放进程序执行，只返回必要结果，以及让搜索、回答、评估 Agent 各自获得任务所需输入。

其中有一条需要按评价目标补充条件。若 judge 只检查表达是否清楚、结构是否完整，答案与标准可能已经够用；若它要检查事实准确性，就仍然需要来源证据。不能为了隔离搜索过程，把完成验证所必需的资料也一并移走。

子 Agent 返回以后，负责人还要知道结论怎样得到、有什么限制，以及是否改变整体计划。隔离减少了局部干扰，也会丢失隐含决策。跨模块实现、统一文风或共享产品设计，对共同状态的要求通常比独立资料搜集更高。

这也是原文讨论单 Agent 与多 Agent 时值得保留的边界。作者偏向强主 Agent 配合少量承担广度探索的子 Agent，但将其作为预测。实际选择仍应看任务能否独立拆分、交接是否清楚，以及增加的协调成本是否值得。

四种动作可以沿一次任务串联理解：有用状态先写下来，当前步骤选择相关部分，历史过长时压缩，独立工作隔离执行，再把结果写回。评估这条链时，应同时看任务质量、成本和可恢复性，检查信息在哪一步丢失或失真，而不只观察窗口用了多少。
