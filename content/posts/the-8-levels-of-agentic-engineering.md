同一款模型进入不同团队，可能产生不同的开发效率。除了模型能力，结果还取决于它能读到哪些项目知识、能否验证修改，以及产出的代码怎样进入团队交付流程。

Bassim Eledath 在 [The 8 Levels of Agentic Engineering](https://www.bassimeledath.com/blog/levels-of-agentic-engineering) 中，将自己观察到的实践归纳为八个层级。作者也说明，这个顺序并不严格。它是个人经验框架，没有提供统一的成熟度测量或因果实验，更适合用来检查工作流缺了什么。

## 八级分别增加哪一种能力

| 层级 | 主要变化 | 需要回答的问题 |
| --- | --- | --- |
| 1. Tab Complete | 接受局部代码补全 | 开发者如何表达待补结构？ |
| 2. Agent IDE | 围绕代码库对话并修改文件 | 模型看到了哪些相关代码？ |
| 3. Context Engineering | 管理规则、历史和工具信息 | 当前步骤需要什么输入？ |
| 4. Compounding Engineering | 将审查经验沉淀回项目 | 下次怎样避免重复犯错？ |
| 5. MCP 与 Skills | 接入外部能力和可复用流程 | Agent 能执行并验证哪些工作？ |
| 6. Harness Engineering | 建立环境约束和反馈循环 | 失败能否被发现并纠正？ |
| 7. Background Agents | 异步执行，协调多个任务 | 没有人盯着时如何推进与上报？ |
| 8. Autonomous Agent Teams | Agent 直接协调任务与依赖 | 并行工作如何避免冲突和停滞？ |

这些层级没有统一的技术门槛。例如，一个团队可以很早使用 Skills，也可以在单 Agent 阶段就建立充分测试。表格的作用是区分需要建设的能力，而非给产品或工程师排名。

## 从一次纠正到可复用的项目知识

作者用 plan、delegate、assess、codify 描述经验沉淀循环：明确任务、委派执行、检查结果，再把有价值的发现写回规则或文档。最后一步决定一次纠正能否影响以后的会话。

原文举例，模型可能重新引入昨天已经移除的依赖。如果新的会话没有看到移除原因，它无法仅凭过去被纠正过，就知道这是一项持续约束。把决策依据保存到可发现的项目资料里，才能为下一次选择提供输入。

但规则文件不能无限膨胀。作者建议把可复用知识分散到结构清楚、保持更新的文档中，让简洁的入口指向它们。这里需要同时处理“保存”与“发现”：有文档却找不到，和根本没记录，都会使 Agent 重走旧路。

Skills 在此基础上保存可重复执行的程序性知识。原文中的团队审查 Skill 会按 PR 特征调度不同检查，包括数据库集成、复杂度和提示格式，并运行 lint。它表达的是审查流程，而不是把每条历史意见都复制进系统提示。共享 Skill 还需要版本、审查和维护，否则多人复用也会放大过时规则。

## 自动化上限取决于反馈是否可用

Harness 这一层把注意力转向工作环境。作者称自动化反馈为 backpressure，包括类型检查、测试、lint、预提交检查等。模型修改以后，可以依据外部结果继续修正，而不必等待人逐次指出错误。

原文提供了一个具体实践：作者的团队开发语音与聊天排障 Agent，并通过自建 `converse` CLI 与后端进行逐轮对话。编码 Agent 改完实现后调用它，检查对话是否遵守规定流程、是否在应转人工时调用相应工具，再继续迭代。这里的反馈直接覆盖产品行为，比只看源代码更接近验收目标。

反馈也有覆盖边界。测试只验证已表达的条件，模型自述“全部完成”不能替代检查。作者因此强调把实现者与审查者分开，使用另一模型或独立会话检查产物。这可以减少沿用实现阶段假设的倾向，但并不保证两个模型不会共享同一种盲点。

环境权限则限制出错后的动作范围。原文把 Agent、生成代码和秘密信息的隔离放进同一讨论：可靠性既需要告诉系统什么算正确，也需要限定它能影响什么。

## 后台执行会把瓶颈移到协调与验收

后台 Agent 的特点，是任务可以在用户离开交互界面后继续推进。作者讨论了本地调度与云端隔离环境：前者便于快速反馈和调试，后者适合长时间运行，但增加环境准备、快照与安全管理的成本。

任务多了以后，人可能把节省的编码时间花在分派、追踪和检查上。作者自建的 Dispatch 用负责人会话协调独立上下文中的执行者，执行者受阻时返回澄清请求。分离上下文能减少负责人窗口里的执行细节，也要求返回材料足以支持审查。

到了第八级，Agent 开始直接领取任务、交换发现和处理依赖。原文同时报告了这类实验中的协调困难：缺少层级可能停滞，缺少 CI 容易破坏已有功能。作者明确认为这一层仍在探索，对多数日常工作更愿意投入第七级。

因此，阅读这张层级表时，最有用的落点是当前瓶颈。如果 Agent 反复误解项目，先完善知识入口；如果无法判断修改是否成功，先补反馈；如果结果积压在审查环节，就改善验收与交接。增加更多执行者之前，先让一个任务具备明确输入、完成证据和失败出口，收益更容易判断。
