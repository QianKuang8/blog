同一项能力，可以做成一个工具、多个小工具、一段提示，或者让模型通过 shell 自己组合。人类工程师觉得简洁的接口，模型未必容易使用；工具能执行，也不代表模型会在正确时机选中它。

Thariq Shihipar 的 [Seeing like an Agent](https://x.com/trq212/status/2027463795355095314) 通过 Claude Code 的几个演进案例讨论 action space，即模型可选择的动作集合。作者没有提出固定工具数量或通用协议，而是主张阅读模型输出、观察实际失败，再调整接口。以下机制均按原文所述阶段理解。

## 提问应该是一个明确的动作

团队设计 AskUserQuestion，最初想降低用户回答澄清问题的负担。纯文本可以问问题，却不容易稳定提供可选择的选项，回答起来也较慢。

第一版把问题数组加入 ExitPlanTool，让模型提交计划时同时提问。它在实现上简单，却混合了两个阶段：计划已经提交，相关问题又尚未回答。如果答案改变计划，模型是否应该再次退出计划？原文报告这种语义让 Claude 困惑。

第二版约定一种 Markdown 格式，再由系统解析成界面。它更通用，但模型有时追加句子、遗漏选项或改变格式。自然语言响应仍然可以理解，界面所需的结构却不够稳定。

最终方案是独立 AskUserQuestion。工具调用提供结构化问题与选项，界面显示弹窗，Agent 循环等待用户回答后再继续。它可以在需要时调用，团队尤其在计划阶段引导使用。这个边界把“获取尚缺的信息”从“提交已有计划”里分离出来，也让 SDK 和 Skills 能复用同一动作。

原文强调，工具设计还需要模型愿意且能够调用。结构化 schema 提供约束，但好的命名或完备参数，并不能单独保证正确使用；实际调用轨迹仍是验证入口。

## Todo 与 Task 服务于不同协作需要

Claude Code 早期用 TodoWrite 保存并显示待办，还每五轮插入一次系统提醒，帮助模型维持目标。随着模型能力提升，提醒反而可能让它认为必须遵守旧清单，不能调整计划。

与此同时，子 Agent 使用增加，单份待办需要承载的不再只是“我接下来做什么”，还包括“谁在做什么”“哪些任务等待其他结果”。团队因此用 Task 工具取代 TodoWrite，支持依赖、跨子 Agent 状态更新，以及修改和删除任务。

这个变化说明，旧工具可能继续正常工作，却已经不再匹配主要问题。单 Agent 防遗忘与多 Agent 协调，都可以显示为列表，底层所需的状态语义却不同。只把旧清单做得更详细，未必能补足协作能力。

## 搜索接口把部分上下文选择交给模型

原文还回顾了代码搜索：早期 RAG 向量索引速度快，但需要构建、配置，并可能在不同环境中脆弱。后来团队给 Claude 提供 Grep，让它搜索当前代码并逐步建立上下文。

这一转变的前提，是模型已经更善于决定下一步查什么。若模型缺少导航能力，只减少预先提供的信息，可能让它找不到关键代码。作者因此强调工具应适配所支持模型的能力，而不是把某种搜索方式当作永久最优解。

Skills 将类似思路扩展为 progressive disclosure，即渐进披露。先给发现入口，模型读取 Skill 文件后，再沿引用读取其他资料。一个 Skill 还可以说明怎样调用 API 或查询数据库，从而增加能力，而不一定新增一个常驻工具。

这里需要保持发现链可走通：入口说明用途，文件给出具体方法，方法能到达实际资料。仅把知识挪到外部，如果模型不知道它存在，就只是减少了可用信息。

## Guide 子 Agent 解决了搜索过程的隔离

团队发现，Claude 对自身产品的配置知识不足。如果把所有说明放进系统提示，会让不相关任务长期承担额外上下文；只给文档链接，模型又可能为回答一个问题把大量搜索结果带回主会话。

原文介绍的 Claude Code Guide 子 Agent 接收这类问题，在自己的上下文里搜索文档，并按专门指令返回所需信息。这样既保留可发现的知识入口，也把检索过程与主任务隔开。作者同时承认，它仍会在某些配置问题上困惑，没有把这一方案描述为完全解决。

这个案例与 AskUserQuestion 的方向不同。前者通过独立工具澄清动作语义，Guide 则借助已有子 Agent 机制组织工作，没有新增同等数量的专用工具。是否加工具，要看当前缺的是一个明确动作，还是已有动作之上的知识与流程。

## 用失败轨迹检验工具边界

这几个案例可以转成一组具体检查：模型是否在计划前得到必要信息，是否把旧待办误当不可改的约束，能否找到需要的材料，以及搜索结果是否挤占主任务上下文。

接口调整后，再观察同类任务中的调用选择、参数质量和结果。模型升级也需要重新做这项检查：原本帮助它保持方向的提醒，可能限制新能力；原本必须常驻的知识，可能已经可以按需发现。

工具设计由此成为持续实验。保持动作含义清楚，给知识留出发现路径，并让共享状态能支持协作，比单纯追求更少或更多工具更能解释系统为何有效。
