团队纠正了一次 Agent 的评审意见，下一个 PR 里，同类问题仍可能出现。对使用者来说，纠正已经发生；对下一次任务来说，那条意见却未必进入了它能读取的知识。怎样把一次反馈变成以后都能使用的工作方法，是持续使用 Agent 时绕不开的问题。

Anthropic 在 [How Warp builds self-improving agents on Claude](https://claude.com/blog/how-warp-builds-self-improving-agents-on-claude) 中介绍了 Warp 的做法：用一个 Skill 执行领域任务，再用另一个 Skill 定期归纳反馈、提出修改，经人审核后更新前者。本文讨论的“自我改进”发生在这些指令文件和工作流程中。

## 两条流程，各自交付什么

Warp 把领域知识放在基础 Skill，也就是原文的 inner/base skill 中；另一个 improver skill 负责观察任务结果和人的回应。前者随任务事件触发，后者定时运行：

| 阶段 | 输入 | 产物 |
| --- | --- | --- |
| 任务执行 | 任务与领域 Skill | 评审或分类 |
| 方法改进 | 反馈与旧 Skill | 修改 PR |
| 人工审核 | 修改及反馈依据 | 合并决定 |

改进者对照原有行为与反馈，提出聚焦某个问题的修改；合并后，后续任务再使用新版 Skill。这样拆分带来的一个工程性质是：执行者可以完成眼前的工作，方法更新则拥有单独的审查入口。反馈出现、修改提出、规则生效，成为可以分别检查的状态。把它们都称为“Agent 学会了”，会掩盖系统究竟走到了哪一步。

文件也让改进对象变得具体。审查者可以看到哪句话变了、适用条件是否扩大、它和既有规则是否冲突。根据这个设计，可以进一步要求每次修改保留反馈来源与旧版本，便于日后解释行为变化；这是落地时可补充的版本管理约定。

## 一个标签，暴露了判断条件的缺口

原文用 Issue 分类展示了完整过程。Agent 漏打了 `ready to spec` 标签，维护者在 Issue 下说明预期及原因。定时运行的改进 Agent 收集反馈，提出 Skill 修改：当 Issue 描述了真实问题，即使 UI 或 UX 细节尚未确定，也可以进入规格设计阶段。修改经人工审核合并，后续运行再使用新版 Skill。

这个案例值得拆开看。漏打标签是输出偏差，维护者解释的是进入下一阶段所需的条件。若只修正当前 Issue，后续任务仍缺少判断依据；将条件写进 Skill，才有机会影响同类输入。

由此可以推导出一种更有用的反馈格式：指出当前结果、说明期望结果，再解释两者之间的判断理由。这里的理由尤其关键，它帮助改进者判断，哪些条件应当保留，哪些只是这次任务的偶然细节。

例如，对这一规则做后续验证时，可以同时准备“问题明确、方案未定”和“只有模糊愿望、问题尚未明确”的样例。这是根据案例提出的测试思路，原文没有展示这组测试。它检验的是改动的适用边界，避免把纠正漏标扩大成过度打标。

## 反馈如何成为可复用的方法

从一次纠正到通用指令，中间有一次概括。概括过窄，Skill 只记住某个 Issue；概括过宽，未来遇到不同情形也会套用相同结论。改进 Agent 的难点正在这里：需要找出真正影响判断的条件。

因此，一份可审查的修改说明最好能回答三个问题：哪条反馈揭示了缺口？这次修改影响哪类任务？什么情况下仍不适用？这些问题构成本文建议的审查尺度，不能据此假定 Warp 已实现对应的自动检查。

同样需要注意反馈的身份。代码评审中的一句建议可能代表仓库约定，也可能只是某位贡献者的偏好。若缺少范围说明，局部偏好会随着 Skill 分发成为默认要求。改进流程应保留原任务上下文，让审核者有条件判断这条经验应该适用于整个仓库、某个模块，还是仅限当前任务。

持续维护时，还要关注指令之间的关系。新反馈可能补充旧规则，也可能说明旧规则已经失效。只在文件末尾追加句子，会把冲突留给下一次执行者处理。更合理的审查对象是修改后的整体判断条件，包括被替换或删除的内容。

## 合并成功以后，仍要检查任务结果

原文提供了流程与案例，没有给出改进前后的准确率、误报率或对照实验。因此，可以据此理解反馈怎样进入下一版 Skill，尚不能量化判断这套机制带来了多少质量提升。

对准备采用这一做法的团队，可以把验收分成两个问题。首先，修改是否准确表达了已认可的反馈？其次，新版执行者在其他任务上是否表现更好？前者可以通过审阅文件回答，后者需要运行样例、检查输出。

一个小规模试点可以先保存旧版 Skill 在一组任务上的结果，再用新版重跑。除导致此次修改的失败样例外，也应保留原本正确的样例和边界样例。对评审 Agent，还应同时看有用意见是否增加、无效意见是否减少，避免通过减少输出获得表面上的“低噪声”。这些是本文提出的验证建议，并非原文报告的实验。

## 把方法更新纳入日常维护

Warp 这个案例提供了一个可以讨论和审查的改进单位：一份有反馈依据的 Skill diff。它让团队可以从小范围任务开始，明确谁提供判断、谁提出修改、谁决定生效，再观察后续执行结果。

沿着这条思路，采用时值得先选那些重复发生、结果容易检查、团队已有明确约定的任务。每次只处理一个清楚的判断缺口，既便于审核，也便于在效果不佳时定位原因。
