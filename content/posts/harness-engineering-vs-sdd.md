Agent 有能力读写代码、运行测试，仍可能把跨服务约定实现错。它能看到调用接口，却可能不知道某个错误码代表可以重试、需要降级，还是应该立即终止。执行工具再齐备，也补不上缺失的业务含义。

何艺萍的 [《Harness Engineering 来了，SDD 还有意义吗？》](https://mp.weixin.qq.com/s/Laz4W0180y9yGW0b6EpUMQ) 以此讨论两类工作：Harness 建设执行环境和反馈机制，Spec-Driven Development（SDD，规范驱动开发）组织意图、契约与行为定义。本文解读的是作者基于公开材料与个人实践形成的分析，其中转述的外部实验不视为本文独立核验结果。

## 错误码案例缺少的是共享语义

原文作者报告过一个案例：服务 A 定义了错误码含义，负责服务 B 的 Agent 没有拿到跨服务约定，于是自行选择处理方式；补充系统级错误码契约后，同一 Agent 的实现通过验证。

这一案例说明，代码事实和需求语义提供不同信息。读代码能知道当前分支怎样运行，契约则说明各方应该怎样理解这个结果。两者冲突时，要先确定哪个是目标行为，再决定改代码还是改规范。

这个案例支持的是一个具体判断：缺少契约会造成错误。补上文档之后，Agent 仍可能漏读、误解或执行出错，这些问题要靠工具、测试和执行轨迹一起定位。

## Spec 要能导航，也要能成为检查依据

文章将 Spec 分成几个作用：帮助 Agent 找到相关知识，提供接口和行为语义，以及给反馈循环提供正确性判据。它们可以对应到不同材料，而不必塞进同一份巨大指令文件。

系统概览说明服务职责与边界，接口契约说明字段、状态和错误语义，行为场景说明在某个条件下应得到什么结果。Agent 从较短入口进入，再沿指针读取当前任务所需内容。这样既保留全局方向，也避免每轮加载大量无关细节。

验收场景还应能与实际检查连接。例如，契约约定某类错误需要重试，就要有办法构造该响应并观察后续行为。写进文档的规则，要有实现和验证与之对应，Spec 才能参与任务验收。

原文把 linter 与语义约束作了区分。更准确地说：普通的格式规则判断不了业务语义，但明确的语义可以编码成契约测试或专用检查。文字说明与确定性验证有机会相互补充。

## 入口文件保持短，深层材料按职责维护

原文引用“地图而非百科全书”的组织思路，建议 `AGENTS.md` 负责导航和行动入口，产品规范、设计文档与执行计划各自承担不同粒度的信息。

这种拆分的价值在于减少重复事实。若同一个字段含义同时复制到多份文件，改动时就容易出现几个版本。入口可以指向定义所在的位置，执行计划引用已有契约，再补充本次实现与验证步骤。

本文据此理解，Spec 的质量不宜用篇幅衡量。清楚的适用范围、可定位的定义、未决问题和验收方式，比把所有可能细节写进一个文件更有助于执行。尚未确定的行为也应显式保留歧义，避免被 Agent 当成已达成共识的要求。

## 规范也会过时，需要与代码一起检查

文章指出 Spec 漂移往往没有明显报错：代码已经演进，文档仍标为有效，下一次任务于是基于旧约定展开。作者提出按 Draft、Active、Deprecated 等状态管理规范，并讨论对照接口、Schema 和配置的主动一致性检测。

这里应区分已提出的方向和已经建立的能力。自动扫描可以发现部分结构差异；一次语义变化是缺陷还是有意的契约修改，要由人确认目标，再同步规范和验证。

代码审查发现问题后，也可以检查上游材料是否缺少对应约束。若是需求遗漏，应补充契约；若规范正确但实现违反它，则应修复实现或执行流程。按原因分别处理，才能避免把每次失败都变成不断膨胀的文档。

Harness 与 SDD 的关系最终落在这一执行链上：任务能找到相关定义，工具能够实现与观察行为，验证能够指出偏差，修复再回到正确层级。它们配合得好，才有机会减少下一次重复解释和返工。
