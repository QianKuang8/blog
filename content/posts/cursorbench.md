两个模型在公开榜单上分数接近，放进同一个编辑器后，却可能表现出明显差异：一个经常需要追问和修正，另一个能更快找到相关文件。这时需要检查评测任务是否覆盖了实际工作，以及评分有没有遗漏交互成本。

Cursor 的 [《How we compare model quality in Cursor》](https://cursor.com/en-US/blog/cursorbench) 介绍了一套线上与离线结合的评估方法。离线部分 CursorBench 取材于 Cursor 工程团队的真实会话；线上部分通过受控实验检查改动对开发者的影响。二者分别承担可比较实验和现实校验。

## 用请求与提交建立任务对应关系

CursorBench 通过 Cursor Blame 把已提交代码追溯到产生它的 Agent 请求，由此取得用户描述与最终解决方案的对应关系。许多任务来自内部代码库和受控来源，降低了模型训练中已经见过题目的风险。原文说评测集每隔几个月更新，以跟随使用方式变化。

这种采样保留了真实请求的一项特征：描述短，常常省略开发者认为显而易见的背景。模型需要依据代码库补充理解，而不是只按详尽题面实现一个孤立功能。原文还纳入了 monorepo 多工作区、生产日志调查和长时间实验等任务。

不过，最终提交只能作为一个已采用方案，不能自动成为唯一正确答案。同一个请求可能有多种合理实现。任务来源贴近产品，也意味着分布更贴近 Cursor 自己的工程实践；它对所有团队是否同样有代表性，还需要各自的数据验证。

## 更真实的任务要求更灵活的评分

作者认为，一些公开评测集中于 bug fix 或解谜式任务，与产品中的工作分布不一致；另一些评分只接受狭窄解法，会惩罚合理替代方案。CursorBench 为简短、可能存在歧义的任务使用 agentic grader，而没有要求输出逐行复现参考补丁。

这里多了一层需要校验的判断。自动评分器可以检查更开放的结果，但它仍可能误解需求、漏掉缺陷，或偏好某种代码风格。因此，不能因为任务来自真实会话，就认为分数天然代表用户满意度。

文章说明完整评测同时关注正确性、代码质量、效率和交互行为，而公开展示重点是解决方案正确性，并用完成 token 数描述计算与延迟的取舍。正确率相同的方案，若频繁重复搜索或产生大量输出，使用体验仍可能不同；单张正确性图表无法覆盖全部维度。

## 线上实验检查离线评测遗漏了什么

Cursor 在线上汇总多项交互和输出质量信号，观察它们是否一致变化。原文没有公开这些代理指标的完整定义，因此读者能理解设计方向，却不能仅凭文章复现全部评估协议。

一个具体例子是语义搜索消融：团队在受控实验中完全移除语义搜索工具，观察哪些场景受到影响。结果帮助他们识别该能力对大型代码库问答的作用。这个实验针对的是工具对系统结果的贡献，不能简单归因为底层模型能力变化。

线上结果也能反过来暴露离线任务的盲点。如果某次改动提高了 grader 分数，开发者相关指标却下降，就需要调查任务分布、评分标准或执行行为之间的差异。离线评测负责让比较更快、更可控，线上实验负责检验这些比较是否仍对产品有用。

## 任务变长以后，复现成本也会增长

原文报告，从初版到 CursorBench-3，任务涉及的代码行数和平均文件数大致翻倍。行数只能粗略描述范围，不能独立衡量难度；但它反映了团队在增加需要协调多处状态的任务。

当时这些任务仍在单次会话内完成。文章将更长期、使用外部服务的 Agent 工作列为下一阶段，并明确提出评分成本与可复现性问题：外部状态变化后，同一个请求未必面对相同环境，比较结果也就更难解释。

对于自建评测，值得借鉴的顺序是先保留真实请求与可检查的结果，再确认任务能否重放、评分能否接受合理替代方案，最后用线上结果校验它。公开 benchmark 仍可用于共同基线；内部评测则需要持续回答，它究竟覆盖了自己的哪一部分工作。
