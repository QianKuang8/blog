改了一条提示，Agent 的任务成功率提高了，怎样判断这个变化值得上线？它可能确实更会解决问题，也可能只是这次运行更顺利，或者更容易满足评分器的偏好。要让分数支持工程决策，需要知道它来自什么任务、怎样执行、依据什么证据判分。

Anthropic 在 2026 年 1 月 9 日发布的 [《Demystifying evals for AI agents》](https://www.anthropic.com/research/demystifying-evals-for-ai-agents)，把这些问题放进同一套评估框架。本文重点讨论三个相互关联的条件：验证任务结果、校准评分逻辑，以及解释重复运行的波动。

## 被测对象包括模型与 Harness

单轮问答可以直接对回答评分。Agent 会调用工具、修改文件或数据库，并根据中间结果继续行动；最终回复只保留了这一过程的一部分信息。原文用订票说明区别：Agent 说“订好了”属于执行记录，数据库里确实存在预订才是任务结果。

因此，一个评估任务需要明确输入与成功条件；每次执行称为一次 trial，同一任务可以反复执行。每次 trial 都留下完整执行记录，也就是 transcript 或 trajectory，并产生最终环境状态 outcome。评分器可以检查记录，也可以检查结果，两者承担不同职责。

*图 1：原图，来源：[Anthropic](https://www.anthropic.com/research/demystifying-evals-for-ai-agents)。左侧组织任务、评分规则与重复执行，右侧是被调用的 Agent Harness；底部将最终状态与执行轨迹交给评分器。点击可查看完整图。*

图中两种 harness 也要区分。Agent Harness 负责让模型使用工具、接收反馈并推进任务；Evaluation Harness 负责准备环境、运行试验、收集记录和汇总评分。原文强调，被评估的 Agent 包含模型与 Agent Harness 的共同作用。

这意味着，更换工具接口、调整上下文或改变执行预算，都可能改变结果。若比较时同时改了模型和这些配置，分数反映的是整组改动。我的理解是，评估报告应保留这些条件，才能让后续的提升归因与失败复查有据可依。

## 评分器需要接受有效的替代解法

原文把评分器分为程序、模型和人工三类。选择依据是需要判断的证据：测试结果、数据库记录适合程序检查；交互质量、研究报告的完整性等开放维度，需要更灵活的判断。

| 评分方式 | 适合检查什么 | 需要防止什么 |
| --- | --- | --- |
| 程序评分 | 测试是否通过、状态是否正确、约束是否满足 | 把固定字符串或实现路径当成唯一答案 |
| 模型评分 | 代码质量、表达清晰度、论述是否有依据 | 标准含糊、判断波动、证据不足时仍下结论 |
| 人工评分 | 专业领域判断、开放任务验收、评分器校准 | 成本过高、不同评审者理解不一致 |

对 coding agent，单元测试通常是正确性验证的基础，模型评分可以补充代码质量。研究 Agent 则需要分别关注论点能否由来源支持、关键事实是否覆盖，以及来源本身是否可靠。一个总分很难解释这些维度分别出了什么问题。

评分器越具体，也越需要检查它有没有额外添加题面未声明的要求。原文提到一种 Terminal-Bench 审计中发现的问题：任务要求写脚本，却没有规定文件路径，测试仍只在固定路径找文件。这样的失败暴露了任务与评分之间的不一致。

同样，强制要求一套工具调用顺序，会把许多有效解法排除在外。更稳妥的起点是检查产物与最终状态；只有某个中间动作本身属于任务要求时，再对动作设置约束。例如必须完成身份核验，不能仅因最终退款状态正确就视为全部合格。[行为评估的另一篇解读]({{< relref "/posts/harness-engineering-behavioral-evaluations.md" >}})进一步讨论了这类动作证据的边界。

模型评分的灵活性也有成本。原文建议用清晰的 rubric，也就是分维度的评分标准，与专家判断反复校准，并允许评分器在信息不足时回答 Unknown。执行记录值得人工抽查，因为一次低分既可能来自 Agent 错误，也可能来自评分器拒绝了正确方案。

## 能找到一次答案，与反复可靠是两种要求

Agent 在相同任务上重复运行，结果可能变化。原文用两个指标区分不同产品目标：`pass@k` 关注 k 次尝试里至少一次成功的概率，`pass^k` 关注 k 次尝试全部成功的概率。

为了说明二者差异，假设同一个任务每次成功的概率固定为 p，各次试验相互独立，那么：

- 至少一次成功：`pass@k = 1 − (1 − p)^k`。
- 全部成功：`pass^k = p^k`。

按原文正文使用的 p = 75% 算例，三次尝试中至少成功一次约为 98.4%，三次全部成功约为 42.2%。下面按这一假设绘制曲线，展示同一基础成功率如何随指标定义呈现不同趋势。

![固定单次成功率为百分之七十五时，至少一次成功的概率随尝试次数增加而上升，全部成功的概率则下降；三次时分别为百分之九十八点四和百分之四十二点二。](/images/demystifying-evals-for-ai-agents/repeated-trial-probabilities.png)

*图 2：本文绘制，依据[原文](https://www.anthropic.com/research/demystifying-evals-for-ai-agents)对两类指标的定义，按固定 p = 75%、各次试验相互独立计算。横轴为试验次数，纵轴为对应事件的概率；这是数学示例，不是模型实测结果。*

如果用户可以低成本重试，并且系统能够识别哪个结果正确，至少一次成功有参考价值；面向用户反复执行的任务，则更需要关注一致性。由此还可以推导出一个工程前提：产生了一个正确候选，不代表产品已经选中了它，候选识别也需要可靠的验证手段。

上述公式用于解释指标。原文已经提醒，不同任务各有自己的成功率；这意味着，不能直接把整套任务的平均成功率代入公式，用总体平均值代替每道题的 p，会掩盖任务难度差异。若试验共享缓存、残留文件或资源瓶颈，相互独立的假设也不成立。

因此，增加运行次数之前要先隔离环境。原文提到，Agent 曾通过查看前次试验留下的 Git 历史获得优势；另一方面，共同的资源不足也可能制造一批相关失败。两者都会让分数偏离实际要测量的能力。

## 从真实失败建立可维护的评估闭环

原文建议尽早从 20–50 个真实失败任务开始。这个规模适合早期识别明显变化；当系统成熟、改动收益变小时，通常需要更多、更有区分度的任务。小套件的价值在于尽快明确成功条件，并让反复出现的失败能够重放。

建立这类套件时，可以依次确认四件事：

1. **任务是否明确且可解。** 准备能通过评分的参考解，检查题面是否包含所有验收要求。
2. **样本是否覆盖行为的两面。** 既检查该搜索时有没有搜索，也检查不需要搜索时是否过度调用。
3. **运行是否可比。** 环境从干净状态开始，保留被测配置、执行记录、评分依据与成本指标。
4. **失败能否得到解释。** 抽查轨迹，区分任务缺陷、环境问题、评分错误与 Agent 自身失误。

长期维护还要区分能力评估与回归评估。前者保留尚未做好的任务，用于寻找改进方向；后者保护已经稳定完成的任务，期望接近全通过。能力任务被解决后，可以进入回归套件，同时补入新的挑战。否则，高分只说明旧题已经熟练，无法继续揭示进步。

这些离线检查仍需要与生产监控、用户反馈和人工评审配合。任务分布会变，评分标准也可能落后于实际需求。[CursorBench 的解读]({{< relref "/posts/cursorbench.md" >}})提供了一个具体参照：从真实开发会话取样，再用线上实验检查离线分数是否对应体验改善。

对工程团队而言，一次评估应能帮助回答：哪里变好了，哪些既有行为仍然可靠，以及下一次失败该从哪份证据查起。只有这些问题可以追溯，分数才能持续支持迭代。
