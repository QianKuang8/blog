Agent 已经写出完整方案，读者却很难快速比较选项或指出要改哪里。输出文件的格式会影响这段协作。Thariq Shihipar 在 [《The Unreasonable Effectiveness of HTML》](https://claude.com/blog/using-claude-code-the-unreasonable-effectiveness-of-html) 中介绍了自己的做法：让 Claude Code 生成 HTML，用布局、图示和交互承接复杂内容。

这是一份团队成员的实践分享。作者越来越偏好 HTML，不等于 Markdown 已经失去价值；值得分析的是，什么任务会从额外的表达能力中受益，以及产物如何回到后续工作。

## 让读者看清关系，而不只是增加内容

原文从一个阅读问题出发：模型能写越来越长的 spec 和 plan，但作者发现自己和同事很难认真阅读超过百行的 Markdown。这里的百行是个人体验，没有构成普遍的阅读阈值。

HTML 给出的额外空间，是把不同关系直接表达出来。CSS 可以并排放置多个方案，SVG 可以连接状态或数据流，导航和折叠可以控制读者一次看到多少信息。Markdown 也能表达表格、链接和图片；差别在于复杂布局和交互是否需要额外的呈现层。

例如，原文建议把六种 onboarding 方案放在同一页面比较，并标明各自的取舍。对这类任务，读者需要在不同方案之间来回查看；并排布局可能比六段顺序描述更容易保持比较维度。但如果问题只需要一个命令或一段说明，页面布局也可能成为额外负担。

因此，评价输出格式时，应先看读者要完成什么动作：阅读一条结论、理解一段机制、比较多个方案，还是修改一个参数。内容组织决定了页面要承担的工作，HTML 提供实现它的手段。

## 交互结果需要能导出

原文更有特点的用法，是为一次任务生成临时编辑界面。比如把 30 个 Linear ticket 放进可拖拽的栏目，调整按钮动画参数，或在左右分栏中编辑 prompt 并预览样例输入。

这些例子的共同过程是：Agent 整理初始数据，人在界面里作选择，再把选择导出成 JSON、Markdown、参数或新的 prompt，交回 Agent。导出让操作成为明确输入；只有一张可以拖动却不能取回结果的页面，协作仍会停在中间。

由此可以提出三项检查：导出内容是否反映页面的最终状态，字段是否足以让下一步继续，以及 Agent 是否理解哪些选项已被确认。这些是根据原文用例整理的验收问题，不能假定所有生成页面都已经实现。

## 产物可以串起探索、实现与验证

作者描述的规划过程从多个方案开始，再扩展其中一个，加入 mockup、数据流和代码片段，最后形成实施计划。进入新会话后，这些文件继续作为实现材料；验证者也可以读取它们，核对最终结果是否符合前面的选择。

HTML 在这里承担了持久的任务材料，而不只是一条聊天回复。它是否有用，取决于里面是否保存了必要的要求、取舍和验收依据。漂亮的版面不能弥补需求遗漏，生成的图也必须与文字和代码一致。

分享同样有条件。本地文件可以在浏览器打开，需要给别人访问时则另行托管。浏览器可读只解决呈现问题，文件包含的项目资料、访问权限和后续版本仍需按实际协作方式处理。

## 多出来的表达能力也有维护成本

作者估计 HTML 生成可能花费 Markdown 的 2—4 倍时间，并消耗更多 token；这个范围来自其体验，原文没有提供固定负载的对照实验。他同时提到，当时使用的 Opus 4.7 百万 token 窗口让额外用量更容易接受。这是特定环境下的取舍，不代表输出格式必须等到某个窗口规模才能使用。

版本控制是更持久的限制。样式、结构和正文一起变化时，HTML diff 会更难审阅；作者也越来越多地请模型修改文件。对需要长期手工维护的规范，Markdown 的简单结构仍有优势。选择格式时要把生成、阅读、修改和审查的成本放在一起看。

一个适合尝试的起点，是挑选本来就需要比较或调参的任务，明确页面应该帮助读者作出哪项决定，并要求导出结果。然后检查这项决定是否更容易形成、是否准确进入后续实现，再决定要不要扩大使用范围。
