一个助手能回答问题，并不意味着它能接下一个持续执行的业务任务。任务要跨系统、等待外部事件、处理失败，还可能在中途收到新的约束。这些要求会同时改变交互界面、执行架构与验收方式。

Zippland 的 [《2025 年 AI 产品及架构演进深度研究报告》](https://blog.zihanjian.com/article/2b69db82-fa86-80f4-abc2-f6a70258f7ad) 用这个变化串联了当年的 Agent 产品与技术。它是一篇覆盖面很广的二手综述，混合了产品案例、研究方向和作者预测。本文把它作为问题地图阅读，聚焦可以讨论的设计机制；其中“某架构已成为行业默认”“某产品形态全面衰退”等判断，不能仅凭这篇综述视为已经证实的共识。

## 交付目标改变后，人还负责什么

原文将 Copilot 与后台 Agent 的差异放在任务推进方式上：前者通常由用户持续提示，后者接受目标后异步执行，并在关键节点请求决策。这个区分有助于发现隐藏的人力成本。系统即使生成内容很快，如果人仍要搬运上下文、判断下一步、检查每个输出，业务流程的组织负担就未必降低。

后台执行把这项负担部分交给系统，也产生新的产品要求。用户需要看到任务目前处于什么状态、为什么停住、哪项操作等待批准，以及最终产物在哪里。对话仍可作为表达目标和补充约束的入口；当流程开始运行，时间线、任务状态与可操作的产物就承担更多信息。

综述讨论的影子模式提供了一个渐进路径：让 Agent 接收真实输入、生成候选处理结果，但先不执行关键操作，再由人或评估器审查。这种方式能够收集贴近实际任务的失败样本。不过，影子输出被认可只证明建议质量，真正接入业务后的权限、外部状态变化和执行失败，仍需要单独验证。

## 长链任务需要明确的检查与恢复位置

原文批评单体 ReAct 在长任务中的错误累积。它给出一个说明性计算：若十个步骤各有 95% 成功率，且假设步骤独立、每步都必须成功、没有重试，那么整体成功率约为 60%。这个数字说明假设下的累积效应，并不是对所有 ReAct 系统的实测结果。

更值得关注的是如何打断错误传播。综述介绍了规划、执行、验证的职责划分：规划器把目标变成子任务及验收条件；执行器获得相关输入并完成局部工作；验证器依据程序检查或模型判断，决定接受、返工或调整计划。它们可以由不同 Agent 承担，也可以表现为同一系统的几个明确阶段。

增加验证的前提，是验证结果确实提供新证据。如果几个角色共享同一个错误假设，只是互相确认，多次推理仍可能得出同样的错误。把测试结果、外部状态或可复核资料纳入检查，才更容易区分“实现看起来合理”和“目标已经达成”。这是从综述机制出发的工程推论。

原文还把额外搜索、候选比较和慢思考归入 test-time compute。这里的资源选择应连着任务条件看：复杂步骤可以分配更多预算，但预算增加后是否更可靠，要由任务结果验证，不能用推理长度替代正确性。

## 编排要保存可恢复的业务状态

当任务包含循环、等待和人工介入时，把全部状态藏在聊天历史里会增加恢复难度。原文介绍的图编排与事件驱动，分别帮助表达状态转移和外部触发：节点执行工作，条件边决定接下来去哪；事件则让系统在工具返回、审批完成或新信号到来时继续推进。

这类结构最有用的产物，是一个可以检查的任务状态。例如，系统能够区分“尚未执行”“已执行但结果待核对”和“失败后需要重试”。如果只有一句自然语言总结，恢复流程时就更难确定哪些操作已经发生。

多 Agent 会进一步增加交接要求。负责人需要定义子任务输入、返回格式和完成条件，执行者则要带回足以核对的结果。MCP、A2A 等协议在综述中分别承担工具连接和 Agent 协作的角色；协议可以统一信息交换方式，但任务是否适合拆分、谁能执行操作、返回结果是否可信，仍由应用设计承担。

## 记忆还要回答“这条信息何时成立”

长期任务不能只按文本相似度挑选历史。原文用项目状态变化说明问题：过去的“延期”与后来的“按时交付”都可能与当前问题高度相关，把它们并列送进模型，并没有自动回答哪个状态仍然有效。

综述借时序知识图谱讨论一种处理方式：记录实体、关系与有效时间，并区分事实发生时间和系统得知时间。新信息与旧关系冲突时，可以让旧关系失效，同时保留历史查询能力。检索结果于是能回答“当前状态是什么”和“当时已知什么”这两种不同问题。

这条思路的价值是把时效性变成显式数据。它不意味着所有 Agent 都需要图数据库。若任务只需近期文件与少量稳定偏好，更简单的版本、时间戳和来源管理可能已经足够。架构选择应由查询需求和实际错误决定，而不是把综述里的技术演进写成必经路线。

## 结果计费反过来要求结果可验收

原文把账号计费、消耗计费和结果计费放在同一条产品变化里。按消耗收费，需要解释调用量与成本；按结果收费，则必须先定义什么算成功、哪些异常不计入，以及多方参与时如何归因。

这会影响整个执行链：开始时要有目标，过程中保留状态与证据，结束时按照相同口径验收。否则，“关闭了一个工单”可能只是系统状态改变，并不能证明用户问题已解决。

因此，这份综述适合用来检查设计遗漏：任务能否被持续推进，关键动作能否检查与恢复，历史信息能否区分新旧，最终结果能否验收。至于是否需要多 Agent、图编排或复杂记忆，应从具体失败和约束出发逐项决定。把这些选择一并升级，既难以归因收益，也会增加新的协调成本。
