长期使用 Coding Agent，项目里往往会积累不少规则：遇到某类任务先读文档、执行前询问、修改后检查。每条规则都可能对应一次真实失败，但换了模型以后，这些规则是否仍然合适，需要重新判断。Eric Provencher 在 OpenAI 的 [《Rethinking skills and prompts for GPT-6 Astra》](https://developers.openai.com/blog/rethinking-skills-and-prompts-for-gpt-6-astra) 中提出了这个问题。

这篇文章可以作为一次指令审计的起点。下面先提炼原文的建议，再用一个假设的工程场景说明如何检查规则；具体的审计方法是本文的延伸分析。

## 原文提出了哪些调整

作者指出，Skill 的名称与描述会进入上下文；描述过长、数量过多时，Codex 会缩短描述，影响选择。触发范围过宽或互相冲突，还会引入无关指导。因此，描述要简短且明确，多流程 Skill 的入口应按需指向辅助材料。AGENTS.md 也应按任务关联文档，重新检查过细步骤与重复测试要求。针对 Astra 可能较早停下的情况，作者建议明确可继续执行的范围，以及任务何时算完成；仓库内共享的 Skill 还需考虑不同模型。[来源：原文建议](https://developers.openai.com/blog/rethinking-skills-and-prompts-for-gpt-6-astra)

这组建议覆盖了三个不同的工程问题：模型有没有选对方法，执行时拿到了哪些信息，什么时候可以交付。把它们分开，才能判断一条规则究竟应该删除、改写，还是移动到更合适的位置。

## 先检查触发，再检查执行内容

设想团队有一个“生成月度数据报告”的 Skill。有人为了提高使用率，把描述写成“涉及数据、图表、报表或分析时使用”。现在用户只想知道某个查询字段的含义，Agent 却开始读取报告模板、导出流程与版式要求。这里的问题已经发生在选择阶段：即使报告流程本身完全正确，它也没有回应当前任务。

一种更容易检验的描述是：“根据月度业务数据生成约定格式的报告；用户要求生成或更新月报时使用。”这个例子是本文构造的。它把可识别的任务动作写进了入口，让使用者能够列出正反案例，而不只是判断文字看起来是否清楚。

| 请求示例 | 是否使用 Skill | 判断理由 |
| --- | --- | --- |
| 根据本月数据生成经营月报 | 是 | 需要约定的报告产物 |
| 更新已有月报中的本月数据 | 是 | 仍在维护同一类产物 |
| 解释查询中的字段含义 | 否 | 只需要理解字段 |
| 帮我比较两个数据源 | 需结合目标判断 | 可能尚未涉及月报 |

这张表还能区分两类修复。如果入口误触发，应修改描述或任务边界；如果触发正确但结果格式错误，才需要检查正文、模板或脚本。把两种失败混在一起，容易不断扩充 Skill，反而扩大它干预任务的范围。

## 让规则出现在需要它的地方

沿用月报场景，生成报告、更新数据和检查导出结果，可能需要不同材料。入口文件可以说明各材料解决什么问题，再由当前任务决定读取范围。目录清晰只是第一步，路由说明还要能帮助模型作决定：什么时候需要模板，什么时候需要字段说明，什么时候需要导出检查。

这种整理会引出一个实际取舍。提前读完所有材料，选择负担较小，却会让简单任务承担整套流程的成本；按需读取减少了初始材料，但要求入口足够准确。若入口只列出一串文件名，必要规则仍可能被漏读。因此，审计时可以逐条追问：这项要求在哪个动作之前必须已知？它的入口能否覆盖那个时刻？

仓库级规则也可以按这个问题整理。例如，统一的输出目录适合在相关任务开始时可见；只有导出 PDF 才需要的字体检查，则可以放到导出流程中。这里调整的是信息出现的位置。规则是否必要，要根据项目契约判断，不能仅凭模型能力更强就作决定。

## 用交付证据定义完成

假设任务是“更新月报并导出 PDF”，生成源文件只完成了其中一部分。可以把完成标准写成一条可检查的链：数据已更新，PDF 已生成，渲染结果已检查，交付位置已明确。这样，执行者知道还剩什么，审查者也知道该看什么。

同时，需要说明自主执行的范围。例如，测试数据和本地输出目录可以允许反复生成、检查和修正；发送给外部收件人则是另一个动作，应按实际授权处理。这样的描述提供了具体环境和动作边界，执行者遇到问题时更容易判断能否继续。

从工程上看，提示词中的完成标准与运行环境中的权限控制承担不同职责。前者帮助 Agent 组织工作，后者约束实际可执行的操作。对模型判断力的期待，不能作为某项外部操作已经获得授权的证据；同样，允许继续处理本地任务，也不意味着可以无限扩大工作范围。

## 把指令修改作为可验证的变更

整理规则之后，可以固定几类代表任务，比较修改前后的运行：应该触发的任务有没有漏掉，无关任务是否还会加载整套材料，必要检查是否完成，交付是否达到同一个标准。上述月报案例中的正反请求就可以作为起点。需要时再补充耗时、读取量和人工介入次数，解释变化发生在哪一环。

这里的验收对象是任务结果。文件变短、读取变少，都只能说明过程发生了变化；如果报告遗漏数据，或在生成 PDF 前就停下，修改仍然需要调整。反过来，必要的检查即使增加了几步，也可能直接支撑交付要求。

对于共享仓库，还可以保留规则的来源说明：它保护什么约定，曾经对应哪类失败，在哪些运行条件下检查过。以后更换模型或工具时，维护者就能重新验证这些前提。这样的记录也让删除规则有据可查，避免在下一次失败后凭印象把旧指令全部加回来。
