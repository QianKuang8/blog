改一段提示词，评估分数涨了两个点，这个改动该不该留下？回答它需要两样东西：一个可信的评估，以及一套不会骗过自己的迭代方法。Lance Martin 在 [Automating eval design and hillclimbing with Claude](https://claude.dev/blog/automating-eval-design-and-hillclimbing/) 中把这两部分整理成原则，并写进了 `claude-api` Skill 的两个子命令：`/claude-api build-eval` 在代码库里构建评估，`/claude-api hillclimb` 据此逐轮改进应用。

这篇值得读，是因为它把很多团队靠经验掌握的做法写成了可执行的检查：评估先过哪几项体检，评分器怎样确认可信，每轮改什么、改完按什么规则保留，分数停滞时先查什么。文末两个案例给出了完整的数字。下面按原文的顺序梳理，最后一节讨论留出集在这个流程里实际承担的角色。

## 好评估的四个特征

作者列出四条，每一条都可以当作对评估本身的检查：

| 特征 | 怎样检查 | 不满足时常见的原因 |
| --- | --- | --- |
| 任务贴近生产 | 任务分布是否代表实际要处理的问题 | 因为容易生成或容易判分才选了某些任务 |
| 更强的模型、更高的 effort 得分更高 | 换模型或调高 effort 后，分数是否按预期上升 | 任务有歧义，或评分器没有校准好 |
| 最强配置仍有提升空间 | 最强模型在最高 effort 下明显低于 100%，且差距来自可以完成的任务 | 评估已接近饱和；或者剩下的差距来自无法完成、有歧义的任务 |
| 重复运行波动小 | 同一配置多跑几次，分数是否稳定 | 任务有歧义；评分器对相同输出给出不同结论；effort 等配置没有一致生效；上一次试验留下的文件或 git 历史泄露了答案 |

第三条有一个实用的判别方法：某道题无论重复多少次都失败，多半是题目本身有问题。作者对好任务的定义是：两位领域专家会给出相同结论，评分器检查的每一项都在任务里写明了。

第二条也值得单独记住。它把模型能力当作评估的对照组：更强的模型分数没有更高时，先怀疑评估，再怀疑模型。

选样本时，作者提醒避免“对抗式采样”，即只挑今天的模型做错的题。模型能力参差不齐，这样挑出来的是某一个模型能力曲面上的低谷，评估最后测到的是这个模型的失败特征，而不是应用本身的难点和价值所在；下一代模型的低谷也可能在别处。更好的做法是由人判断哪些任务难，并且在收录前能说出它难在哪里；也要收录来自生产流量、bug 报告和工单的具体失败。用户流量本身也要谨慎使用：用户有时只尝试他们预期能成功的事，完全从用户流量抽样的任务分布可能偏简单。

## build-eval：先让人确认样例和评分器

运行 `/claude-api build-eval` 时，Claude 先访谈用户，再在代码库里构建评估，并在几个节点停下来等用户确认。

样例来源有先后顺序：生产 transcript（先询问数据保留和敏感信息的要求），bug 报告与支持工单，用户手写的 5 到 10 个用例，最后才是根据代码库合成的用例。合成数据也以用户提供的少量真实样例为锚点。所有输入会生成一个页面供用户逐条查看，用户确认后才继续。

评分器选择满足需求的最便宜方案：

- 输出空间受限时用程序判分：精确匹配、固定标签集合、符合 JSON schema、测试通过。
- 输出开放、合理答案很多但质量标准清楚时，默认用 LLM-as-judge。评分依据写成可以逐条核对的陈述，不用 1 到 5 分的量表；有基线时，评审模型以随机顺序阅读两份输出，不知道哪份是基线，只选出更好的一份。评审模型由用户选择，并且应当与被测模型不同。

接着 Claude 先给少量用例打分，问用户是否会给出不同的分数。作者特别强调，相信评估器之前要阅读一批已评分的 transcript，评分错误是评估配置出错最常见的原因之一。站内的[产品评估三步法]({{< relref "/posts/product-evals.md" >}})把这一步展开成了人工标注与评估器对齐的完整流程。

评分器确认后，Skill 会报告评估规模（用例数 × 重复次数 × 模型数，以及大致耗时），运行基线，给出带置信区间的分数。产出包括用例、评分器、运行器、每个用例一行 JSON 和一份完整 transcript，以及一个列出逐例分数、链接到各自 transcript 的简单页面。

运行基线时还会做三项诊断：

- **评分器**：对同一份输出评两次，报告结论是否改变。
- **管线**：检查超时、API 错误和被截断的回答，避免把基础设施的噪声当成模型的波动。
- **提升空间**：基线已经达到约 95% 或更高时发出提醒，建议 hillclimb 转向成本或延迟。

## 选什么来 hillclimb，过拟合从哪里来

hillclimbing 指在当前配置附近反复尝试修改，按评估反馈决定是否保留。作者给出三条选择优化对象的标准：

- **迭代便宜**：修改和回滚的时间、成本都低。提示词、Skill 这类文本最适合；对 Harness 做开放式改动可能涉及大量代码。
- **分数变化可以归因**：分数变化应当来自被修改的对象。作者举的成功例子是 Skill 触发：触发率这个指标直接由被修改的 Skill 描述决定。
- **目标范围清楚**：在接近饱和的评估上“提升性能”，或者笼统地“改进 Harness”，都容易停滞。成本是一个通用的好目标：评估饱和了，仍然可以在质量持平的前提下降低成本。

过拟合是这一节的重点。评估很少与生产中的任务分布完全一致，hillclimb 可能把评估自身的特征写进 Harness，也就是模型周围的提示词、工具和调用循环。

![左侧列出基准的特征，右侧列出对应加进 Harness 的内容：任务需要 OCR 就加 OCR 工具，任务都在 /app 下就加“总是 cd /app 再运行 pytest”，题目有特有的措辞就把提示词调向这些措辞，读过的失败各打一个补丁；虚线标出直接泄露：存在带答案的公开仓库，Harness 就去 curl 参考解。](/images/automating-eval-design-and-hillclimbing/harness-overfitting.png)

*图 1：原图，来源：[Automating eval design and hillclimbing with Claude](https://claude.dev/blog/automating-eval-design-and-hillclimbing/) Figure 5。前四种改动都能提高评估分数，对生产流量却没有帮助；虚线一项是直接拿到答案。*

图中第一项是原文的例子：评估任务大多受益于 OCR，生产任务却很少需要，hillclimb 给应用加上 OCR 工具后，评估分数提高，生产表现不变。作者给出三项对策：

1. **拆分用例**：hillclimb 可以读取 train 集，test 集从不展示。train 分数上涨而 test 持平，是常见的过拟合信号。
2. **不把失败内容贴进提示词**：可以阅读失败的 transcript，但不把其中的内容复制进提示词。
3. **从结构上让模型拿不到答案**：模型有时会直接找到评估的答案，也就是 reward hacking。

## hillclimb 每一轮怎样决定保留

运行 `/claude-api hillclimb` 时，用户先指定 Claude 可以修改的范围：system prompt、Skill 或指令文件、工具描述、模型选择与 effort 等 API 参数、Harness 代码。Claude 再询问优化目标（提升质量，或在质量持平时降低成本），然后把评估集随机拆成 train 和 test。目标是成本时，它会先考虑几个常见的成本来源：Prompt Caching、按所选模型审计提示词、选择模型与 effort。

第一轮之前，Claude 检查评估的噪声，也就是分数仅凭随机能移动多少，是否小于用户愿意采取行动的最小提升。噪声更大时，它会直接说明，并建议增加重复次数或用例。

此后每一轮：

1. 读取上一轮 train 的 transcript，以 patch 的形式提出一处修改。
2. 这处修改要让效果有机会超过噪声，所以从根源修复失败行为，例如重写导致问题的那一段，或补上缺失的规则；逐句改措辞这类小修不在考虑之列。
3. 运行评估，按规则决定：train 上涨而 test 持平，怀疑过拟合，回滚；出现退步，回滚；train 和 test 都上涨，保留。原文邮件分流的示意报告里，v1 给每个队列下定义并加一条平局规则，train 和 test 都到 0.875，被保留；v2 加了两个完整示例，train 上涨、test 持平，被回滚。

![Hillclimbing 流程：被编辑的对象（例如提示词）送入固定的模型与 Harness，分别在留出的 test 和 train 上评分；分析者只读取 train 的失败，每轮提出一个 diff；train 与 test 都上涨时保留，只有 train 上涨或任一边下降时回滚。](/images/automating-eval-design-and-hillclimbing/hillclimb-loop.png)

*图 2：原图，来源同上 Figure 6。分析者看不到 test 的样例内容，但每轮的保留和回滚都参考 test 分数。*

分数连续两三轮停滞时，Claude 暂停修改，逐条阅读剩余的 train 失败并按原因归类；如果判断任何单项修复都超不过噪声，也会提前做这一步，并建议增加重复次数或用例。这一步能发现有歧义的用例、Harness 错误和运行波动，此后只有确属应用本身的失败进入后续轮次。

结束时，代码停在 test 上表现最好的版本，Claude 报告相对基线的 test 结果和置信区间；提升落在噪声范围内时，它会明说，并建议不要合并。

## 两个案例

**降成本。** 作者在一个内部客服基准上运行 hillclimb，目标是降低成本并提升质量（这个基准的背景见站内的 [Claude Platform 成本优化]({{< relref "/posts/reducing-cost-and-improving-performance-with-claude-platform.md" >}})）。基准有 44 张工单，30 张用于搜索，14 张留出：

| 步骤 | 配置 | 搜索集决策准确率 | 每张工单成本 |
| --- | --- | --- | --- |
| 起点 | Opus 4.8，默认 effort（high） | 74.4% | 4.6 美分 |
| 审计提示词：删去强制的工具调用流程、草稿步骤和相互矛盾的规则；再换模型 | Opus 5.5，low effort | 87.8% | 1.9 美分 |
| 已超过基线，降一档模型试试 | Sonnet 5，low effort | 88.9% | 约 1 美分 |
| 补充路由规则和退款上限的交叉引用 | Sonnet 5，low effort | 98.9% | 约 1 美分 |

Opus 5.5 这一步的节省有一部分来自定价：输入和输出 token 比 Opus 4.8 便宜 20%，缓存读取便宜 60%。在搜索从未接触的 14 张留出工单上，最终配置得分 90.5%，原配置 78.6%，成本约为原来的五分之一。

两组数字放在一起看更有意思。起点时留出集的分数反而高于搜索集（78.6% 对 74.4%），终点时搜索集提高了 24.5 个百分点，留出集提高了 11.9 个百分点。我的理解是，搜索过程中有相当一部分收益只适用于那 30 张工单，只看搜索集会高估这次改进；留出集的价值就体现在这个差距上。

**提升一份 Skill 的质量。** 第二个案例的对象是 `claude-api` Skill 本身，评估集根据 API 文档构建，检查用了 Skill 以后能否正确写出调用 API 的代码。起点 66%。hillclimb 可以访问文档和 SDK，发现 Skill 缺少 8 个功能的说明，补上后到 74%；修正 C# 和 Java 的类型表后到 77%。

随后分数停滞两轮，Claude 进入归类步骤，有两项发现：

- 内容已经写在 Skill 里，Claude 仍然写出训练中记住的旧 API 形式。于是在 Skill 开头加了一张对照表，把它记得的写法映射到当前写法，例如从固定 token 预算的 extended thinking（新近的 Opus 模型会拒绝这种调用）改为 adaptive thinking，从旧版 web search、web fetch 工具改为当前版本；同时把 C# 和 Java 中禁止固定预算 thinking 的警告移到 adaptive thinking 示例之前。分数到 80%。
- 补上明显缺失的内容后始终没有改善的任务，往往是题目或评分器有问题。一道题要求只捕获一种错误类型，评分器却要求至少三层的错误链，Claude 改写了题目；另一个评分器的说明与文档矛盾，实际调用 API 证明文档正确。修正这些问题并继续修改 Skill 后，分数到 87.9%。

这个案例里最有价值的是归类步骤。每轮一处修改擅长补具体的缺失内容；模型受旧知识影响、题目与评分器本身出错这两类问题，要把失败放在一起看才发现得了。我认为还要注意，后半段的提升有一部分来自修正评估：题目和评分器变了，前后分数衡量的已经是两套标准，对比新旧版本时应当在修正后的评估上重跑基线。

## 留出集参与选择之后

hillclimb 的 test 集与通常意义的测试集有一处差别：分析者看不到 test 的样例，但每一轮的保留、回滚，以及最后停在哪个版本，都参考 test 分数。内容隔离挡住了针对具体题目打补丁；反复参与选择，又让 test 在实验设计上承担了验证集的作用。轮次越多，越可能选中一个碰巧适合这批留出题的版本。降成本案例只有 14 张留出工单；原文没有说明它们是否就是每轮参与保留判断的 test 集，如果是，这种风险更明显。

需要对外报告效果或据此决定上线的项目，可以把数据分成三份：

| 数据用途 | 是否参与迭代 | 回答的问题 |
| --- | --- | --- |
| train | 读取失败并修改 | 当前方法为什么出错 |
| test（验证） | 只用分数筛选候选 | 这轮修改是否值得保留 |
| 最终测试 | 版本冻结后只用一次 | 选定版本在没参与选择的任务上表现怎样 |

hillclimb 已经报告置信区间，并在提升落在噪声内时建议不合并，这能挡住多数偶然的提升；最终测试补上的是另一件事，即衡量多轮筛选本身带来的乐观偏差。[skill-creator 解读]({{< relref "/posts/anthropic-skill-creator-breakdown.md" >}})讨论过同样的问题：那里的描述优化循环中，40% 的留出样例也参与了候选选择。这一节是本文的分析，原文没有讨论最终测试集。
