“分析这份报告”和“从报告中提取指定指标，缺失值写为 null，输出供程序读取的 JSON”，交给模型的是两个不同清晰度的任务。前者留下用途、范围和格式供模型猜测，后者说明了如何处理输入和判断结果。

Claude 官方的 [Prompt engineering best practices](https://claude.com/blog/best-practices-for-prompt-engineering) 从这些基本问题出发，再讨论示例、格式和任务拆分。本文依据 2026 年 6 月保存的文章版本解释其方法；其中涉及模型或 API 的技巧，应按实际使用版本确认支持情况。

## 指令要表达结果，也要交代用途

原文建议直接说明动作、范围和质量预期。只写“创建一个分析仪表盘”，模型需要自行决定包含哪些功能、做到什么程度。补充相关交互和完整性要求，能减少这种歧义，但“功能尽量多”也只是原文特定示例的偏好，不适合成为所有产品任务的默认目标。

更可迁移的做法，是把需求中影响实现的条件写出来：面向谁，拿什么材料工作，交付什么，哪些约束必须遵守。输出若用于自动处理，格式就是接口要求；输出若用于人类讨论，解释的深度和组织方式则可能更重要。

原文还强调动机。例如，表达“偏好连贯段落，因为更便于阅读”，比只禁止列表更能帮助模型处理相邻选择。理由不是额外装饰，它提供了规则未覆盖场景下的判断方向。当然，动机不能代替明确约束；有精确格式要求时，仍应直接给出。

## 示例用于传递难以描述的模式

当格式或语气很难靠抽象形容词表达时，一个示例可以同时展示字段、长度、措辞和结构。原文建议先给一个，只有结果仍不稳定时才继续增加。

示例的副作用是，它也会传递不想保留的规律。若示例省略了缺失值处理，模型可能照样省略；若示例语气与文字指令不一致，它就收到两种信号。因此，示例要和目标输出一起审查，而不是只检查看起来是否专业。

原文将这一点与上下文成本联系起来。多个例子、详细说明和额外步骤都会占用输入。增加一个示例之后，应该观察它是否减少了某类错误；若只是重复同一模式，未必值得继续保留。

## 为缺失信息定义合法输出

文章建议明确允许模型表达不确定。对信息提取任务，这可以转化为更具体的规则：材料没有明确给出的指标，返回 `null`；证据不足以支持趋势判断时，说明缺口。

下面沿用原文的指标提取场景，整理为一个示意提示，并非经过本文实测的通用模板：

```text
从所附季度报告提取 revenue、profit_margin、growth_rate。
结果用于自动处理，只返回包含这三个字段的 JSON。
保留报告中的单位和期间口径。
报告未明确给出的字段使用 null，不按其他指标推算。
```

它把缺失值变成允许的结果，降低模型为凑齐字段而猜测的压力。但一句“不猜测”不能保证可靠性。程序仍需检查 JSON 是否可解析，字段与单位是否符合约定，重要数值是否能回到原文。提示表达行为目标，验证负责检查实际输出。

原文也介绍了通过预填响应开头影响格式的技巧，例如从左花括号开始生成。它可以约束开头，却不能凭自身保证完整 JSON 合法或内容正确；具体模型是否支持该接口，也需要按版本确认。因此，阅读时应把格式引导与格式校验分开。

## 多阶段任务在有检查价值时再拆开

当一次请求同时包含研究、整理和校对，错误可能难以定位：究竟是材料理解有误，还是写作时丢了条件？原文提出 prompt chaining，让每次调用承担一个阶段，上一阶段的输出成为下一阶段的输入。

例如，先形成摘要，再按准确性和完整性检查，最后根据发现修订。分拆的价值在中间结果可以被检查。如果每个阶段只是重复表述同一个目标，多次调用可能只增加延迟和费用。

这个方法也需要交接契约。检查者若只看到摘要，看不到原始材料，能够审查的是结构和内部一致性，未必能发现事实遗漏。将必要证据随中间产物传递，是从原文方法推导出的工程要求。拆分既要缩小任务，也要保留完成该任务所需的输入。

原文还讨论 extended thinking、XML 边界与角色设定。更稳妥的选择方式，是先识别失败：需要区分资料与指令时增加结构，需要固定分析视角时写明关注项，需要多步判断时给足推理预算。没有相应问题，就不必把全部技巧叠加进去。

## 用输出变化判断提示是否更好

文章最后回到迭代：先写清基本任务，查看输出，再为具体失败增加结构。对同一组有代表性的输入，可以比较字段是否齐全、事实是否有依据、格式是否稳定，以及完成任务需要多少修订。

这些观察项比提示的长度或术语数量更贴近目标。若问题是资料缺失，就先补资料；若问题是格式不稳定，再强化输出约定；若问题跨越多个阶段，才考虑拆分。每次修改回应一类已观察到的问题，提示就更容易维护，也更容易解释为何有效。
