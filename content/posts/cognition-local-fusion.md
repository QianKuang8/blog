Coding Agent 的成本优化需要回答一个具体问题：哪些工作值得交给另一个模型，交出去以后又要花多少精力检查？Cognition 的 [《Introducing Fusion in Devin Desktop & CLI》](https://cognition.com/blog/local-fusion) 提供了一个双 Agent 的例子。理解它的价值，需要同时看工作如何分配、信息如何传递，以及最终结果是否满足要求。

## 两份上下文，一个会话负责人

原文介绍的 Fusion 由 Lead 和 Sidekick 组成：Lead 使用前沿模型，负责规划、处理歧义和审查；Sidekick 承接任务，探索代码、实现并运行测试。双方各自维护持久上下文与工具，通过任务说明、结果和反馈沟通。Lead 保留会话控制权，必要时接管执行；这种上下文组织也用于利用 prompt caching。[来源：Fusion 架构说明](https://cognition.com/blog/local-fusion#the-fusion-architecture)

![Fusion 分工示意：用户与 Lead 交互，Lead 向 Sidekick 下发任务并审查返回结果，两个 Agent 各自保留上下文。](/blog/images/cognition-local-fusion/lead-sidekick.svg)

*根据原文架构说明整理。图中表示职责和信息流，不表示底层调度时序。*

从工程上理解，两份上下文让系统可以决定信息的接收者。搜索中遇到的无关文件、一次失败命令的完整输出，可能对执行过程有用，却未必需要全部进入最终审查。不过，减少传递也带来一个新问题：执行者如何判断哪些信息必须向负责人报告？如果筛选掉的恰好是反例，审查者就可能依据一份过于乐观的摘要作决定。

因此，可以把这类架构的设计重点放在交接处：Lead 给出的内容能否支撑独立执行，Sidekick 返回的内容能否支撑独立判断。两个模型之间传了多少 token，只能描述通信量；这些信息是否足以作决定，才关系到任务能否完成。

## 把委派写成可检查的任务契约

下面以“修复分页接口重复返回记录”为例说明一种可能的委派方式。这是用于分析的假设案例，并非原文披露的 Fusion 提示模板或产品行为。

| 交接内容 | 示例 |
| --- | --- |
| 目标 | 相邻分页之间不重复返回同一条记录 |
| 约束 | 保持现有响应字段和排序约定 |
| 验收 | 构造排序字段相同的记录，检查跨页结果 |
| 需要上报的发现 | 现有分页协议无法表达稳定的排序位置 |

这样的说明仍然把实现空间留给执行者，同时让负责人能够检查结果是否回应了问题。反过来，只说“修好分页并跑测试”，就把需求解释、测试范围和完成标准一起交了出去。返回一句“测试通过”，很难判断它修复的是用户问题，还是某个更容易处理的局部症状。

同样，返回结果可以包含修改位置、验证命令及结果、尚未验证的情况，以及影响原计划的新发现。这里没有必要复制整个终端历史，但需要让负责人能沿着证据回到实际改动。若执行者发现需求与现有协议冲突，交接的价值就体现为及时修订计划，而不是继续扩大补丁。

这一分析也给任务拆分提供了判断标准：在下发之前，能否说明什么结果算完成？如果连验收对象都尚不清楚，可以先委派一个有边界的调查任务，例如定位重复记录出现的条件，再决定后续实现范围。

## 用任务总账检验分工是否划算

为了分析成本，可以把一次运行粗略拆成三部分：

> 任务成本 = 规划与委派成本 + 执行成本 + 审查与返工成本。

这是便于讨论的成本拆分，不是 Fusion 的计费公式。它提醒我们检查一种常见情况：执行阶段变便宜了，负责人是否因此需要花更多轮次补充说明、纠正实现或重新调查？如果后两类开销没有被记录，选型时就容易把局部节省当成完整收益。

Cognition 公布的数据也需要把分数和成本一起读。以下选取原文中 Astra 与 Astra + SWE-2 的两项对比，保留其报告口径；本文未独立复现这些评测。

| 评测 | Astra：分数 / 成本 | Fusion：分数 / 成本 |
| --- | --- | --- |
| DeepSWE 1.1 | 67.6 / $7.88 | 67.3 / $4.69 |
| Terminal-Bench 4 | 55.6 / $10.08 | 50.0 / $6.06 |

*数据来源：[原文评测表](https://cognition.com/blog/local-fusion#savings-across-benchmarks)。*

这两行的阅读重点不同：前者在成本下降时分数接近，后者同时出现了更明显的分数下降。它们说明，接受某种分工配置之前，需要先定义质量底线。对于失败后必须人工接手的任务，便宜的一次运行还可能伴随额外的交付成本；只比较单次运行账单，无法回答整个流程是否划算。

## 如何在自己的 Harness 中验证

若把这种分工方式用于自己的 Agent，一个可操作的评估方法是固定一组任务，分别运行现有方案与候选组合，再按相同标准检查产物。除了任务结果和总费用，还可以记录委派后的补充说明次数、审查退回次数、负责人接管情况和整体耗时。这些是本文提出的观察项，并非原文公开的完整评测协议。

接下来应当沿失败轨迹修改分工。如果执行者持续误解同一约束，就检查任务说明是否清楚；如果负责人频繁重做调查，就检查返回材料是否缺少可核实的依据；如果耗时主要来自等待，就检查任务之间是否存在无法并行的依赖。每次调整都对应一个可观察的问题，再回到同一组任务检查效果。

更换模型以后，也应重新检查这条交接链。原来需要详细说明的步骤，可能已经能独立完成；原来可靠的结果摘要，也可能遗漏新的失败类型。对这类双 Agent 系统而言，值得持续维护的是任务、证据和验收之间的关系。只有这条关系清楚，成本变化才容易解释，配置调整才有依据。
