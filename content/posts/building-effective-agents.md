给 LLM 接上工具以后，下一步该由代码安排，还是交给模型决定？Anthropic 的 [Building Effective Agents](https://www.anthropic.com/engineering/building-effective-agents) 围绕这个问题整理了多种生产实践。文章建议先找到足够简单的方案，只有评估表明新增复杂度改善了结果，才继续增加步骤或自主性。

这不是一张必须依次升级的架构路线图。一次带检索的模型调用、固定工作流和自主 Agent 各有适用条件，也可以组合使用。设计时需要识别的是任务中哪部分已经明确，哪部分必须在执行后才能知道。

## 控制流由谁决定

原文把预先由代码定义路径的系统称为 Workflow，把由 LLM 动态决定过程与工具使用的系统称为 Agent。两者都可以调用模型、搜索信息和执行操作，区别在于下一步的决策权。

如果任务能够稳定拆成“大纲—检查—正文”，程序可以规定顺序，并在中间设置检查门槛。这样的 prompt chaining 把一次复杂生成变成几次较容易的调用，代价是更多延迟。如果输入本来就分为几类，例如退款咨询与技术支持，routing 则先分类，再把请求送到不同提示与工具流程；它能否奏效，取决于分类是否足够可靠。

这两种模式都要求开发者先掌握任务结构。若一个问题只需检索相关材料并作答，文章建议先优化单次调用，不必为了使用 Agent 而增加循环。

## 并行、委派与反馈解决不同问题

原文的并行模式有两种用途。一种把可独立完成的部分分开执行，例如分别评估不同质量维度，以减少等待；另一种让多个调用处理同一问题，再汇总或投票，以获得不同视角。后者增加计算投入，但是否提高置信度仍需评测，重复调用本身不保证答案独立或正确。

Orchestrator-workers 处理的是另一类不确定性：任务开始时无法预先列出全部子任务。协调模型先根据输入拆解工作，再交给执行模型，最后整合结果。多文件代码修改就是原文的例子，涉及哪些文件、每处改什么，往往要理解具体需求后才能决定。它与固定并行的差异是子任务动态生成，而不仅是多开几个模型。

Evaluator-optimizer 则建立生成与反馈循环：一个调用产出候选，另一个调用检查并给出修改意见。适用前提包括明确的评价标准，以及反馈能够带来可测改进。没有这样的条件，循环可能只是反复润色，无法说明输出更接近目标。

这些模式对应不同输入和输出：路由输出处理分支，协调者输出任务划分，评价者输出可执行反馈。把它们区分清楚，比把所有多调用系统统称为多 Agent 更有助于调试。

## 自主循环必须从环境获得反馈

当步骤数量和执行路径都难以事先确定时，原文才进一步讨论 Agent。用户给出目标后，模型规划行动，调用工具，读取环境返回，再决定继续、调整、请求帮助或停止。

这里不能只让模型根据自己的叙述判断进展。代码执行结果、工具响应等环境反馈，才是下一轮决策的重要依据。原文也建议设置人工检查点和终止条件，例如最大迭代次数，以控制成本和错误累积。

Coding Agent 是较适合这一循环的场景：代码与测试提供了结构化反馈，失败结果可以引导下一轮修改。不过，自动测试主要验证被覆盖的功能，是否符合更广泛的系统要求仍需要人工审查。测试通过和任务整体完成，需要保持各自的判断范围。

## 工具接口决定模型能否正确行动

架构确定后，模型仍要通过具体工具接触环境。Anthropic 把这层设计称为 Agent-Computer Interface（ACI）。同一个文件修改，既可以要求模型输出带行号的 diff，也可以输出完整内容；同一段代码，放在 Markdown 与放在 JSON 字符串中，模型承担的格式负担并不相同。

原文建议减少无必要的计数和转义要求，并把工具名称、参数、使用示例、边界情况以及相近工具之间的区别写清楚。之后应观察模型实际怎么调用，再根据错误调整接口，而不是只检查工具函数本身能否执行。

一个具体案例是路径处理：Agent 离开仓库根目录后，使用相对路径会出错。团队让工具统一要求绝对路径，消除了这类歧义。这个例子说明，重复失败有时可以通过参数约束直接消除，无需继续堆叠提醒。

框架能减少调用和编排的样板工作，但也可能隐藏提示、响应和状态变化。选择框架时，仍应能够追踪一次任务的输入、分支、工具调用与结果。文章提供的共同原则，是让新增能力有评估依据，让失败有可定位的过程，并让工具接口尽量减少可预见的错误。
